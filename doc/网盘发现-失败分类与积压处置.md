# 网盘发现:失败分类、积压处置与三条链的落点

> 面向「积压 N 条该怎么办」。**先看失败原因再动手** —— 同一句「积压 77 条」背后
> 可能是三件完全不同的事,对应的动作互相不能替代。

## 一、积压的构成怎么读

`pan_discovery` 的积压(`pending` + `failed`)是**待办队列**:每一轮都会把这些行重新试一遍。
所以「积压不降」有两种性质完全不同的原因:

| 现象 | 性质 | 该做什么 |
|---|---|---|
| `pending` 多、`failed` 少 | **额度**不够,链是好的 | 调 `PAN_DISCOVERY_TRANSFER_LIMIT`(积压额度)/ `PAN_DISCOVERY_FRESH_LIMIT`(新发现额度) |
| `failed` 多、`pending` 少 | **链或落点**的问题 | 看具体措辞,别调额度 —— 调了只会让同一批多跑几遍 |
| `pending` 多但原因写着「空间不足」 | **盘满**(见 §三) | 清理盘 / 加号 |

## 二、`failed` 的几种措辞分别是什么意思

| 措辞 | 含义 | 终态? |
|---|---|---|
| `转存失败(errno=-32 剩余空间不足，无法转存)` | **百度盘没有空间**(见 §三) | 否(清盘后能搬) |
| `转存失败(errno=2 转存路径不存在)` | 目标目录被删(代码会**自动补建**再重试一次) | 否 |
| `提取码验证失败(errno=105)` | ⚠️ **曾经是本仓自己的 bug**,见 §二.1 | 否 |
| `分享地址已失效(errno=105):…分享页 404` | 死链(有 404 证据才会这样写) | **是**(`skipped`) |
| `转存被限制(errno=105/-70),稍后重试` | 这一步是 `/share/transfer`,与上面那个 105 **不是一回事** | 否 |
| `PASS_CODE_EMPTY` / `SENSITIVE_RESOURCE` | 迅雷分享状态本身异常 | **是**(`skipped`) |

判终态的门槛是「**有确凿证据**」(分享页 404 / 状态码原文)。宁可多试一次,
也不把一条能搬的链永久钉死 —— 这个反方向的坑 2026-10-02 踩过。

### 二.1 `提取码验证失败(errno=105)`:链没坏,是我们把 `surl` 切歪了

**2026-10-25 受控 A/B**(同一条链、同一个 Cookie、相隔 1 秒):

| `surl` 入参 | `/share/verify` |
|---|---|
| `Ftzp5KvW7tYegpsm48Qu_w?pwd=0000` | **`errno=105`** |
| `Ftzp5KvW7tYegpsm48Qu_w` | **`errno=0`**(验码通过,能列出文件) |

根因:`transfer_and_share` 用 `share_url.split("/s/1")[1]` 取 surl,把 `?pwd=xxxx`
**一起带进去了**。凡是**链接里自带提取码**的候选,每轮都死在验码这步;而分享页本身是活的
⇒ `_share_page_gone` 正确地判 False ⇒ **永远判不了终态** ⇒ 每天重试、每天同样失败。

生产库里那 35 条 `failed` 全属这一类(`origin_url` 100% 带 `?pwd=`)。

修法:新增 `baidupan_transfer.surl_of()`,一律只取路径段。修完复测同一条链:
验码通过、文件列表读得出,一直走到 `/share/transfer` 才被 `errno=-32` 挡下
(**证明链是好的,只是盘没空间** —— 见 §三)。

## 三、百度盘:超额 43 倍,这才是 40 条的真正落点

2026-10-25 实测(唯一那个百度号 `百度2`,`/api/quota`):

```
total = 128_849_018_880   (≈120 GiB)
used  = 5_573_035_305_813 (≈5.07 TiB)
ratio ≈ 43.2              ← 超额,不是"用了 43%"
```

⇒ `errno=-32 剩余空间不足` 是**真的**,重试一万次也不会变。两条出路:

1. **清理百度盘**(删掉历史转存;注意:删掉我们自己的落点目录会让我们发出去的链失效);
2. **换/加一个还有空间的百度号**(「Cookie 管理」里加一个)。

⚠️ 代码侧已改为**先探配额再决定要不要逐条转存**:配额已超额时,当轮**一条都不去撞**,
直接把这批标成 `pending` 并写明 `百度盘空间不足(已用 5.07 TB / 配额 120.00 GB,超额 43 倍)`。
清理出空间后下一轮**自动继续**,不需要人工重新排队。

## 四、告警文案的纪律

`_alert_backlog` 的动作必须**按证据给**,三种构成给三件不同的事。
2026-10-25 修掉的那次是:积压全是 `errno=-32` 时,它落到最后的
「**这些是链本身的问题**」那一支 —— **让人去查链,而链一条都没坏**。
「给错动作比不给动作更坏」:照着做完没用,下次就没人看告警了。
