# 网盘发现:失败分类、积压处置与三条链的落点

> 面向「积压 N 条该怎么办」。**先看失败原因再动手** —— 同一句「积压 77 条」背后
> 可能是三件完全不同的事,对应的动作互相不能替代。

## 一、积压的构成怎么读

`pan_discovery` 的积压(`pending` + `failed`)是**待办队列**:每一轮都会把这些行重新试一遍。
所以「积压不降」有两种性质完全不同的原因:

| 现象 | 性质 | 该做什么 |
|---|---|---|
| `pending` 多、`failed` 少 | **额度**不够,链是好的 | 调 `PAN_DISCOVERY_TRANSFER_LIMIT`(积压额度)/ `PAN_DISCOVERY_FRESH_LIMIT`(新发现额度) |
| `failed` 多、`pending` 少 | **链或落点**的问题 | 看具体措辞,别调额度 —— 调了只会让同一批多跑几遍 |
| `pending` 多但原因写着「空间不足」 | **盘满**(见 §三) | 清理盘 / 加号 |

## 二、`failed` 的几种措辞分别是什么意思

| 措辞 | 含义 | 终态? |
|---|---|---|
| `转存失败(errno=-32 剩余空间不足，无法转存)` | **百度盘没有空间**(见 §三) | 否(清盘后能搬) |
| `转存失败(errno=2 转存路径不存在)` | 目标目录被删(代码会**自动补建**再重试一次) | 否 |
| `提取码验证失败(errno=105)` | ⚠️ **曾经是本仓自己的 bug**,见 §二.1 | 否 |
| `分享地址已失效(errno=105):…分享页 404` | 死链(有 404 证据才会这样写) | **是**(`skipped`) |
| `转存被限制(errno=105/-70),稍后重试` | 这一步是 `/share/transfer`,与上面那个 105 **不是一回事** | 否 |
| `PASS_CODE_EMPTY` / `SENSITIVE_RESOURCE` | 迅雷分享状态本身异常 | **是**(`skipped`) |

判终态的门槛是「**有确凿证据**」(分享页 404 / 状态码原文)。宁可多试一次,
也不把一条能搬的链永久钉死 —— 这个反方向的坑 2026-10-02 踩过。

### 二.1 `提取码验证失败(errno=105)`:链没坏,是我们把 `surl` 切歪了

**2026-10-25 受控 A/B**(同一条链、同一个 Cookie、相隔 1 秒):

| `surl` 入参 | `/share/verify` |
|---|---|
| `Ftzp5KvW7tYegpsm48Qu_w?pwd=0000` | **`errno=105`** |
| `Ftzp5KvW7tYegpsm48Qu_w` | **`errno=0`**(验码通过,能列出文件) |

根因:`transfer_and_share` 用 `share_url.split("/s/1")[1]` 取 surl,把 `?pwd=xxxx`
**一起带进去了**。凡是**链接里自带提取码**的候选,每轮都死在验码这步;而分享页本身是活的
⇒ `_share_page_gone` 正确地判 False ⇒ **永远判不了终态** ⇒ 每天重试、每天同样失败。

生产库里那 35 条 `failed` 全属这一类(`origin_url` 100% 带 `?pwd=`)。

修法:新增 `baidupan_transfer.surl_of()`,一律只取路径段。修完复测同一条链:
验码通过、文件列表读得出,一直走到 `/share/transfer` 才被 `errno=-32` 挡下
(**证明链是好的,只是盘没空间** —— 见 §三)。

## 三、百度盘:超额 43 倍,这才是 40 条的真正落点

2026-10-25 实测(唯一那个百度号 `百度2`,`/api/quota`):

```
total = 128_849_018_880   (≈120 GiB)
used  = 5_573_035_305_813 (≈5.07 TiB)
ratio ≈ 43.2              ← 超额,不是"用了 43%"
```

⇒ `errno=-32 剩余空间不足` 是**真的**,重试一万次也不会变。两条出路:

1. **清理百度盘**(删掉历史转存;注意:删掉我们自己的落点目录会让我们发出去的链失效);
2. **换/加一个还有空间的百度号**(「Cookie 管理」里加一个)。

⚠️ 代码侧已改为**先探配额再决定要不要逐条转存**:配额已超额时,当轮**一条都不去撞**,
直接把这批标成 `pending` 并写明 `百度盘空间不足(已用 5.07 TB / 配额 120.00 GB,超额 43 倍)`。
清理出空间后下一轮**自动继续**,不需要人工重新排队。

## 四、告警文案的纪律

`_alert_backlog` 的动作必须**按证据给**,三种构成给三件不同的事。
2026-10-25 修掉的那次是:积压全是 `errno=-32` 时,它落到最后的
「**这些是链本身的问题**」那一支 —— **让人去查链,而链一条都没坏**。
「给错动作比不给动作更坏」:照着做完没用,下次就没人看告警了。

## 六、★ 2026-11-13:两类"机制上搬不动"的积压,一次性释放

### 6.1 百度:224 条(`pending` 100% 是它)

复查时 `discovered_pan_links` 的 pending **共 224 条**,`message` **全部**是同一句:

```
百度盘空间不足(已用 5.03 TB / 配额 120.00 GB,超额 43 倍)—— 本轮**未尝试**转存
```

来源:tieba 164 + weibo 60,`origin_url` **100% 是 `pan.baidu.com`**。

⚠️ **原来那句「清理百度盘或换一个号后会自动重试」现在做不到** —— 现场探活
(`/api/quota` 的 `errno`)结果:

| 账号 | `cookie_key` | 探活 | `last_ratio` |
|---|---|---|---|
| 百度2 | `baidupan` | **活**(`errno=0`) | 43.08(超额) |
| 百度3 | `baidupan#2` | **死**(`errno=-6`) | 0.0025 |
| 百度4 | `baidupan#3` | **死**(`errno=-6`) | 0.0 |

`cookies_for` 会把这两枚死号滤掉(2026-10-31 那条修复),于是**池里只剩那个超额的主号**
⇒ 这 224 条在**可预见的将来一条都搬不成**,却每轮排在 `backlog` 最前面、
占着 `pan_discovery_transfer_limit`(10)的名额,把真正能搬的存量挤在后面。

⇒ 处置:**标 `skipped`**,`message` 里写明**恢复动作**
(`重新扫码登录 baidupan#2/#3 或清理主号后,把 status 改回 pending 即可重搬`)。

**这不是判它们"链坏了"** —— 链是好的,是盘的问题。所以原因里必须写恢复动作,
而不是含糊的"放弃了"(「给错动作比不给动作更坏」,见 §四)。

### 6.2 迅雷群:39 条「单个资源比剩余空间大」

判据 = `message LIKE '%单个资源比剩余空间大%'`(由 `xunlei_transfer.space_insufficient`
判出,与「盘满」**刻意分开**,见 `xunlei_group.py:624` 的注释)。

实测这 39 条要 **0.68 ~ 12.77 TiB**,而四个迅雷号加起来总空间约 **2.0 TiB**:

| 账号 | 已用 / 配额 | 使用率 |
|---|---|---|
| `xunlei` | 16.04 TiB / 10 GiB | **164210%** |
| `xunlei#2` | 0.12 TiB / 10 GiB | 1235% |
| `xunlei#3` | 0.67 TiB / 1.01 TiB | 66% |
| `xunlei#4` | 0.42 TiB / 1.01 TiB | 42% |

⇒ **这些包本身就比整个盘大**,换哪个号都装不下。而代码里那条「保持 pending」是
**刻意的**(清出空间后确实能搬)—— 所以这次改的是**存量数据的一次性处置**,
**判据不动**:以后新进来的超大包仍然保持 `pending`(换更大的号时还有救)。

### 6.3 落地

| 位置 | 作用 |
|---|---|
| `scripts/release_untransferable.py` | 两族一起处置;默认只报告,`--apply` 才改,`--only baidu\|xunlei` 可分开跑 |
| 恢复动作 | 写在 `message` 里 —— 三个月后看到 `skipped` 的人必须知道**怎么让它回来** |

执行结果(2026-11-13 16:5x):

```
百度盘满积压: 命中 224 条 → 已标 skipped
迅雷超大包:   命中 39 条 → 已标 skipped
剩余 pending: discovered_pan_links = 0 / xunlei_group_shares = 30
```

⚠️ 剩下的 30 条迅雷 pending 全是 **11-03** 的(`message` 全空 = 从没被挑中过),
已超出 `xunlei_group_transfer_max_age_days`(7 天)的新鲜窗口,**不会再被挑中**,
会在 11-17 由既有的「过期分诊」自动转 `skipped`(`xunlei_group.py:468`),不需要额外处置。

### 6.4 顺带:`AccountRef` 不可哈希 ⇒ 百度池 ≥2 个号就抛 `TypeError`

`cookies_for` 里过滤百度死号那句原来写成 `r not in {a[0] for a in alive}`,
而 `AccountRef` 是 **dataclass(带 list 字段)⇒ 不可哈希**。生产池里恰好有 3 个百度号
⇒ **每次取号都 `TypeError`**,又被调用方的 `except` 吞成"没凭据"。

**守卫为什么没抓到**:`tests/test_pan_accounts_alive.py` 原来用一个普通类 `_R`
(按 identity 可哈希)当替身 —— **替身与真类型不是一回事**。
现补 `test_真AccountRef也要能滤死号`,用真的 `AccountRef` 跑。

## 七、★★ 2026-11-23:盘满时**跳过转存、直接推源链**(用户口径「内存不足时不转存直接推送」)

### 7.1 为什么改

11-13 那次一次性释放之后,积压又从 0 爬回 **327**(11-19 起**连续 5 天转存 = 0**):

| 平台 | 条数 | 原因 |
|---|---|---|
| 百度 | 243 | 唯一活着的号仍超额 43 倍 |
| 夸克 | 51 | 夸克1 100.0% / 夸克2 163.8%,池里**两个号都满** |
| 迅雷 | 32 | `空间不足:这个包需要 X` |

这些链**本身都是好的** —— 客户点开就能拿到那份资源。它们被扣住的原因不是内容,
而是我们这边一句内部前提:**「必须转存成我方链才推」**。盘满时这个前提**物理上做不到**,
于是几百条可用资源静静躺在待办队列里,客户一条都收不到,而系统一路 `success`。

### 7.2 现在的行为

`transfer_pan_url` 返回的失败**被判定为盘空间问题**时(`_is_space_blocked`:认
`空间不足` / `容量不足` / `file_space_not_enough` / `space_insufficient`):

1. **跳过转存**,把**源链**直接放进这一轮的推送 items(卡片照推);
2. 库里**仍记 `pending`**,`message` 以 `**未转存,已按源链推送**` 开头
   —— 空间出来后下一轮**照常补搬**(不是终态,链不会被丢);
3. **提取码当场补**:源链是别人的分享,很多带密码 ⇒ 用
   `baidupan_transfer.extract_pwd`(先认 URL 的 `?pwd=`,再认正文「提取码:xxxx」)。
   **取不到就空着**,卡面上不显示 🔑 —— 客户需回原帖找码,这是**已知降级**,不伪装;
4. 每轮上限 `PAN_DISCOVERY_SOURCE_PUSH_LIMIT`(**默认 20**,`0` = 关掉这条路)。
   超出的照旧留 pending —— 积压三百多条一次全推 = 给客户群刷屏。
   ⚠️ 这一档 **`our_url` 保持为空**:那一列的定义是「**我方**分享链」,下游
   `ai_calibration`(`our_url != ''` = 搬成)和 `chain_delivery`(`moved`)都读它 ——
   塞源链进去等于把「没搬」记成「搬了」。
5. ★★ **窗口内已经直推过的不再占名额**(`_recent_source_pushed` 查推送台账,
   窗口 = `PUSH_PAN_DEDUPE_HOURS`,默认 72h)。这不是优化,是**上线当天用真实积压
   跑出来的必答题**:直推出去的行**仍然是 `pending`**(要补搬)⇒ 下一轮它们还在队首、
   仍被判盘满、**又吃满名额** —— 不查的话每轮推的都是同样那 20 条(推送侧的 24h 去重
   又会把它们从卡上挡掉,于是**卡片是空的**),后面三百多条**永远轮不到**。
   这与本仓「排序 + 截断把某一类源整批埋掉」是同一个病。
   被跳过的行**不改消息、不擦提取码**(转存照样试过 —— 空间一放出来就走正常搬运)。
6. ★ **直推额度拆积压 / 新发现两份**(`PAN_DISCOVERY_SOURCE_PUSH_FRESH`,默认 5;
   `min()` 把它压到**不超过总额的一半**,防止总额调小时积压被饿死)。
   理由与 2026-10-05 拆转存额度**完全同源**:积压 327 条排在最前,单额度下当天新搜到的
   资源要 **17 天**才轮得到,而新资源恰恰最有时效性(用户口径「在新在精」)。

### 7.3 卡面口径(不能撒谎)

含源链行时,卡片头**不再说**「已转存成我方分享链」,而是按混合比例写清楚
「N 条已转存 / M 条因网盘空间不足未转存」;表头那一列从「我方分享链」换成中性的
**「可用链」**,并且**逐行**在链后标 `(源链,未转存)`,客户能一眼分出哪条是我们的。

### 7.4 哪些失败**不会**走这条路

判据必须窄。以下仍然是 `failed` / `skipped`,**绝不**当"盘满"推出去
(那些链客户同样打不开,推出去就是内容事故):

- `分享地址已失效` / `41011` / `PASS_CODE_EMPTY` / `SENSITIVE_RESOURCE`(死链族)
- `提取码验证失败` / 验码不通过
- `未配夸克 Cookie` / 登录态失效(是凭据问题,不是空间)

### 7.5 怎么确认它在工作

`runs.detail` 现在会多出一段 `**盘满直推源链N**`(以及 `(本窗口已推M)`):

```
候选44 转存3 (复用1) **积压320** **盘满直推源链18** (本窗口已推120) 卡片已推
```

⚠️ 这一档**不花转存额度**(根本没转存),也不计入 `转存N` —— 与 `复用` 一样单独报。
看到「转存 0」但「盘满直推源链 20」,说明系统在正常工作(盘仍是满的),
该去处置的是**盘容量**,不是链。
看到「盘满直推源链 0」但「本窗口已推 120」,说明**这一窗口已经推过一批**、
还没到重推时间 —— 也不是坏了(没有这一项的话,这两个 0 长得一模一样)。

### 7.6 上线前用真实积压验过什么(2026-11-23)

拿生产库快照连跑三轮(不联网、转存固定返回「百度盘空间不足」):

| 轮次 | 直推 | 已推跳过 | 卡片 | 跨轮重复 | 含新发现 |
|---|---|---|---|---|---|
| 1 | 15 | 0 | 15 | 0 | — |
| 2 | 16 | 15 | 16 | **0** | **是** |
| 3 | 15 | 31 | 15 | **0** | — |

- 三轮累计推出 **46 个不同源链**,`our_url` 全空、`status` 全 `pending`;
- 补到提取码 **15/15**(这一批 URL 里没有 `?pwd=`,全是从标题认出来的);
- 「已推跳过」逐轮递增而「跨轮重复」恒 0 —— 轮转成立、**没有霸占名额**。

## 八、★★ 2026-11-24:百度转存**按配置停用**(`PAN_TRANSFER_BAIDU`)

用户拍板:「**暂时先放弃百度转存,等有空间了再加回来**」。

### 8.1 为什么是配置,不是改代码删分支

那个百度号 `used ≈ 5.02 TB / total 120 GB`(**超额 43 倍**),近 3 天积压里
**97 条**候选的失败原因全是「百度盘空间不足」。但它**只是一时没有空间** ——
加一个号、清一次盘就恢复。把代码删掉再改回来是最贵的那种修法;
`PAN_TRANSFER_BAIDU=false` 是**一个开关**,恢复时改回 `true` 即可,**池里的号没被动过**。

### 8.2 停用后的行为

| 那条链 | 停用后的行为 |
|---|---|
| 网盘发现 `pan_discovery._transfer_pan_url_raw` | **不构造 `BaiduPanClient`**(连凭据都不读)、**不打配额探针**;直接返回 `status=pending`,消息写「百度转存已按配置停用(`PAN_TRANSFER_BAIDU=false`;该号空间不足)…」 |
| 公众号监听 `wechat/_enrich` 的百度块 | **整块跳过**(它不走统一入口,自己 new 了客户端 ⇒ 必须在那一块也挡一道) |

**客户侧不变**:那条消息里含「空间不足」⇒ 上游 `_is_space_blocked` 命中 ⇒
走上面 §七 的**直推源链**分支 —— 客户照样拿到这条链,只是不是我们转存的。
**库里状态仍是 `pending`**:开关改回来、空间出来后会自动补搬。

### 8.3 与「盘满」的措辞必须分开

这两件事**出口相同、原因不同**:

- 盘满 = **试了才知道搬不动**(探针/转存接口告诉我们);
- 按配置停用 = **按配置根本不试**(连请求都没发)。

消息措辞分开是有意为之:运维看到「按配置停用」就去改旋钮,看到「空间不足」
才去清盘。混成一句会让人去查一个**根本没满的盘**(或反过来,去改一个不用改的配置)。

### 8.4 恢复

```sh
# .env
PAN_TRANSFER_BAIDU=true
```
重启服务即生效(settings 在进程启动时读)。⚠️ 恢复前先确认那个号真有空间:
`python -c "from app.services.baidupan_transfer import BaiduPanClient; ...quota_usage()"`。
