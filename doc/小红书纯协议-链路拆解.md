# 小红书纯协议:链路拆解与自修指南

> 2026-10-07。**目的**:这份文档不是"我们用了 xhshow"就算完 —— 而是**把链路拆到能自己修**。
> `xhshow` 在 PyPI 上**没有声明许可证**(`license: None`,默认"保留所有权利"),
> 所以它哪天停更、或者我们**不能**继续依赖它时,要能自己接上。
> ⚠️ 下面标 **【已读源码】** 的是我实际读过实现确认的;标 **【推断】** 的需要动手验一次。

---

## 1. 链路长什么样

```
浏览器档案(data/xhs_2)
   │  ① 一次性:Playwright ctx.cookies() 解密读出 cookie
   ▼
加密 cookie 库(或 .env)
   │
   │  ② 每次请求:算签名
   ▼
xhshow  →  x-s / x-s-common / x-t / x-b3-traceid / x-xray-traceid
   │
   │  ③ ⚠️ 必须**自己把 Cookie 头加上**(见 §4 的坑①)
   ▼
POST https://edith.xiaohongshu.com/api/sns/web/v1/search/notes
   body: {"keyword":…, "page":1, "page_size":20, "search_id":…, "sort":"general", …}
```

**"纯协议"的范围**:采集全程不开浏览器。但 **cookie 仍需浏览器取一次**
—— 手抄那份实测**丢了 `id_token`**,站点直接不认。

## 2. 两个签名头,算法不同

### `x-s`(**已读源码**)
```
content_string = uri + json(payload)              # POST;GET 则是 uri?k=v&k=v(逗号不转义)
d_value        = _generate_d_value(content_string) # 某种 hash
m_value        = d_value(POST)                    # GET 时 = md5(uri)
payload_array  = build_payload_array(d_value, m_value, a1, xsec_appid, content_string, ts)
xor_result     = xor_transform_array(payload_array)      # ← 用 HEX_KEY(144 字节)整段异或
x3             = "mns0301_" + x3_base64(xor_result[:144])
x_s            = "XYS_" + custom_base64(json({"x3": x3, …}))
```

### `x-s-common`(**已读源码**,49 行,最好懂)
```
fingerprint = FingerprintGenerator.generate(cookies, UA)   # ← "埋点"就在这
b1          = generate_b1(fingerprint)
x9          = crc32_js_int(b1)                             # JS 风格 CRC32
x_s_common  = custom_base64(json({**模板, "x5": a1, "x8": b1, "x9": x9}))
```
**`x5` 就是 `a1`** —— 所以 `a1` 换了,这个头必须重算。

### 第二种格式 `XYW_`(**已读源码的注释**)
有些**取数接口**(`user_posted` 等)用 `XYS_` 会回 **HTTP 406**,要改用 `XYW_`
(AES-128-CBC,独立一条加密路径)。上游 issue 里那些"修了 461 又冒出 406"就是这个。

## 3. 关键常量在哪、改什么(**已读源码**)

| 东西 | 位置 | 说明 |
|---|---|---|
| 自定义 base64 字母表 ×3 | `config/config.py` | `CUSTOM_BASE64_ALPHABET`(x-s 用)、`X3_BASE64_ALPHABET`(x3 用)、标准表 |
| **144 字节 XOR key** | `HEX_KEY` | x-s 的 payload 整段异或用它 |
| 模板前缀 | `XYS_PREFIX="XYS_"`、`XYW_PREFIX="XYW_"`、`X3_PREFIX="mns0301_"` | **平台升版时先看这几个** |
| 版本号 | `SIGNATURE_DATA_TEMPLATE` 的 `x0="4.3.5"`、`x1="xhs-pc-web"`、`x2="Windows"` | 会随 web 端版本走 |
| **签名模板版本号(我们钉的)** | `app/services/xhs_protocol_source.py` 的 `SIGN_TEMPLATE`(可被 `.env` 的 `xhs_sign_template` 覆盖) | ★ 库自带的 `x0` **过时**(见 §4 ④)⇒ 我们从 `_signer()` 统一打补丁,**别裸构造 `Xhshow()`** |
| 指纹数据 | `data/fingerprint_data.py` | 各字段的取值范围/默认值 |
| DES key | `DES_KEY="zbp30y86"` | 只用于 gid 加密(`shield/webprofile` 接口) |

**小红书改算法时,最可能是改**:`HEX_KEY`、字母表、`X3_PREFIX`/`XYS_PREFIX` 这类**前缀与常量**
—— 而不是重写整个算法。所以**先比对这些常量**。

## 4. 实测踩到的三个坑(都真踩过)

**① 签名对了,但你没带 `Cookie` 头 ⇒ `code:-101 无登录信息`**
`xhshow` 只拿 cookie 去**算签名**,它返回的头里**没有 `Cookie`**。必须自己加。
⚠️ 这个坑很有欺骗性:HTTP 200、签名被接受、**没有 461**,看起来完全正常。

**② 手抄的 cookie 不认**。手抄那份**丢了 `id_token`**(以及 `x-rednote-*`);
从浏览器档案 `ctx.cookies()` 解密读出来的是**全套**,才通。

**③ "未登录" 与 "真的没搜到" 必须分开**。搜索页会写「登录后查看搜索结果」、
被踢会写「电脑设备登录超限,请重新登录」—— 这些**都不是"没热度"**。
(判据见 `app/services/xhs_page_source.py` 的 `NEED_LOGIN`,以及
`app/services/xhs_protocol_source.py` 的 `needs_login()`。)

**④ 库自带的签名模板版本号是过时的 ⇒ `461 + code 300011「检测到账号异常」`**
`Cloxl/xhshow` 出厂是 `x0=4.3.5` / `x4=object`,而 2026 年线上是 `x0=4.4.3`。
**控制变量实测**(同一 cookie、同一时刻,只改这一处):

| | 结果 |
|---|---|
| 库自带模板 | `HTTP 461 + code 300011 当前账号存在异常` |
| 换成 `4.4.3` / `x4=空` | **`HTTP 200`** + `code -100 登录已过期`(签名这关过了) |

⚠️ 这条的教训比结论重要:**`300011` 那行字(「当前账号存在异常」)会把人(把我)引向
"换号/过验证"**,而真因在签名里。两处独立来源都指向 `4.4.3`(`xhshow` issue #110、
以及公开实现的 HAR 实测:线上 `x-s-common.x1` = `4.4.3`,且 `4.4.1`/`4.4.3` 服务端都收)。
⚠️ **未决项**:我当初把 `x0` 与 `x4` **一起**改了,**没做隔离** —— 所以"`x4` 到底该是空还是 `object`"
至今没有单变量实测(那张公开文档说 `x4` 是 **body 类型**,搜索请求是对象,本该是 `object`)。

## 5. 出问题时的排查顺序(照这个走,别乱试)

1. **看返回码**:
   - `code:-101 无登录信息` ⇒ 90% 是 **cookie 没了/没带上**(先查 `Cookie` 头和 cookie 是否过期)
   - **HTTP 461** ⇒ 签名或指纹不对(见下)
   - **HTTP 406** ⇒ 这个接口要 `XYW_` 格式,不是 `XYS_`
   - `code:300011 检测到账号异常` ⇒ ⚠️ **先想签名模板版本号**(§4 ④ 实测它就能招来这句),
     再谈账号级风控。**别一看到"账号异常"就换号/重登** —— 那正是把我带偏了几天的那句话。
2. **对照签名常量**:把 `config/config.py` 里的字母表/`HEX_KEY`/前缀与**网页版的 JS** 比
   —— 网页端 JS 里能搜到这些表。
3. **单独验签名**:把同一份 `uri+payload+cookie` 用库算一遍、再用**页面内 `window._webmsxyw`**
   (小红书网页自己的签名函数)算一遍,对比前缀与长度。
4. **换 `XYW_`** 试一次(406 时)。

## 7. 协议**扫码登录**(2026-10-11 新增,`app/services/xhs_login.py`)

### 为什么它比"浏览器档案导 cookie"重要
我们卡住的从来不是采集,是**登录**:纯协议那枚 cookie 活不过几分钟,而兜底是
「人开浏览器档案重登 + 再导一次 cookie」。扫码登录把它换成**扫一次码**,而且**全程不开浏览器**
(签名还是 `xhshow` 在 Python 里算)—— 所以远程机也能重登。

### 三步 + 接口

| 步 | 接口 | 方法 | 说明 |
|---|---|---|---|
| ① | `/api/sns/web/v1/login/qrcode/create` | POST | body `{"qr_type":1}` → `data:{qr_id, code, url}`;**`url` 本地生成二维码**(别发给第三方渲染) |
| ② | `/api/sns/web/v1/login/qrcode/status` | **GET** | 带 query(`qr_id`/`code`/`client_public_key_base64`)——**注册 X25519 公钥,也是 `login_info` 唯一的下发通道**;每轮都要打 |
| ② | `/api/qrcode/userinfo` | POST | body `{"qrId":…,"code":…}` → `codeStatus`(**过期以它为准**) |
| ③ | `/api/sns/web/v2/user/me` | GET | **登录成功的唯一判据**:`guest === false` |

`codeStatus`:`0` 等待扫码 · `1` 已扫待 APP 确认 · `2` 已确认(**唯一成功信号**) · `3` 已过期。
二维码寿命实测 **~6.9 分钟**(不是 60 秒 —— 按 60 秒自动刷新会把还能用的码刷掉)。

### 四个坑(照做,别自己发明)
1. **凭据在 `qrcode/status` 的 `login_info`,不在 `activate`**。`activate` 即使**没人扫码**
   也回 `code:0` + 一个 session,但那是**游客档**(`guest=true`;真登录态 session 前缀 `04…`,游客 `03…`)。
   丢掉 `login_info` 去调 `activate` = 把真凭据扔了换游客档,**表现为静默失效**。
2. **成功只能以 `user/me` 的 `guest === false` 判定**。`userId` 任何阶段都返回(未登录时是游客 id)、
   外层 `code` 只表示"接口调用成功" —— 都不能当判据。而且要把「**确定未登录**」与「**检测失败**」
   分开:自查请求自己报错(406/网络)**不等于**未登录(否则人会一直重扫)。
3. **带登录 session 的无头浏览器再去导航 = 自杀**。实测:注入真 `web_session` 后**纯 API** 一切正常,
   一旦无头页面 `goto` 小红书,**服务端会下发删除指令把 `web_session` 作废**。
   ⇒ 别拿这里登到的 session 去页面路"刷新一遍完整 cookie"。
4. **`status` 那条 GET 的 query 必须参与签名**(`x5` 拿它算),且**每轮都要调**。

⚠️ **`HTTP 471` 不是失败**(本机实测):连续创建二维码后立刻轮询撞到过,而响应体仍是
`{"code":0,"success":true,"msg":"成功","data":{}}` ⇒ 它是"服务端忙/限频",代码里单列成 `kind=busy`,
**下一轮接着试**即可;别把它当成"这条链坏了"。

### 用法
```
python tools/xhs_qr_login.py            # 二维码印在终端里(也存 data/xhs_qr.png 并自动弹开)
python tools/xhs_qr_login.py 2          # 登到用户 2
```
只用**全新 `a1`**(新设备;`a1` 是设备标识不是账号)+ 库的 `build_json_body()` 序列化
(**签名用的字节 = 发出去的字节**,自己再 `json.dumps` 一遍就是 406)。

### 证据边界(别夸大)
本模块**落地的机器验证到第 ②**:`create` 200/`code=0`、`status`+`userinfo` 两条通道
在**不扫码**时稳定回 `code_status=0` 且无错 —— 这正好是公开实现说的"**只有状态 0 能靠纯协议自证**"。
第 ③ 的 `guest:false` 与 `0→1→2` 状态机**必须真人扫码**才能验(上游那份是真人实测过的)。

### ⚠️ 2026-10-11 真人实测:状态机走到了 `2`,但**凭据没拿到**

真人扫码 5 次,结论**稳定可复现**:

| 观测 | 结果 |
|---|---|
| `code_status` | `0 → 1 → 2` **全程走通**(`userinfo` 回的) |
| `userinfo` 完整响应 | 200,**`codeStatus:2`**、还带真实 `userId`(`661685be…`) |
| `status` | 扫码之后**稳定** `HTTP 471` + `{"code":0,"success":true,"msg":"成功","data":{}}` |
| 手机 App | 提示「**成功登入**」 |

⚠️ **`471` 是"嘴上说成功、手里什么都不给"**(信封 `code:0/success:true`,但 `data` 是空的),
**不是**普通报错 —— 判据代码因此加了信封校验(HTTP 200 也可能是拒绝,**不能只看状态码**)。

**为定位它做过的对照(同一张票、同一时刻、只变一个变量)** —— 全部**一模一样**,故全部划掉:

| # | 变量 | 结果 |
|---|---|---|
| ① | 基准 | 471 + 空 `data` |
| ② | 签名格式 `xyw` → `xys` | 同上 |
| ③ | 补 `Referer`/`Origin`(上游有发,我们没发) | 同上 |
| ④ | 去掉 `client_public_key_base64` | 同上 |
| ⑤ | cookie 罐 3 项 → 5 项(补上 WAF 的 `acw_tc`) | 同上 |
| ⑥ | 身份来源:库"编"的 `a1` → **站点页面 JS 造的** `a1`(11 项 cookie) | 同上 |
| ⑦ | 轮询次数(怀疑被打成限流):**不扫码**连打 16 轮 | **全 200** ⇒ 与次数无关 |
| ⑧ | 出口/IP:同一时刻 `userinfo` 正常 | ⇒ **不是**整客户端被封 |
| ⑨ | `activate`(上游说只给游客档) | 实测 session 前缀 **`030037…`= 游客**,真档是 `040069…` ⇒ 这条路是死的;但它**只在带公钥时才回 `ssk`** ⇒ 公钥确实被服务端用了 |

**⇒ 挡的不在客户端**。剩下的两种可能,以及**唯一能分辨它们的实验**:

1. **账号级**(这个号正在限制期:`-104`、会话几分钟就死、连新会话都铸不出来)—— 最可能;
2. **出口级**(我们这台机器的 IP 被盯上,只挡"带凭据的响应")。

**分辨办法(都只需再扫一次码)**:换一个**干净的号**扫同一张票(→ 成则账号级),或者
**在另一台机器/另一个出口**上跑同一套(→ 成则出口级)。⚠️ 在那之前**别再反复扫同一个号**了:
每次扫码都是一次风控输入,而我们已经从这条链上拿不到新信息了。

**这条链上真正可复用的产出**(与"能不能登进去"无关):状态机、四个坑、
`_request` 的**信封校验**(HTTP 200 也可能是拒绝)、以及对 `471` 的定性。
