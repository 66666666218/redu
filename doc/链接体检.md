# 链接体检:链打不打得开 + 有没有货不对版

> 2026-10-16 建立。用户口径:「检查一下链接资源是否都是对齐的有没有货不对版的情况,以及链接打开的情况」。

## 怎么跑

```bash
python scripts/link_audit.py                    # 每个来源抽样 20 条(默认)
python scripts/link_audit.py --n 15 --gap 0.6   # 控制抽样量与请求间隔
python scripts/link_audit.py --sources 迅雷      # 只跑某些来源
python scripts/link_audit.py --json > x.json    # 给别的工具吃
```

**只读**:只调各盘的"取分享详情"那类接口,不转存、不分享、不删除。
⚠️ 每次探活都是**一次平台请求**(夸克还要两次:token + detail)⇒ 默认抽样、默认留间隔。

## 两道判据**必须分开报**

合在一起就再也分不清"链死了"和"链配错了" —— 而这两件事**修法完全不同**:

| 判定 | 含义 | 修法 |
|---|---|---|
| **打不开** | 分享已失效/被取消/被封 | 重新搬一份 |
| **空分享** | 链**能打开**但**里面没有条目**(实测夸克 `force=1` 也是 0 条) | 同上:这份是空的,等于死链 |
| **货不对版** | 打得开,但**分享里的名字**与库里那条资源对不上 | 是**内容事故**,要核对配对(比死链更坏) |
| **待人工看** | 探活本身失败(限流/超时/没配凭据) | **不是**链的问题,别无脑重搬 |
| **对齐** | 名字对得上 | — |

⚠️ 「待人工看」那一档是**刻意留的**:把"我们被限流"报成"链死了"就是**假红**,
而假红会训练人忽略整份报告(2026-10-16 实测踩到:探针没带 captcha 重试,
30 条迅雷链**全被误报成打不开**;补上 `_with_captcha_retry` 之后 **30/30 全对齐**)。

## 对齐判据(实测校准过两次,别再简化)

**同一份资源在真实世界里会被加装饰**:emoji、分隔符、年份、繁体、括号标注。

```
库里的标题            《死刑将至》全集4K1080P高清百度网盘…
分享里的名字          S_死丨刑丨将丨至丨2026丨率丨FLAC丨20丨DDP丨HiFi

库里的标题            1000套+优质PPT模版（免费下载/可修改）
分享里的名字           2025年1000套优质PPT模板

库里的标题            乔迁之喜【邀请函】高清电子版【免费保存】
分享里的名字           乔迁邀请函
```

⇒ 判据是四条**并列**(任一成立即算对得上),而且**两边各取两种归一化**:
`match_key`(剥括号、剥盘商尾巴 —— 回库匹配的规矩)与 `_loose`(只去标点/分隔符、**保留括号内容**):

1. 归一化后**互含**;
2. **最长公共子串 ≥ 4 字**(名字被分隔符切开时还能留下连续的一段);
3. 标题的字 ≥70% 出现在分享名里;
4. 分享名的字 ≥80% 出现在标题里(治「短分享名 vs 长标题」那一类)。

⚠️ 3/4 都带**长度下限(≥4 字)**,否则 `合集`/`资源` 这种短词会乱命中。
⚠️ `_loose` 要额外**丢掉 `丨`** —— 它 `isalnum()` 为真(是 CJK 里的"字母"),
但**在资源名里就是分隔符**,不去掉的话"死刑将至"会被逐字切开、只剩 1 个字的公共子串。
⚠️ **判错的代价不对称**:把"对得上"判成"货不对版"只多一条待人工看的行;
反过来会让人**以为链是好的** ⇒ **宁严不宽**,而且**每条非对齐都把两边的名字原文带出来**给人复核
(判据是启发式的,不许装成权威)。

### 发现一:68 个不同标题**共用同一条链**(货不对版的主因)

```
盘链发现:68 个不同标题(伪装直男/亭言心事/纸鸢/逐世安/三千年等一口将军气/…)
          的 our_url **全是** https://pan.quark.cn/s/d1d3c3385b95
          而那条链的分享里只有一个目录:「中医古籍」
抖音线索:8 条(今天才拿到的)也指向它 —— 走的是「回库复用」那条路
```

**判据本身是对的**:按 `三千年等一口将军气` 去库里搜,命中的那 3 行**标题确实点名了它**
(`_title_claims` 通过)⇒ 错的是**那 3 行自己挂的链**。也就是说:
**一条错链被"回库复用"扩散到了 68 行**。

⚠️ 关键证据:这条链在库里**当 `our_url` 出现 69 次,而当 `origin_url`(从帖子里发现的)出现 0 次**
⇒ 它**不是**从任何帖子里发现的,只能是**转存/复用**环节写进去的。
⇒ 要根治得往上游看:那条链最早是哪一行、哪一步写进去的(候选:帖子里有多条盘链时取错了那条;
或口令解析给了别的分享)。**本文只到"定位到扩散机制"为止,上游原因未定案。**

## 发现四(2026-11-14):迅雷链是**按设计到期**的,到期率 100%

复跑 `python scripts/link_audit.py --n 6 --gap 0.8 --json`(30 行):

```
总计 30 {'货不对版': 9, '对齐': 7, '空分享': 1, '打不开': 13}
抖音线索  {'货不对版': 6}
公众号    {'对齐': 5, '空分享': 1}
迅雷群转存 {'打不开': 2, '对齐': 2, '货不对版': 2}
盘链发现  {'打不开': 5, '货不对版': 1}
迅雷盘同步 {'打不开': 6}
```

### 根因一:`expiration_days` 被**写死成 `"7"`**(两处)

`app/services/xunlei_transfer.py` 里 `share_files()` 与 `transfer_and_share()` 都写死了 `"7"`。
**⇒ 我们发出去的每一条迅雷链,7 天后必然失效。** 这不是"某条链坏了",是整批按设计死。

实测(同一个文件夹 `B-不二定律 85`、同一个号 `xunlei#3`,**只改这一个参数**):

```
expiration_days="7"   → expiration_at=2026-11-21T17:22:37+08:00   (7 天后)
expiration_days="-1"  → expiration_at="-1"                        (永久)
```

存量对账:

```
xunlei_resources      未过期 0     已过期 1886  合计 1886   ← 100% 过期
xunlei_group_shares   未过期 589   已过期 2578  合计 3167   ← 迅雷链部分
```

夸克那边一直是**永久**(`share_fids(..., expire_days=0)` → `expired_type=1`),两边口径根本不一致。

**修法**:新增 `SHARE_EXPIRATION_DAYS = "-1"` + `share_expiration_days(settings)`,
两处建链都走它;`settings.xunlei_share_expiration_days` 可覆盖,但**默认与回退值都是 `-1`**
(回退成正数就等于把事故口径又写回去)。

### 根因二:我们自己的清理作业在删**正被分享**的文件夹

`xunlei_cleanup` 每天按「3 天没人再提」删 36~81 个文件夹,而它**不知道那个文件夹正被
我方分享链指着**。夸克那边从 2026-10-20 就有 `KEEP_SHARED`,迅雷这边**一直缺这道边界**。

抽检源文件存在性(四个账号分别以自己身份 `GET /drive/v1/files/<id>`,取「任一账号找得到」):

```
xunlei_group_shares  带 fid 的 1865 条   随机 20 → 在盘上 0    不在 20
xunlei_resources     1886 条              随机 30 → 在盘上 10   不在 20   (全在默认号)
```

⚠️ **订正**:早先记的「12/12 全部 `file_not_found`」是**按 id 升序取最老 6 条**得到的,
抽样偏差极大 —— 按年龄分层时 **7 天内的 4/4 都还在**,30 天以上的 0/4。
**判存活率只能随机抽样**;分层抽样只能说"越老越可能没了",不能当总体比例。

**修法**:`xunlei_cleanup._shared_fids()` —— 从 `xunlei_group_shares.fid`(`our_url` 含
`pan.xunlei.com`)与 `xunlei_resources.fid`(`share_url` 含 `pan.xunlei.com`)收保护集,
`plan()` / `plan_duplicates()` 都按它排除,`run_cleanup()` 的执行清单**再排一次**
(只靠统计过滤 = 报告对了、执行器照样删)。

⚠️ 两表 `fid` 交集实测只有 **45** 条 ⇒ **必须两张都查**,只查一张会漏掉绝大多数。
⚠️ 保护集读失败 ⇒ 返回空集(退化成"不保护")但**必须记日志** —— 空集看起来和"没有分享"一样。

### 存量能不能救回来(2026-11-14 实测)

| 来源 | 可救的路 | 实测结果 |
|---|---|---|
| `xunlei_resources` | 源文件还在 ⇒ **重新 `share_files(fid)` 就行** | 随机 30 条里 **10 条还在盘上**(约 1/3,全在默认号) |
| `xunlei_group_shares` | 源文件基本没了 ⇒ 只能**回群原链重新转存** | fid 存活 **0/20**;群原链随机 15 条 **活 8 死 7** |

⇒ **只对有 `fid` 且源文件还在的那 1/3 做「重新分享」,其余靠群原链重搬(一半原链也已死)。**
不是"续期"能解决的 —— 迅雷没有给已建链改有效期的接口。

### 存量重建已执行(2026-11-16)

用户口径:「**只重建能救的那批**」。工具 `scripts/xunlei_relink.py`(dry-run 默认,
`--apply` 才真动;探活/建链全在内存,最后**一次性** `UPDATE` —— 不在循环里抱着 SQLite 写锁调外部接口)。

**全量探活 1886 条 `xunlei_resources`(带 fid + 我方迅雷链)⇒ `exists` 678 / `not_found` 1208`。**
比随机抽样估的 1/3(约 600)略高,方向一致。**fid 与转存它的号绑定** ⇒ 不同行可能属于不同的号:
`exists` 的 678 条里 **668 在默认号 `xunlei`、10 在 `xunlei#2`**。
⚠️ **不是"全部在默认号上"**(早先那句是抽样偏差):受控复核那 10 条,**只有 `xunlei#2` 说 exists、
其余三号全 `not_found`** ⇒ 少问一个号就会把"只在某号上"的源误判成已丢。
所以「默认号优先、命中即停」只省请求,**不能据此断言归属**;脚本里
`not_found` **不会 break**,会继续问遍所有号(四号全否才判 `not_found`)。

⚠️ **探活不能用 `_folder_exists`** —— 它把"认不出"一律当**存在**(那是"转存落点"场景的保守取舍),
用在这里会把"不存在"当成"能救",整套计划虚高。用自写 `_probe()` 的三态:
`exists`(200) / `not_found`(404 或 `error=file_not_found`) / `unknown`。
**只有 `exists` 建链**;`unknown` 单列一档不建链,下一轮再试。

建链走 `xt.share_files()` ⇒ 自动是**永久**(`SHARE_EXPIRATION_DAYS = "-1"`)。

**执行结果(2026-11-16 13:0x):** 建链 **677 成功 / 1 失败**。唯一失败的是
`（压码1207）伪装直男19 无雾.zip` —— 迅雷回 `share_illegal_files`(**源文件在盘上,
但不许分享**)。它同样是「链永远修不好」⇒ 也标 dead。
终态:`xunlei_resources` 活 **677** / dead **1209** / 合计 1886。
抽查 4 条重建后的链(走 `GET /drive/v1/share` 看 `share_status`):
**4/4 `status=OK`、`expiration_at=-1`、files≥1** —— 是真能打开的永久链。

**新列 `xunlei_resources.status`**:`not_found` 的行标 `"dead"` —— 它们**永远修不好**
(没有源就没有分享)。`share_url` 留着留痕,但 `resource_library` 的两个读取点
(`_xunlei_resources` / `_find_by_approx_name`)按 `status != "dead"` 跳过:
资源库若对"我们有没有这个资源"回答**一条必然打不开的链**,比回答"没有"更糟
(会让人以为已有、不再去搬)。`unknown` 的行**不标**,下一轮再试。

### 还没处理的

- **`xunlei_group_shares`** 未重建:带 fid 的 1936 条随机 20 → 源文件存活 **0/20**,
  要救只能**回群原链重新转存**(群原链随机 15 条也只剩 8 条活)。不属于 `xunlei_relink.py` 职责。
  ⚠️ **这条用受控方法复核过**(2026-11-16):从这批里随机抽 10 条,**四个账号逐个**探活
  (`xunlei` / `#2` / `#3` / `#4`,走 `_with_captcha_retry`)⇒ **40/40 全部 `not_found`**。
  所以「源文件全没了」不是「只问了默认号」得出的结论。
  ⚠️ 顺带一条方法论:第一次复核时我**没带 captcha 重试**,三个号回的是 `HTTP 400 captcha_invalid`,
  而我的脚本把它记成了 `?400`。**那既不是「存在」也不是「不存在」** —— 若当时偷懒把 `?400` 当 not_found,
  就会得出一个「看起来一样、其实是没测成」的结论(本仓最忌讳的静默失败)。
  ⚠️ **第二条方法论(2026-11-17 追记):判「源文件在不在」只认 HTTP 状态码,不许猜响应体字段。**
  11-14 有个一次性作业用 `'在' if (r or {}).get('file') else '无'` 判存活,而真实的 200 响应体是
  `{"kind": "drive#folder", "id": …, "name": "H 回乡BL44", …}` —— **根本没有 `file` 这个键**
  ⇒ `.get('file')` **恒为假** ⇒ 那 22 行「源文件=无」**一条有效信息都没有**,它连「存在」都打不出来。
  ⚠️ **同一个错误有两种症状,第二种更坏**:
  - **症状 A(响的错)**:`'在' if ….get('file') else '无'` ⇒ 一律打印「无」;
  - **症状 B(静默)**:`ok = bool(….get('file'))` + `if not ok: continue` ⇒ 5 个候选**全被 continue 掉**,
    **输出是一个 0 字节的文件**(11-14 16:36 那个作业就是这样)。空输出看起来像"还没跑完",
    比打印错值更难察觉 —— 别把「没有输出」读成「没有问题」。
  ⚠️ 那个作业还有**第二重错**:它把账号写死成 `xunlei#3`,而 `xunlei_resources` 的 fid
  **绝大多数在默认号上**(实测 668 在 `xunlei` / 10 在 `xunlei#2`;见上面「账号归属」那段)
  ⇒ 即便 `.get('file')` 写对了,用 3 号去问也只会得到 `not_found`。
  **两重错叠在一起,却表现为同一种「什么都没有」** —— 这正是为什么要一次只改一个变量。
  ⚠️ **还有第三种「空」:等待器自己**。那批作业里还有一个是 `sleep 120; cat 上面那个文件`,
  它当然也输出 0 字节 —— **等的是一个空文件**。所以看到一个空输出时,先分清它是
  「作业自己没产出」还是「它只是在等别人」;两者都长得一样,也都**不能**被读成「被测的东西没问题」。
  实测对照(同一个函数、同一天):`VP5H-btGBA…` → **200 + name**;`VP5_5krvUA` → **404 `file_not_found`**。
  ⇒ 正确判据是 `_probe()` 那种三态:**200=exists / 404 或 `error=file_not_found`=not_found / 其余=unknown**。
  这也解释了为什么那份旧输出不该拿来当证据 —— 它是 **11-14 16:24** 的产物(mtime 可查),
  比 11-16 的重建还早两天。
  ⚠️ **第三条方法论(2026-11-17 复核时踩的):`_with_captcha_retry` 只有配 `_json()` 才真的在防护。**
  它只捕 `_CaptchaExpired`,而**只有 `xt._json(resp)` 会把 `captcha_invalid` 转成那个异常** ——
  我复核时写成裸 `requests.get(...)` 再自己 `.json()`,于是这层包装**全程空转**:
  captcha 过期时它既不续期、也不报错,直接把 `400 captcha_invalid` 当结果交回来
  (现象:`GET /drive/v1/files` 200 正常,`GET /drive/v1/share?pass_code=…` 却 400「验证码无效」,
  两个号一致 —— 差点判成"链有问题")。**强制铸新 captcha 后同一发立刻 `200 status=OK file_num=1`。**
  ⇒ 凡是写 `_with_captcha_retry(_once, cred)`,**`_once()` 内部必须调用 `xt._json(r)`**。
  现有的 `_probe()`、`link_audit._check_xunlei`、`_folder_exists` 都走对了;错的是临时脚本。
  ⚠️ **同一个 `_with_captcha_retry` 还有第二个必填项:第二个参数 `cred` 不能漏。**
  它决定"续期时铸**哪个号**的 captcha" —— 漏了就退回默认号,于是**用 2 号的凭据列目录、
  captcha 过期时铸的是 1 号的**,续期白做、症状只是「列目录失败」。
  **2026-11-17 发现真 bug**:`xunlei_transfer.list_all_files` 第 1075 行写的是
  `_with_captcha_retry(_once)`(没有 `cred`),而它的调用方 `find_folder` / `xunlei_cleanup.plan`

### ★ 2026-11-17 补:共用坏链与「重复推送」是**同一根因的两个面**

上面这三条共用坏链,在推送台账上长得一模一样 —— 近 7 天带盘推送 1979 行只涉及
**378 个不同盘链**(**81% 的行是重复**),被推得最多的正是这三条:

| 盘链 | 近 7 天推送行数 |
|---|---|
| `.../4d00f5bdd943` | 55 |
| `.../1e4c093cb2cd` | 50 |
| `.../d1d3c3385b95` | 35 |

**机理**:`drop_recent()` 长期只按 `item_key`(内容的身份)去重,而客户拿到手的是
**那份资源**(盘链)。一篇文章换个标题就是新 `item_key`,同一个盘链于是被不同号、
不同文章各推一遍;最极端的一条被 **7 个板块各推一遍**。
⇒ 这不只是「群消息刷屏」,它还**把一条坏链放大了 193 倍**:链死一次,193 个标题各自
把它重新推给客户。修 `push_ledger.pan_key` 那层去重,两个面一起收窄。
