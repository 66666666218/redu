# 链接体检:链打不打得开 + 有没有货不对版

> 2026-10-16 建立。用户口径:「检查一下链接资源是否都是对齐的有没有货不对版的情况,以及链接打开的情况」。

## 怎么跑

```bash
python scripts/link_audit.py                    # 每个来源抽样 20 条(默认)
python scripts/link_audit.py --n 15 --gap 0.6   # 控制抽样量与请求间隔
python scripts/link_audit.py --sources 迅雷      # 只跑某些来源
python scripts/link_audit.py --json > x.json    # 给别的工具吃
```

**只读**:只调各盘的"取分享详情"那类接口,不转存、不分享、不删除。
⚠️ 每次探活都是**一次平台请求**(夸克还要两次:token + detail)⇒ 默认抽样、默认留间隔。

## 两道判据**必须分开报**

合在一起就再也分不清"链死了"和"链配错了" —— 而这两件事**修法完全不同**:

| 判定 | 含义 | 修法 |
|---|---|---|
| **打不开** | 分享已失效/被取消/被封 | 重新搬一份 |
| **空分享** | 链**能打开**但**里面没有条目**(实测夸克 `force=1` 也是 0 条) | 同上:这份是空的,等于死链 |
| **货不对版** | 打得开,但**分享里的名字**与库里那条资源对不上 | 是**内容事故**,要核对配对(比死链更坏) |
| **待人工看** | 探活本身失败(限流/超时/没配凭据) | **不是**链的问题,别无脑重搬 |
| **对齐** | 名字对得上 | — |

⚠️ 「待人工看」那一档是**刻意留的**:把"我们被限流"报成"链死了"就是**假红**,
而假红会训练人忽略整份报告(2026-10-16 实测踩到:探针没带 captcha 重试,
30 条迅雷链**全被误报成打不开**;补上 `_with_captcha_retry` 之后 **30/30 全对齐**)。

## 对齐判据(实测校准过两次,别再简化)

**同一份资源在真实世界里会被加装饰**:emoji、分隔符、年份、繁体、括号标注。

```
库里的标题            《死刑将至》全集4K1080P高清百度网盘…
分享里的名字          S_死丨刑丨将丨至丨2026丨率丨FLAC丨20丨DDP丨HiFi

库里的标题            1000套+优质PPT模版（免费下载/可修改）
分享里的名字           2025年1000套优质PPT模板

库里的标题            乔迁之喜【邀请函】高清电子版【免费保存】
分享里的名字           乔迁邀请函
```

⇒ 判据是四条**并列**(任一成立即算对得上),而且**两边各取两种归一化**:
`match_key`(剥括号、剥盘商尾巴 —— 回库匹配的规矩)与 `_loose`(只去标点/分隔符、**保留括号内容**):

1. 归一化后**互含**;
2. **最长公共子串 ≥ 4 字**(名字被分隔符切开时还能留下连续的一段);
3. 标题的字 ≥70% 出现在分享名里;
4. 分享名的字 ≥80% 出现在标题里(治「短分享名 vs 长标题」那一类)。

⚠️ 3/4 都带**长度下限(≥4 字)**,否则 `合集`/`资源` 这种短词会乱命中。
⚠️ `_loose` 要额外**丢掉 `丨`** —— 它 `isalnum()` 为真(是 CJK 里的"字母"),
但**在资源名里就是分隔符**,不去掉的话"死刑将至"会被逐字切开、只剩 1 个字的公共子串。
⚠️ **判错的代价不对称**:把"对得上"判成"货不对版"只多一条待人工看的行;
反过来会让人**以为链是好的** ⇒ **宁严不宽**,而且**每条非对齐都把两边的名字原文带出来**给人复核
(判据是启发式的,不许装成权威)。

## 2026-10-16 首轮实测(75 条样本)

```
对齐 51 | 货不对版 14 | 空分享 10 | 打不开 0

抖音线索     对齐 3  / 货不对版 11 / 空分享 1     ← 最严重
公众号       对齐 11 / 货不对版 2  / 空分享 2
迅雷群转存   对齐 15 / —          / —            ✅
盘链发现     对齐 7  / 货不对版 1  / 空分享 7     ← 空分享集中在这
迅雷盘同步   对齐 15 / —          / —            ✅
```

### 发现一:68 个不同标题**共用同一条链**(货不对版的主因)

```
盘链发现:68 个不同标题(伪装直男/亭言心事/纸鸢/逐世安/三千年等一口将军气/…)
          的 our_url **全是** https://pan.quark.cn/s/d1d3c3385b95
          而那条链的分享里只有一个目录:「中医古籍」
抖音线索:8 条(今天才拿到的)也指向它 —— 走的是「回库复用」那条路
```

**判据本身是对的**:按 `三千年等一口将军气` 去库里搜,命中的那 3 行**标题确实点名了它**
(`_title_claims` 通过)⇒ 错的是**那 3 行自己挂的链**。也就是说:
**一条错链被"回库复用"扩散到了 68 行**。

⚠️ 关键证据:这条链在库里**当 `our_url` 出现 69 次,而当 `origin_url`(从帖子里发现的)出现 0 次**
⇒ 它**不是**从任何帖子里发现的,只能是**转存/复用**环节写进去的。
⇒ 要根治得往上游看:那条链最早是哪一行、哪一步写进去的(候选:帖子里有多条盘链时取错了那条;
或口令解析给了别的分享)。**本文只到"定位到扩散机制"为止,上游原因未定案。**

### 发现二:「空分享」是**真的**(不是判据错)

抽到的 4 条链(对应 10 行)确实**里面什么都没有**:

```
pan.quark.cn/s/0e7a2b7d5d9e   (教资资料,7 行)      ← force=1 也是 0 条
pan.quark.cn/s/a8110359b413   (霸王茶姬杯贴)
pan.quark.cn/s/bd2013f4b95b   (霸王茶姬杯贴)
pan.quark.cn/s/5bea6da448fa   (高性价比人生指南)
```

对照组(同一次探活里):`pan.quark.cn/s/a6314db4124e` **能列出**它的文件 ⇒ 不是取列方式的问题。
⚠️ 其中 `5bea6da448fa` 曾被当成"已知可点的对照链"用在 `feishu_card_link_diag.py` 的诊断卡里 ——
它确实**打得开**(所以当时那次诊断有效),但**里面是空的**,别再拿它当"好链"的例子。

### 发现三:迅雷那两路 30/30 全对齐

包括 `xunlei_group_shares.our_url`(群转存)与 `xunlei_resources.share_url`(盘同步) —— 这两条链的产物**是干净的**。

⚠️ **但这条结论只在 2026-10-16 那天成立**(那时链都还年轻)。见下面「发现四」。

## 发现四(2026-11-14):迅雷链是**按设计到期**的,到期率 100%

复跑 `python scripts/link_audit.py --n 6 --gap 0.8 --json`(30 行):

```
总计 30 {'货不对版': 9, '对齐': 7, '空分享': 1, '打不开': 13}
抖音线索  {'货不对版': 6}
公众号    {'对齐': 5, '空分享': 1}
迅雷群转存 {'打不开': 2, '对齐': 2, '货不对版': 2}
盘链发现  {'打不开': 5, '货不对版': 1}
迅雷盘同步 {'打不开': 6}
```

### 根因一:`expiration_days` 被**写死成 `"7"`**(两处)

`app/services/xunlei_transfer.py` 里 `share_files()` 与 `transfer_and_share()` 都写死了 `"7"`。
**⇒ 我们发出去的每一条迅雷链,7 天后必然失效。** 这不是"某条链坏了",是整批按设计死。

实测(同一个文件夹 `B-不二定律 85`、同一个号 `xunlei#3`,**只改这一个参数**):

```
expiration_days="7"   → expiration_at=2026-11-21T17:22:37+08:00   (7 天后)
expiration_days="-1"  → expiration_at="-1"                        (永久)
```

存量对账:

```
xunlei_resources      未过期 0     已过期 1886  合计 1886   ← 100% 过期
xunlei_group_shares   未过期 589   已过期 2578  合计 3167   ← 迅雷链部分
```

夸克那边一直是**永久**(`share_fids(..., expire_days=0)` → `expired_type=1`),两边口径根本不一致。

**修法**:新增 `SHARE_EXPIRATION_DAYS = "-1"` + `share_expiration_days(settings)`,
两处建链都走它;`settings.xunlei_share_expiration_days` 可覆盖,但**默认与回退值都是 `-1`**
(回退成正数就等于把事故口径又写回去)。

### 根因二:我们自己的清理作业在删**正被分享**的文件夹

`xunlei_cleanup` 每天按「3 天没人再提」删 36~81 个文件夹,而它**不知道那个文件夹正被
我方分享链指着**。夸克那边从 2026-10-20 就有 `KEEP_SHARED`,迅雷这边**一直缺这道边界**。

抽检源文件存在性(四个账号分别以自己身份 `GET /drive/v1/files/<id>`,取「任一账号找得到」):

```
xunlei_group_shares  带 fid 的 1865 条   随机 20 → 在盘上 0    不在 20
xunlei_resources     1886 条              随机 30 → 在盘上 10   不在 20   (全在默认号)
```

⚠️ **订正**:早先记的「12/12 全部 `file_not_found`」是**按 id 升序取最老 6 条**得到的,
抽样偏差极大 —— 按年龄分层时 **7 天内的 4/4 都还在**,30 天以上的 0/4。
**判存活率只能随机抽样**;分层抽样只能说"越老越可能没了",不能当总体比例。

**修法**:`xunlei_cleanup._shared_fids()` —— 从 `xunlei_group_shares.fid`(`our_url` 含
`pan.xunlei.com`)与 `xunlei_resources.fid`(`share_url` 含 `pan.xunlei.com`)收保护集,
`plan()` / `plan_duplicates()` 都按它排除,`run_cleanup()` 的执行清单**再排一次**
(只靠统计过滤 = 报告对了、执行器照样删)。

⚠️ 两表 `fid` 交集实测只有 **45** 条 ⇒ **必须两张都查**,只查一张会漏掉绝大多数。
⚠️ 保护集读失败 ⇒ 返回空集(退化成"不保护")但**必须记日志** —— 空集看起来和"没有分享"一样。

### 存量能不能救回来(2026-11-14 实测)

| 来源 | 可救的路 | 实测结果 |
|---|---|---|
| `xunlei_resources` | 源文件还在 ⇒ **重新 `share_files(fid)` 就行** | 随机 30 条里 **10 条还在盘上**(约 1/3,全在默认号) |
| `xunlei_group_shares` | 源文件基本没了 ⇒ 只能**回群原链重新转存** | fid 存活 **0/20**;群原链随机 15 条 **活 8 死 7** |

⇒ **只对有 `fid` 且源文件还在的那 1/3 做「重新分享」,其余靠群原链重搬(一半原链也已死)。**
不是"续期"能解决的 —— 迅雷没有给已建链改有效期的接口。
