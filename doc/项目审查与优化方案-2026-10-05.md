## 摘要:最要紧的三件事

### 🔴 一、阅读数已断一周,而全线监控显示绿/黄

这是**本次审查最重要的发现**,也是你反复强调的第一需求("我们主要就是需要获取到阅读数")。

**实测事实链**:

| 证据 | 值 |
|---|---|
| 最近一条有 `read_num` 的文章 | **2026-09-28 08:00**(库里共 168 条) |
| 近 3 天新入库文章 / 其中有阅读数 | **162 篇 / 0 篇** |
| `data/app.log` 里 `mp/articles 不可用(...-2041)` | **14 次**,从 **09-29 21:30** 到今天 **14:00**,几乎每轮监听 |
| 同轮 `shelf(signals=142)` | **成功** ⇒ **凭证是活的,是列表接口被拒** |
| 每轮 `runs.detail` | `weread_list(ok=0 off=0 off_with_new=23 skipped=10)` |

**为什么没人发现 —— 一路假绿**:

1. `mp/articles` 失败**每进程只记一次 warning**(`_weread_collect._mp_articles_warned`),
   而且是 `logger.warning` → 只进 `data/app.log`,**不推飞书**;
2. `weread_list(ok=0)` 只是 `runs.detail` 里的一个 `0`,**没有任何人/作业解析它**;
3. `chain_health` 把它判成 **🟡「多半是正常空窗」**,并把"真警报"甩给续期作业;
4. 续期作业**报 success**(13:50 确实 `set_cookie` 写成功了,它自己 `shelf()` 验过)。
   ⇒ **"真警报在续期那边"这句话是假的**:续期按它的判据是成功的。

⚠️ **代码里对 `-2041` 有三种互相矛盾的解释**,说明根因**尚未确定**:

- `_is_weread_quota_error` 的 docstring:`-2041(会话列表预算耗尽)`
- `_weread_collect` 行内注释:`-2041 是新版微信读书对该接口的永久限权`
- 同文件另一处:`刚续期的会话回 -2014『额度』,会话老化后回 -2041『不下发』`

第三种解释的推论是"**续期后立刻问就该成功**"—— 但生产正是 13:50 续期、**14:00 就被拒**,
**与事实矛盾**。⇒ 别再按任一说法定方案,先做**控制变量实验**(见"执行顺序"第 1 步)。

### 🔴 二、迅雷 refresh_token 失效复发(今天 15:30/15:40 仍在挂)

`xunlei_group`(15:40)/`xunlei_sync`(15:30)双双 `failed`:
`迅雷刷新 token 失败:{'error': 'invalid_grant', 'error_code': 4126}`。

**01:13 的修复(`615fa28` 写回轮换后的 refresh_token)没挡住复发** —— 代码里 `_save_credentials`
确实在、本机进程 13:11 也重启过。⇒ 要么修复不完整,要么存在**第二条轮换路径**
