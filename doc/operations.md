# 运维手册(FAQ)——上线第一周常见问题

> 2026-09-09 基于代码路径整理。按「症状 → 原因 → 处理」组织。

## 1. 公众号监听没有推送?

**排查顺序**:
1. 「公众号监听」页顶部状态条:在监号数是 0?
   → 还没有对标号:微信读书关注 → 书架导入,或贴文章链添加
2. 对标号有了但没推送:
   - 监听是**每天 4 个定点**(4:00 / 8:00 / 14:00 / 20:00),先看离上一个定点过了多久;
     「采集频率」页的间隔对公众号不参与调度(只影响其它板块),那里只需确认没被"停用监控"
   - 手动点「立即监听一轮」,看返回的 `new` 值
3. `status=skipped reason=no_source` → .env 缺 WEREAD_COOKIE 且缺 DAJIALA_KEY
4. `reason=low_balance` → dajiala 余额不足,充值或忽略(免费源不受影响)
5. `reason=running` → **上一轮监听还在跑**(详情页会写 `running(上一轮监听尚未结束)`),
   这一轮按设计不重复触发(防两轮并发扣费/重复发卡)。偶尔出现是正常的(手动点击撞上定点轮);
   持续出现才要查:一轮跑完必须解锁,若进程被 kill 在轮中,标记最多滞留
   `WECHAT_LISTEN_LOCK_TTL_MINUTES`(默认 20 分钟)后自动被下一轮接管
6. **"推送了但比该号实际发的少"** → 不是推送截断,是采集只看见最新一篇,按 §4e 判定与处置

## 1b. 公众号在管理后台的哪一处(2026-09-22 补齐)

工作台和运维 tab 顶部的「🩺 采集健康度」卡片:
- 平台表里 **公众号监听** 行 = 最近一轮 `wechat_listen` 的状态与 `detail`
  (`accounts=81 new=0 failed=1` 这种);`runs_24h` 最多 4(定点作业,不是每小时)
- 表下一行 = 在监对标号数 / 有在监号的用户数 / 近 24h 新收文章 / 定点时刻 / 下轮时间
- 再下一行 = **夸克转存覆盖率**(近 30 天带盘链文章):已转我方链 N/总 M、待转存、源已失效、
  配了 quark Cookie 的用户数 —— 员工点飞书标题应该进"我们自己的盘",这行就是看有没有做到
- 「最新数据写入」看 `公众号` 一项判断有没有新文章进账;「已配 Cookie」列 `weread`/`quark`
  等中文标签的用户数
- 工作台「公众号」卡片 = 全站文章数 + 在监号数
- 「数据」tab 新增 **公众号** 按钮,可翻最近文章的标题/来源/盘链类型/阅读量
- 「近 30 天告警」柱状图历史上只统计微博/闲鱼/抖音三板块,公众号与百度的告警被静默丢弃;
  现按告警实际板块统计,公众号那根柱子不再恒为 0

要看单用户的对标号明细仍在用户侧「公众号监听」页(`/wechat`),后台只做总览。

## 2. 微信读书 Cookie 过期(收到 🟠 提醒)


- 浏览器登录 weread.qq.com → F12 → Network → 刷新 → 复制任意请求的 Cookie 整行
- **确认含 `wr_skey=` 和 `wr_vid=`**(只复制 weread.qq.com 的,不是 mp.weixin.qq.com 的)
- **想"长期"必须含 `wr_rt=`**:自动续期只认它(约 30 天),缺 wr_rt 的 Cookie 十几小时就死
- 粘贴到「Cookie 管理」页 weread 平台 → 保存(不用重启);**保存即解除续期冷却**
  (`weread_renewal_cooldown_{uid}`,2026-09-22 起;旧版本需手动删该 `system_config` 行)
- 系统有自动续期(wr_rt 换新 skey),正常情况几周才需要手动更新一次
- **手工粘贴的新 Cookie 不会打「全量补采」标记**(只有 `refresh_weread_cookie` 续期成功时打,
  见 `weread_fullsync_pending_<uid>`)。所以"会话初期 `mp/articles` 可用"那个窗口默认是白过的:
  想用它,粘贴后**趁早对高产号逐个点「同步文章」**(免费,列表可用时会补回同日兄弟篇);
  要不要在粘贴保存时自动打标记属调度取舍(会立刻多打 81 次列表 = 刚建立的会话最先被自己烧干),暂未做
- **贴完先核对出口 IP**:会话与出口 IP 绑定(2026-09-27 本机实测:换网络后同把仍有效的 Cookie
  当场 `-2012 登录超时`)。若你是在自己浏览器里扫的、服务器走的是另一个出口,下一轮定点就会又报过期

## 3. 闲鱼触发人机验证(收到 🔴 提醒)

- 这是账号/IP 级风控,**退避无效**,处理顺序:
  1. 手机闲鱼 App 完成一次滑块验证
  2. 换出口 IP(住宅 IP 最有效):`.env` 配 `XIANYU_PROXY_URL=http://user:pass@ip:port`
  3. 系统已自动冷却 30 分钟,期间轮次跳过
- **不要**调高采集频率(每轮 5 词/8s 间隔是社区验证的安全区)

## 4. 夸克转存失败(推送回落原链接)

- 收到「夸克 Cookie 已失效」告警 → pan.quark.cn 重新登录复制 Cookie → 更新到「Cookie 管理」页的 **quark**(本人未配则用 .env 的 QUARK_COOKIE;改界面值不需重启)
- 收到「夸克盘链未转存(缺夸克 Cookie)」告警 → 同上,配上即可,下一轮监听自动开始转存
- 「容量不足」→ 清理网盘空间
- 转存失败不影响监听和推送,只是推送里没有你的链接

### 4a. 网盘 Cookie 的告警覆盖(2026-09-26 补齐百度)与转存支持矩阵

**会主动提醒你的三种时机**(夸克、百度现在完全对等):

| 告警标题 | 触发时机 | 处置 |
| --- | --- | --- |
| `🟠 夸克/百度网盘 Cookie 已失效,转存功能停用` | 每日 07:00 巡检探到;或监听当场转存报鉴权失败 | 重新登录复制 Cookie,更新「Cookie 管理」(quark / baidupan) |
| `百度盘链未转存(缺百度网盘 Cookie)` / 夸克同名 | 本轮识别到该盘链,但这个人一份 Cookie 都没配 | 去「Cookie 管理」配对应平台,下一轮自动生效 |
| (不提醒)对方分享已被封 | 夸克 41031,重试永远不成功,与我方 Cookie 无关 | 卡片上显示 `⛔源失效`,文章已出队不再重试 |

- 百度盘**没有全局默认值**,只能在「Cookie 管理」按用户配(含 `BDUSS`);夸克可用 .env 的 `QUARK_COOKIE` 兜底
- 百度转存失败时看到的是 `errno`(长得像"对方链接失效"),所以**本轮第一次失败后会探一次登录态定性**:
  确实死了才告警,并停掉本轮剩余百度链;没死则安静留到下轮
- 每日巡检按 Cookie 值去重(多人共用同一份凭据只探一次、只告一次),禁用用户不巡检

**转存支持矩阵**:识别四家盘链(夸克 / 百度 / UC `drive.uc.cn` / 迅雷 `pan.xunlei.com`),但**只有夸克和百度能自动转存**。
UC / 迅雷只有 `pan_types` 标签、没有我方链(卡片上是 `—`),要接需要各自的转存+分享协议与 Cookie,尚未实现。

### 4b. 飞书卡片"网盘"列的三个标记(点标题会去哪)

- `🔴夸克` = 标题链指向**我方转存链**(带提取码时附 🔑xxxx)
- `⏳待转存` = 文里有别人的夸克链但还没换成我方链 → 点标题进的是**公众号原文**;
  补转存队列每轮最多 `PAN_TRANSFER_BACKFILL_LIMIT`(默认 8)篇,配好 Cookie 后会自己追上
- `⛔源失效` = 对方分享已被封(夸克 41031),**永远转不了**,该篇已出队不再重试
  (旧版这些死链会一直霸占补转存配额,把能转的文章挤在后面 —— 2026-09-22 修)
- 已决策的开放项:转好的文章**不会**追推一条新卡(员工看到的仍是那条 ⏳ 卡),要不要补推待用户定
- `🔴` 不止出现在转存当场:标题链的优先级是"本轮转存链 > 已落库的我方链 > 原文",所以 `⏰ 补推`
  卡与重推卡上也显示我方链。此前回落**只认夸克前缀**,已转存成功的百度文(库里写作
  `https://pan.baidu.com/s/xxx (提取码 abcd) [百度]`)在非当轮卡上会退回原文,2026-09-26 修
- **补转存队列只收「带夸克链」的文章**(2026-09-26 第八轮审计修):旧版入队条件只有
  `pan_urls != ""`,于是只带百度/UC/迅雷链的历史行也被排进这 8 个名额——而队列里只有夸克转存
  会消费它们(百度走自己的门控),它们既转不动也永远不会落 `my_pan_urls`,等于**永久霸占队头**,
  把名额吃光,真正待转的夸克文再也轮不到。现在只有 UC/迅雷是"识别不转存"(见 §4a),
  送进夸克接口的非夸克链也不再产生"无法解析夸克分享链接"的假失败日志

### 4c. 「同步文章」= 入库 + 当场转存 + 推飞书(2026-09-23)

点用户侧「公众号监听」页某个号的「同步文章」,后端一次做完:拉历史入库 → **同盘链去重**(同一资源
只保留一篇,更早入库过的链不重复推、也不重复转存进盘)→ 夸克/百度转存换我方链 → 推卡片(点文章名
直接进我的夸克盘,提取码明文附后)。前端 toast 与运行记录 detail 都会写
`pushed / deduped / truncated` 三个数,不会静默少推。

- 同步**不采样**阅读量(一次入库上百篇 × ¥0.06 会打穿余额),这些文章读起来是 `—`,等每日采样作业
- 单轮窗口 `WECHAT_SYNC_PUSH_LIMIT`(默认 20 篇,资源文优先):转存是同步网络调用,不设窗口一次点击
  能把请求拖到十几分钟占死线程池;窗口外的旧文留给定点监听的补转存队列换链,但**不会再补推**。
  **近 24h 内发的文章(以及发布时间未知的刚采到的文)不受这个窗口限制**——它们先占满名额,
  剩下的名额才轮到 24h 之前的历史补采文(2026-09-26 把"近24h全推"定为硬要求)
- 同步**不叠加**补转存队列(那是监听每轮 8 篇的活儿),所以一次点击的夸克调用数 = 窗口内资源文篇数

### 4d. 卡片上「网盘」列一根 `—`,点标题进原文(2026-09-26 补齐六类缺口)

`—` 的正确含义是"**这篇我们没认出任何盘链**"。历史上它混进了几种误判,现已分别修掉:

1. **链在超链接里** —— 号主写"点此保存"并把夸克链做成锚文本,去标签时 URL 在标签里被一起删了
2. **链只在「阅读原文」里** —— 正文只写"点左下角阅读原文",真链在页面 JS 变量 `msg_source_url` 上
3. **历史行的 `pan_urls` 是空的** —— 百度链提取晚于这些文章入库,而"进补转存队列"的条件就是
   `pan_urls != ""`,于是它们**永远排不到**换链。`_backfill_pan_urls` 会自动修(每用户每轮 ≤100 篇),
   无需手工 SQL;但它一度被"`if not rows: return`"挡在早退之后 —— **一轮没采到新文就不回填**,
   本机库 27 篇因此长期不动(现在空轮也回填,只是转存仍留给有新文的轮次)
4. **标题不含盘商词** —— 旧粗筛词表只有"夸克/网盘/资源/合集…","XX入口""限时领取"类标题压根没抓正文,
   词表已补齐引流词
5. **直抓正文被风控,却没用微信读书兜底**(26%,`—` 的最大来源)—— 监听拿到的 cover/列表条目**自带
   `reviewId`**,却丢掉它去直抓 `mp.weixin.qq.com`;风控返回空正文 → 认不出链。现在**直抓为空就用本篇
   `reviewId` 走微信读书转发页 `mp_content`**(与「同步文章」同源),直抓成功则不再追打(省 2s 节流)
6. **认出了链、卡片却还是原文** —— 不是 `—` 而是"点进去不对":`my_pan_urls` 的回落解析只认夸克前缀,
   百度转存成功的行(`… (提取码 xxxx) [百度]`)在 `⏰ 补推`/重推卡上退回原文;`(自分享)` 尾巴还会
   粘进 href 让链接点不开。两处都改为按盘链正则取 URL 本体

运维视角的检查顺序:健康页那行**转存覆盖率**(近30天带链/已转/待转/源失效)→ 若"带链"数明显偏低,
看 `wechat_listen` 运行记录/日志里有没有成片"正文容器缺失(疑似风控壳页)" —— **出口 IP 被微信挡**时自抓
返回 JS 壳页,现在判失败不再入库垃圾正文,而正文会由第 5 条的微信读书转发页兜住;兜底也失败(该号
没关联 `weread_book_id`、或微信读书 Cookie 死了)才真的认不出链。此时先按 §2 修 Cookie,再考虑降监听
频率/换出口;dajiala `article_detail`(¥0.01/次)兜底仍待决策(余额风险)。

**剩下真出不了链的合法情形**(不要当缺陷排查):纯资讯文不带任何资源、资源是公众号自建小程序/网盘
搜索页而非 `pan.quark.cn`/`pan.baidu.com` 分享链、图片里的二维码。
**这类文章仍然会推**——`—` 只代表"没有网盘链",不代表员工看不见这篇发了什么(入库侧全部
`require_pan=False`,卡片 note 一行写明 `—` 的含义;2026-09-26 用户明确"找不到链接的也必须推送名称")。

### 4e. 「近 24 小时发的文章全部推到飞书」怎么判定(2026-09-26)

这是产品铁律,不是愿望:飞书是员工看新发文的唯一入口,少推一篇等于员工看不见。链路里**推送侧从来没有
截断**(监听采到的新文全推,每卡 20 篇只是分页;「同步文章」的窗口也砍不到 24h 内的文)。所以"漏推"
只可能来自**采集侧根本没看见**,而采集侧只有一个真实缺口:

- **推送范围包括没认出网盘链的文章**(2026-09-26 用户补的要求:"找不到链接的也必须推送名称")。所有
  监听/同步入库都是 `require_pan=False`,纯资讯文照样上卡,网盘列显示 `—`、标题点进去是公众号原文

- 微信读书 `mp_cover` 只返回**最新一篇**。同一天发第 2、3 篇时,前一顶后一,两轮监听之间(定点 4/8/14/20,
  最长空档 8h)那几篇就永久漏采
- 能枚举同日兄弟篇的是 `mp/articles`(近 3 天列表),但它是一个**按会话/IP 记额度**的稀缺接口,
  不是"能用/不能用"的开关:
  - 会话用了几小时后 → `-2041`(不下发)。2026-09-27 上午用一把老会话实测三种上下文
    (首页 Referer / 无 Referer / 阅读器页)× 两个号 = 六次全 `-2041`,"换调用上下文就能复活"已被否证
  - 换成**刚建立的会话** → `-2014`(有额度、此刻被限),同一天再测:连打 5 次列表后,
    **等 15 分钟仍回 `-2014`**——额度不短、且我们每轮本来就要发 ~162 次(81 号 × cover+列表)
  - 结论:免费列表能不能兑现,取决于**额度分配**而不是调用姿势。所以监听从 2026-09-27 起加了
    轮内熔断(见 §9.2 末),真正的下一步是"把有限额度轮到哪些号"这件事要有人定夺

看三处就知道本轮有没有兑现(不要把"success + new=2"当成"全推到了"):

1. `wechat_listen` 运行记录 detail 的 `weread_list(ok=A off=B off_with_new=C skipped=D)`:
   **C>0 就意味着有 C 个号"采到了新文却列不出它的同日兄弟篇"**,属未知丢失;
   `D` 是本轮被额度熔断挡下、压根没问过列表的号数。detail 里若出现 `quota_skipped=K`,
   表示有 K 个号这一轮**连 cover 都没问到**(见 §9.2 末)
2. 站内「预警」页(`/api/alerts/list`,管理端用户详情与告警导出 CSV 同源)有没有
   `⚠️ 微信读书只能拿到最新一篇,同日其它篇可能漏推`(标题固定、数字写在正文,冷却去重才有效)。
   它**不发飞书**了:这是"要不要自建 WeRSS / 要不要充值"的长期决策,不是员工群里该刷的东西,
   见 §4f
3. **有没有"卡压根没发出去"**(2026-09-26 起有事实可查):`wechat_articles.pushed_at` 只在卡片真的
   送达时盖上,所以
   `select count(*) from wechat_articles where pushed_at is null and source in ('listen','sync')
    and created_at > now() - interval 24 hour`
   非 0 = 有文章入库却欠飞书一条卡。下一轮监听开头会自动补推(卡标题 `⏰ 补推 · 公众号监听 …`),
   运行记录 detail 里带 `repushed=N`;补推仍未送达会在**站内**记
   `⚠️ 公众号文章补推仍未送达,飞书推送可能持续故障` —— 那基本是 webhook 被移出群/被关键词或
   IP 白名单拦截,不是采集问题(这种告警发飞书本来就发不出去,只落站内)

处置(按代价排序):

| 做法 | 成本 | 效果 |
|---|---|---|
| 对高产号点「同步文章」 | 免费,人工 | 列表可用时会补回同日兄弟篇;被限权时仍只有最新一篇 |
| 自建 WeRSS 并把订阅 id 回填进对标号 `biz` | 一次性运维(一台容器 + 一条脚本) | 监听每号拿最新一页全量列表,`weread_list` 不再是瓶颈,**推荐,见 §4g** |
| dajiala 充值走 `post_condition`/`history_by_ghid` | ¥0.14/号/轮 | 同上,付费稳定;当前余额已被禁,且**只对填了 `anchor_url` 的号可达**(线上 81 号全空,见 §9.2 补环待办) |

`run_full_sync_if_pending`(renewal 后的补采窗口)遇到列表 -2041 会**当轮中止并保留 pending 标记**,
不再让其余号一个个白撞;日志里"本轮补采中止"是预期行为,不是故障。
补采一天只随四定点跑四次,所以中止时把"已尝试到哪个号"记进标记值(`cursor:<对标号 id>`),
下个定点**从游标之后接着跑**,轮到队尾才清标记——否则每次都从第一个号重来,排在 -2041 之后的号
永远补不到。想核对进度:管理后台 `system_config` 里 `weread_fullsync_pending_<用户 id>` 的那个值,
时间戳=还没开跑,`cursor:N`=已补到 id N。

**"跑过"≠"答上"(2026-09-27 第 12 轮审计修)**:监听里微信读书分支以前只要没抛异常就把本号记成
"已消费",于是 cover 空响应 + 列表被限权的那种"什么都不知道"会把 ② 的付费兜底一起挡掉——恰好在
风控期的那批号两头落空,而运行记录长得像"81 个号都问过了"。现在 `used` 取 `_weread_collect` 的
第二个返回值(= 源真给出过一篇可看的文),没答上就继续往下试;这条同时不影响 `miss_count`,
"连续 N 轮未发文"仍然只在**确认当天没发文**时才 +1。

### 4f. 告警分两条腿:飞书群只放"文章 + 能当场修的",运维诊断看站内(2026-09-26)

用户口径:**飞书群是员工看文章的地方,对我而言它只该承担两件事——文章推送、Cookie 是否过期**。
"要不要自建 WeRSS""要不要充值""补推链路本身坏了"这类长期决策/自诊断刷进群就是噪音
(群里的人既看不懂也无从处置),而"飞书本身坏了"的告警发飞书更是发不出去。

所以 `notify_incident(..., push_feishu=False)` 走**站内**:`alerts` 表(`AlertRecord`,section=`incident_wechat`)
→ 用户「预警」页"最近预警"、管理端用户详情、告警导出 CSV 三处同源可见。
**冷却门照旧**(每 `FEISHU_ALERT_COOLDOWN_HOURS` 最多记一条),不会因为不发飞书就变成每轮堆一条。

| 告警 | 走哪 | 为什么 |
|---|---|---|
| 公众号新发文卡 / `⏰ 补推` 卡 | 飞书 | 铁律:员工看文的唯一入口 |
| 🟠 微信读书 Cookie 已过期 / 自动续期失败 | 飞书 | 用户当场能修(重新复制 Cookie) |
| 🟠 夸克 / 百度网盘 Cookie 已失效,转存停用 | 飞书 | 同上,去「Cookie 管理」贴新的 |
| 夸克 / 百度盘链未转存(缺 Cookie) | 飞书 | 差的是一步配置,点进去就能补 |
| 🔴 闲鱼滑块导致整轮采集失败 / 🟠 闲鱼 Cookie 已失效 | 飞书(闲鱼板块群) | 采集**已经停了**,当场能修(换 Cookie / 换出口 IP) |
| ⚠️ 闲鱼部分关键词被风控、🟠 网关 WAF 拦截、⚠️ 深采触发滑块(仅 partial) | **只进站内** | 2026-09-27 按用户口径分流:这是"掉了一部分"的降级诊断,不是停摆,轮不到员工群 |
| ⚠️ 微信读书只能拿到最新一篇,同日其它篇可能漏推 | **只进站内** | 根治是自建 WeRSS(§4g)/ dajiala 充值,属长期决策 |
| ⚠️ 公众号文章补推仍未送达,飞书推送可能持续故障 | **只进站内** | 发飞书自己就是坏的那条路;且下轮会自动继续补 |

"只进站内"不等于没人看见:登录后「预警」页就能看到(标题=触发项、正文=说明),管理端用户详情与
告警导出 CSV 读同一张表。反过来,飞书群里从此只会出现"你现在就能修"的和文章卡。

判断新告警该走哪条,问两句:① 收到的人**现在**能不能动手修?② 它是不是"只有运营者看得懂"的内部诊断?
两个都否定 → `push_feishu=False`。

### 4h. Telegram 频道资源源(2026-10-01,默认关闭)

**它是什么**:公众号之外的**第二路盘链 feed**。TG 上有一批专职发资源的公开频道,与公众号是
两个独立生态(重合度低),抓公开预览页 `t.me/s/<频道>` **不需要账号也不需要 Cookie**。

**为什么默认关**:本机(家宽)**直连 `t.me` 超时**,也没有任何本地代理端口;换 `r.jina.ai`
中转、RSSHub 公共实例试过同样不通。解析逻辑已全部单测覆盖(**不联网也能测**),
所以能不能启用只取决于网络出口,不取决于代码。

**怎么启用**(在能出网的机器上,如境外 VPS):
```
TG_ENABLED=true
TG_CHANNELS=频道名1,频道名2      # 不带 @
TG_PROXY=http://host:port        # 需要代理时填;留空则直连
TG_LIMIT=30                      # 单频道每轮取最近几条
```

**它做了什么**:抓最近 N 条消息 → **只留带盘链的**(闲聊/广告不入库,否则稀释共振榜)→
落 `wechat_articles`(`source=telegram`,频道记作 `@频道名`)与 `wechat_pan_links` →
自动进入资源库的检索/共振榜,与公众号来的盘链**同一张表、同一套聚合**。
去重键是消息永久链接(`https://t.me/<频道>/<序号>`),故每 30 分钟抓一次也不会重复入库。

**设计取舍**:转存侧**没有**借鉴 CloudSaver —— 它的开源仓停在 V0.2.5,批量/重试/去重都不如
我们现有的 `quark_transfer`/`baidupan_transfer`;我们只借了它的**页面解析骨架**
(`.tgme_widget_message_wrap` / `data-post` / `js-message_text`,且盘链挂在正文的 `<a href>` 上——
只扫纯文本会漏)。

### 4i. 公众号后台凭据(自研 Wemp)——拿到"全量文章列表"的唯一路径(2026-10-01)

**为什么需要它**:现有取数走微信读书,`cover` 兜底**每个号每轮只能拿最新 1 篇**,还老撞 `-2041`
限流(同日多篇必漏)。后台凭据走的是另一套接口(`appmsgpublish`),**单页 20 篇、可翻页**,
且配额是**账号级**的,与微信读书互不干扰。

**代码早就写好了**:`app/services/wechat/wemp_client.py`(9-30 建,协议完整、异常分类清晰、
已接入监听轮 ⓪ 分支的降级链)——**一直只缺有效凭据**。凭据存 `system_config[wemp_cred_{uid}]`,
**Fernet 加密**(与用户面 Cookie 同一把钥匙;它权限更大,没理由反而不加密)——读写统一走
`app/services/wemp_cred.py`(监听择源 / 健康页 / 录入脚本三方共用,免得改一处漏一处)。

**三步拿到凭据**:

1. 注册一个微信**订阅号**(个人可注册,`mp.weixin.qq.com` → 立即注册)
2. 浏览器登录后台,`F12` → **Network** → 刷新 → 点任意请求 → Request Headers →
   把 **Cookie** 整条复制出来(通常 1~2KB,**必须完整**)
3. **token** 就在登录后地址栏的 URL 里:`...&token=1234567890`

**录入(自带探针,当场告诉你行不行)**:
```bash
cd /d/code/redian
python scripts/wemp_cred.py --cookie "<整条Cookie>" --token "<token>"
python scripts/wemp_cred.py --check          # 以后想确认还能不能用
```

探针结果三种,含义明确:
- `✓ 探针成功:拿到 N 篇` → 凭据有效,下一轮监听(4/8/14/20 点)自动走 ⓪ 分支
- `⚠ 被频率限制(200013)` → **凭据是好的**,只是配额被占;新注册的号配额干净
- `✗ 会话失效(200003)` → 重新登录取一次(后台登录态通常几天就过期)

> ⚠️ **不要用 `--from-werss` 自动提取**:`wx.lic` 把凭据**拆成多行**(`cookie` / `slave_sid` /
> `slave_bizuin` / `wxuin` 各一行),直接取 `cookie` 行只有 74 字符,拼不出可用的登录态
> (2026-10-01 实测:提取后探针返回 200003)。该选项留着仅为将来摸清它的拼接方式。

> 📌 **WeRSS 可以退休了**:它与自研 Wemp 取的是同一套后台接口,而源码不归我们、还有停维前科
> (见 §4g 抗停维三层防御)。有了自持凭据后,`_platform_client` 的择源链会自然走到自研 Wemp。

### 4j. 双实例分工:谁跑什么、怎么隔离(2026-10-01)

**背景**:项目有两套部署 —— 本机(Windows,`D:\code\redian`)与远程 VPS(`https://redu.tian1she.xyz`)。
**两边的数据库是独立的**(本机 sqlite `data/platform.db`、远程 MySQL),但**推的是同一个飞书群**。

**问题**:不加约束时两套实例各跑一份完整调度器 —— 同一个作业执行两次,重复推飞书、重复打上游;
更糟的是**本机的热点数据源早已停用**(`user_schedules` 里 douhot/baidu/weibo 全停),跑热点作业
纯属拿 3 天前的旧数据空转并推送(2026-10-01 审查发现 `hotspot_suggestions` 当天还在用 9-29 的数据更新)。

**机制**:`SCHEDULER_ROLE`(`config/settings.py` → `scheduler._role_allows`)

| 取值 | 含义 | 用于 |
| --- | --- | --- |
| `all` | 全跑(默认) | 单实例/开发 |
| `wechat` | 只跑**公众号 + 闲鱼**侧 | **本机** |
| `hotspot` | 只跑**热点**侧 | **远程** |

- 每个作业在 `build_jobs` 里都标了归属(`wechat`/`hotspot`/`both`);`both` 是中性作业
  (采集调度、告警、清理),两边各按自己库里的数据行事,不冲突。
- ⚠️ **但 `both` 有个破口,2026-10-02 已堵**:`collect_tick` 是 `both`(两端都跑),它的
  防重复靠 `claim_schedule` 原子抢占 —— 而**两台实例的数据库是独立的,各自抢占都会成功**
  → **同一个上游账号会被两端同时采集**。原处置("远程闲鱼 Cookie 已死 → 调度自动归 off")
  是**靠 Cookie 恰好死了**,太脆。现在代码里加了**按板块分侧的护栏**
  (`scheduler._SECTION_ROLE` + `_section_allowed`):`wechat` 侧只采**公众号+闲鱼**、
  `hotspot` 侧只采**微博/抖音/百度**,本实例不分管的板块**直接跳过、不碰上游**。
  **触发原因**:闲鱼实测 `RGV587_ERROR::哎哟喂,被挤爆啦` 是**账号级**限流(换手机热点出口
  也没用、请求量只有 6 次/小时),双跑是头号嫌疑。

**权威分工表** —— 下面的数字是**跑 `build_jobs` 按两种角色各注册一次取交集/差集**
得到的(不是抄文档,文档此前自相矛盾):

```
全部 31 个作业 | 本机(wechat) 跑 24 | 远程(hotspot) 跑 15 | 两端都跑 8
```

> **跨实例可见性(2026-10-03)**:两边**库独立**,所以本机看不到远端的 runs ——
> 微博/抖音/百度热榜归远端跑,本机只知道它们"数据停在某天",分不清是**远端整机挂了**
> 还是**那些源本身没更新**。补了两条:
> ① 本机健康页的「对端实例」探活(`GET /api/source-health/peer`,读远端公开的 `/healthz`,
>    **不新增暴露面**)→ 布上 `PEER_HEALTH_URL` 即可见"远端在线/失联";
> ② 远端每天 09:20(`health_push`)**往管理员群推一张板块健康卡** —— 只在远端跑,本机不重复;
>    ⚠️ **只推管理员群、不回落主群**(采集源健康属运维噪音,进客户群是事故)。
>
> **远端配 `FEISHU_WEBHOOK_ADMIN` 的正确姿势(2026-10-03 实测)**:compose 与 `.env` 都在
> `/www/server/panel/data/compose/redu/`,**服务名是 `redu-api`**(不是 api)。⚠️
> **`docker restart` 不会重读 env** —— 必须让容器**重建**:
> `cd /www/server/panel/data/compose/redu && docker compose -f docker-compose.yaml up -d redu-api`
> (该命令会顺带拉最新镜像,所以它同时也是远程的**手动发版**手段)。改前先 `cp -a .env .env.bak.$(date +%s)`。
> 配好后的实测效果:远端卡显示 `🟢 微博 0.5h / 🟢 抖音 0.9h / 🟢 百度 0.4h` ——
> **本机看到的"那三条停在 09-29"纯粹是库独立造成的,远端一直是健康的**。

| 类别 | 本机 | 远程 | 备注 |
| --- | :---: | :---: | --- |
| 公众号监听/候选/续期(`wechat_collect_tick` 等 4 个) | ✅ | — | Cookie 家产家用,搬过去就死 |
| **闲鱼采集** | ✅ | — | 远程那份**已确认关着** |
| 微博/抖音/百度热榜 | — | ✅ | 它们的 Cookie 在 VPS 有效 |

| 热点侧分析(agent/事件归属/建议结算/窗口) | — | ✅ | |
| 跨平台对标号发现 / 关键词文章 / 会员续费 / 死号清理 | ✅ | — | |
| **告警**(采集失败/健康停滞/定时摘要)、重试、清理 | ✅ | ✅ | **不是重复**:各看**自己库**里的数据,内容本就不同 |

| 类别 | 判据 | 去哪 | 举例 |
| --- | --- | --- | --- |
| **内容** | **给客户看/用的:资源 + 可直接点的链** | 各板块**专属群**;未配则回落**客户主群** | 公众号文章、抖音线索、知乎直链、名字型热度、**迅雷群新分享**、**扫盘资源清单**、资源库推送、复盘周报 |

- ⚠️ `webhook_for(settings, s) or settings.feishu_webhook_admin` 这种写法**不管用** ——
  主群一配,`webhook_for` 就永不返回空串,右边是**够不到的死代码**。
  要改某个推送的目的地,就直接写清 `getattr(settings, "feishu_webhook", "")`(内容)
  或 `feishu_webhook_admin`(维护),别靠 `or` 链去猜。
- **话术口径**:推送是为了**让用户更好总结** —— 卡片**结论先行**(先说"这批是什么、能不能直接用"),
  再上明细,别只甩一张表让人自己数。

## 7. 数据备份

- **自动**(SQLite 本地部署):每日 **03:10**(随 `data_cleanup`,2026-10-03 从 04:00 错开 ——
  那里与 `wechat_collect_tick` 撞、两者都在压 SQLite 写锁)快照到 `data/backups/platform_YYYYMMDD.db`,
  保留最近 7 份。走 SQLite 在线备份 API,库正被写入时也一致;快照产出后会校验非空 + `PRAGMA quick_check`,
  不合格的直接删掉——**宁可没有,也不留 0 字节的假备份**。
- **手动**:`sh scripts/backup.sh`(按 `DATABASE_URL` 自动选 SQLite / MySQL;SQLite 与自动快照同一实现)
- **远程 MySQL 自动备份(2026-10-03 新增)**:VPS 上 `/root/redu-backup.sh` + cron 每日 **03:40**,
  产出 `/root/redu-backups/redu_YYYYMMDD_HHMMSS.sql.gz`(约 57MB),**留 7 份**。
  ⚠️ 脚本是**自包含**的 —— VPS 上只有 `docker-compose.yaml` + `.env`,**没有源码**,
  所以复用不了仓库里的 `scripts/backup.sh`(实测确认)。凭据在容器内取
  (`MYSQL_USER`/`MYSQL_PASSWORD` 是 mysql 容器的环境变量),**不写进脚本**;
  **失败会推管理员群**(备份静默失败等于没有备份)。⚠️ 但它和数据库在**同一块盘上**,
  扛不住盘坏 —— 见 §7c-D 的缺口说明。
- 检查备份是否健康:`ls -la data/backups/` —— **任何 0 字节文件都说明备份失败**,别当成"有备份"。
  备份失败会在服务日志里记 `SQLite 快照备份失败`(stdout,`docker logs` 可见)。
- ⚠️ 不要直接 `cp`/`gzip` 库文件当备份:写入过程中拷贝可能得到撕裂的中间状态,恢复时才发现坏。

### 7b. 数据保留(按表分档,2026-10-03)

`DATA_RETENTION_DAYS`(默认 30)只兜住**热榜/快照/运行/日志**那一批;其余按**性质**各自定窗口
(`app/db/maintenance.py`)。**关键是别把"资产"当成"日志"删** —— 那等于让系统"忘了自己有什么":

| 类别 | 表 | 窗口 | 为什么 |
| --- | --- | --- | --- |
| 热榜/快照/运行/日志 | `douhot_words`、`weibo/baidu_hot_items`、`runs`、`feishu_alerts` 等(~22 张) | **30 天** | 纯时间序列,旧的没有价值 |
| 公众号文章 | `wechat_articles` | **无盘链 60 天 / 带盘链 180 天** | 带链的是改写素材 |
| **结算/复盘底料** | `hotspot_suggestions`、`douyin_leads`、`discovered_pan_links`、`quark_share_stats` | **180 天** | 对账要跨月看,30 天会把刚攒的对照清掉 |
| 群分享 | `xunlei_group_shares` | **未转存且 >60 天** | 转存成功的行是**我方资源的来源凭证**,要留 |
| **资产(不按时间删)** | `xunlei_resources`、`cross_platform_accounts` | — | 我方资源清单 / 收录的对标号,**删了就"忘了自己有什么"** |
| 明确废弃 | `cross_platform_accounts` 中 `status='dismissed'` | 立即清 | 被否掉的号留着没意义 |

> ⚠️ `xunlei_resources` 的另一半联动在 `xunlei_cleanup`:资源**从盘上删掉**时,
> 对应行**一并删除** —— 否则资源库会给出**已经失效的分享链**(比"没有链"更糟:点了打不开)。

### 7c. 恢复步骤(2026-10-03 补 —— 此前**完全没有**恢复文档)

```sh
docker start redu-api && curl -s http://127.0.0.1:8080/healthz
```

#### C. ⚠️ 密钥(`.env`)—— **最容易被忽略、也最容易被做错的一环**

**症状**:只恢复 DB、不恢复 `.env` → **登录能用**(`password_hash` 是 bcrypt,不依赖密钥),
但**所有采集凭据全部解不开** —— 库里的 `user_cookies`、`wemp_cred_N`、`smtp_pass` 都是
Fernet 加密的(密钥来自 `.env` 的 `JWT_SECRET`/`COOKIE_ENCRYPT_KEY`)。结果是**所有平台都要重扫码**。

⚠️⚠️ **但绝不能把 `.env` 放进异地 GitHub 仓库**:
异地仓库里那份 DB **本身是加密的** —— 一旦把密钥放进**同一个仓库**,
等于**把钥匙和锁放在一起**,加密形同虚设(而那个仓库的可见性刚被证明是会变的:
2026-10-03 就查到一起"线上 webhook 落在**公开**仓库"的事故)。

**正确做法**:密钥**单独存一份在别处**(密码管理器 / 离线介质 / 只有你自己能拿到的地方)。
`data/backups/` 与异地仓库都**刻意不含 `.env`**,这是设计,不是遗漏。

### 9.2 mp/articles 的 -2041 与冻结号的替代源(2026-09-18,2026-09-27 修正定性)

- 实测:mp/articles 回 -2041 后**换新 Cookie 依旧**,而 cover/书架接口不受影响。

### 9.1 实战补充(2026-09-17/18 夜):wr_rt 吊销与 renewal 频控

- 症状:重扫后数小时内 Cookie 再死,renewal 冷却(2h)过期重试持续失败超 20 小时,
  白天也不解禁——这不是小时级频控,而是 **wr_rt 被吊销/标记**(多端使用 + 密集续期
  触发账号级风控)。冷却机制保证不撞墙,但救不回被吊销的 wr_rt。
- 判定方法:`refresh_skey` 能换出 skey 但验证即死(或换不出),持续超过 6 小时 → wr_rt 已废。
- 唯一恢复路径:**重新扫码复制新 Cookie**(新登录会话重置风控状态)。
- 预防:① 复制后绝不再在该浏览器使用微信读书;② 监控频率保持克制(81 号×每小时
  已属激进,频繁被锁可放宽到 2h);③ 系统侧冷却+指纹告警保证失效可见、不恶性循环。

### 9.2 `-2014 请求频率过高` 曾被读成"该号暂无文章"(2026-09-22)

- `/api/mp/cover` 的错误**不在顶层 `errCode`**,而是 HTTP 499 信封里的 `data.errcode`
  (`{"statusCode":499,"data":{"errcode":-2014,"errmsg":"请求频率过高"}}`)。
- 旧 `_get` 只看顶层 → code=0 当成功 → `mp_cover` 判"未返回 reviewId"→ `latest_article`
  返回 None → 监听把整轮限流算成"这些号今天没发文",**`status=success new=0`,无任何告警**。

## 9. 微信读书 Cookie:为什么"过期快",怎么免维护

- **机制**:wr_skey 短效(约 12~24h)且**轮换制**——浏览器和服务端谁调续期,旧 skey 都会失效。
  长效兜底是 `wr_rt`(约 30 天)。
- **自动续期**:调度每 6 小时跑 `weread_refresh_tick`(50 */6 * * *),用 wr_rt 换新 wr_skey
  并回写平台内「weread」Cookie,**有效期内主动轮换 = 永不过期**。
- **失败即报**:续期没成功会即时推公众号飞书群(带冷却,不刷屏),不等监听断掉才发现。
  提醒里点名原因(2026-09-22 起,原来一律写"wr_rt 已整体失效"误导处理方向):
  `renewal 换不出新 wr_skey`=wr_rt 死/被频控 → 重新复制;
  `换出新 skey 但书架验证仍报登录失效`=登录态整体过期 → 必须重新扫码;
  `Cookie 里根本没有 wr_rt`=续期根本没起跑(这类过去被当 skipped **静默放过**)。
  ⚠️ 提醒**只推给第一个失败用户**,多账号同时失效时其余人要自行核对。
- **⚠️ 换 Cookie 后的关键动作**:复制 Cookie 后**尽量别再在原浏览器使用微信读书**——
  浏览器会自己轮换 wr_skey,把服务端这份顶失效。这是"Cookie 过期好快"的最常见主因。
  另外 wr_rt 也可能因在别处重新扫码登录被顶掉。
- 手动续期:前端「微信读书」页有续期按钮(POST /api/wechat/weread/refresh)。

## 10. 闲鱼风控体系(现状)

> **换 Cookie 用扫码脚本(2026-10-01 起)**:`python scripts/xianyu_login.py`——
> 终端显示二维码 → 手机闲鱼 App 扫码确认 → Cookie **自动加密入库**(三件套校验后),
> 不再需要 F12 手工复制(手工复制最易漏 `_m_h5_tk`/`unb`/`cookie2` 导致 TOKEN_ILLEGAL)。
> 协议按公开实现调研后独立实现(passport.goofish.com 二维码流程),curl_cffi TLS 指纹同采集侧。
> 采集侧另有**三件套完整性前置校验**:残缺 Cookie 直接 skipped 并给出指引,不再空转一轮。
> ⚠️ 仍适用:扫码后尽量别再用浏览器开闲鱼(会话互顶);连续失败先观察 1-2 个调度周期(间歇风控会自愈)。

- 传输层 curl_cffi 模拟 Chrome TLS 指纹;证书校验默认开启,本机 CA 损坏(curl:77)自动降级并告警一次。

  `XIANYU_REQUEST_DELAY`(默认 8s)带 ±20% 抖动。
- 限流(FAIL_SYS_RATE_LIMIT)指数退避 30/90/180s;滑块(FAIL_SYS_USER_VALIDATE)立即停止本轮。
- 滑块后自动冷却:`XIANYU_COOLDOWN_MINUTES`(默认 30)起,**24h 内每再触发一次翻倍**,封顶 240 分钟,
  期间调度轮次自动跳过(run 记录 `verify_cooldown`),并即时推闲鱼飞书群。
- 深采(详情)限 `XIANYU_DETAIL_LIMIT`(默认 10)个/轮、`XIANYU_DEEP_INTERVAL_HOURS`(默认 6h)一轮,
  当天已抓过的商品不重复请求;网关空响应(WAF 静默拦截)会报"疑似 WAF 风控拦截"并带响应片段。
- 治本手段是**固定住宅出口代理**(`XIANYU_PROXY_URL`);轮换代理池不可用(token 绑定出口 IP)。

## 11. Cookie 加密密钥事故(2026-09-13)

- 现象:重启后闲鱼/微博/抖音采集报"未配置 Cookie",但界面看明明配置过。
- 根因:`JWT_SECRET` 未配置的时期,进程用**随机临时密钥**加密 Cookie,重启即全部失读;
  且旧进程带旧密钥持续回写坏行,新进程读不了。`get_cookies` 此前静默跳过坏行,故障被掩盖。
- 修复:① `get_cookies` 对"行存在但解不开"自动用该平台全局配置/Cookie 文件以当前密钥回写(自愈);
  无兜底源的告警提示重贴。② `.env` 必须固定 `JWT_SECRET`(生产),否则每次重启丢所有登录态和 Cookie。

## 13. 系统代理事故(2026-09-29)——代理软件退出毒杀全部采集

### 现象

9-29 20:02 起 `wechat_listen` 一轮 **81 个对标号全部失败**(错误 `WereadError`,
非 AuthError),baidu 采集连接失败、闲鱼两轮"全部关键词未返回数据"、微信读书
自动续期失败进冷却。白天(04:00-14:00)一切正常,20:00 突然全灭。

### 根因

本机代理软件(Clash 类,监听 `127.0.0.1:7892`)退出时**没有还原 Windows 系统代理
注册表项**——`HKCU\...\Internet Settings` 残留 `ProxyEnable=1, ProxyServer=127.0.0.1:7892`,
而 7892 已无进程监听。Python `requests` 默认 `trust_env=True`,在 Windows 上会读
这张注册表(`urllib.request.getproxies()`),于是**所有未显式指定 proxies 的请求**
(weread/百度/闲鱼/续期……)全撞死代理。`ProxyOverride` 里只有 zhihu/jd 等白名单,
不含本项目任何采集域名,保护不了。

判定方法:请求异常里出现 `ProxyError('Unable to connect to proxy',
... 127.0.0.1:7892 ...)` 即此因;`netstat -ano | findstr 7892` 无 LISTENING +
`reg query ... /v ProxyEnable` 为 1 即坐实。

### 修复(两层,均已落地)

1. **应急**:关闭死系统代理
   `reg add "HKCU\...\Internet Settings" /v ProxyEnable /t REG_DWORD /d 0 /f`
   现有进程下一次请求即恢复(requests 每次请求实时读注册表),无需重启。
2. **防再犯(代码免疫)**:`app/utils/proxy.py::disable_env_proxies()`,
   patch `requests.utils.getproxies` 恒返 `{}`,在三个入口调用
   (`app/main.py` 独立调度/API 模式 + `app/platform.py::create_app`)。
   进程内 requests 从此对系统代理**免疫**,代理软件再怎么开/关/崩都不影响采集。
   注意:不能用 `Session.trust_env=False` 类属性 patch——requests ≥2.33 已把
   trust_env 改为实例属性,类属性会被 `__init__` 覆盖(实测 2.34.2)。

显式代理不受影响:闲鱼专用代理(`xianyu_proxy_url`)、隧道/提取式代理池
(`get_proxies()`)都走显式 `proxies=` 参数,与本开关无关。
