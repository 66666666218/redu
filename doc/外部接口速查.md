# 外部接口速查

> **为什么有这份文档**(2026-10-03):那天为了"补几个活跃群",我先猜 `group/search` 的参数
> (**试了 60 多种形状全 400**)、又去解 APK(结果是**加固壳**:桩 dex 只 21KB/7 个类,字节码拿不到)、
> 又扫群号附近(全是 2 人私聊群)、又找退群接口(不存在)—— **绕完才发现答案一直躺在
> `xunlei_kouling.resolve()` 里**。**问题不在代码,在于没有一份"哪个接口在哪、长什么样"的索引。**
> 这份文档就是那个索引;**新增/改动外部接口时请回来更新它**(和 `doc/API.md` 同级要求)。
>
> 各模块的**详细报文样例与踩坑记录**仍写在对应源码的模块 docstring 里(本文给出位置),
> 本文只做**索引 + 最容易忘的坑**。

### 1.1 群组(chitchat)

```text
GET  {_BASE}/chitchat/v1/group/list        账号所在的全部群
GET  {_BASE}/chitchat/group/records        ⚠️ **没有 v1**,且**只有 GET**(POST 一律 404)
POST {_BASE}/chitchat/v1/group/query       单个群信息(不登录也能查,凭 group_id)
POST {_BASE}/chitchat/v1/group/join        ⚠️ group_id **必须传数字**,传字符串报 201
GET  {_BASE}/chitchat/group/sessions       聊天会话(与 group/list 同集合)
POST {_BASE}/chitchat/v1/group/member/query 群成员
```
`_BASE = https://api-shoulei-ssl.xunlei.com`,详见 `xunlei_group.py` 模块说明。

**四个必记的坑**:
1. **每页只回 20 条**(`count` 传更大也没用),翻页用 `record_id` 游标 + `direction=1`(**往更旧翻**,已实测);
   只拉最新一页会**静默丢消息**(见 `_records_with_catchup`)。
2. **没有退群端点** —— `group/quit|exit|leave|member/*` 全 404。加群是**单向**的,只能去 App 手动退。
3. **`/chitchat/v1/group/search` 存在但参数未知**:返回 `400 code:201` 而非 404,说明路由在;
   但试过 keyword/key/word/q/query/searchKey/超集 body/查询串/表单/camelCase/路径参数 **全 400**。
   **别再去猜它** —— 需求(群名 → 群号)用下面那条 `associate_search` 就够了。
4. **同名群并存**:`三岁分享`=1550069837 而 `三岁分享2`=1556104079 —— **别拿群名当唯一键**。

### 1.2 口令 / 群名解析(⭐ 最容易忘的一条)

```text
GET {_BASE}/xlppc.searcher.api/v3/associate_search?keyword=<词>&guid=<device_id>
      → resp["birdkey"]["action_url"] 里含 group_id= 或 share_id=
```
* 代码:`xunlei_kouling.resolve()`;
* **《群名》会被解析成 `kind="group"` + `group_id`**,`ingest()` 随即 `join_group()` ——
  **"抖音《群名》→ 自动加群"整条链就是它**,别再另找"搜群接口";
* `/xlppc.searcher.api/v1/search` 也存在,但要账号参数(回 `无效的数字账号`),**不用它**。

### 1.3 群邀短链

```text
https://dlj.8uri.cn/dlj/<8位码>  --302-->  https://sj-m-ssl.xunlei.com/group-invite?from_uid=&group_id=&type=url
```
邀请页是 **Nuxt SSR,无需登录**,群名/群号写在 `__NUXT__` 里;`8uri.cn` 本身是"迅雷短网址"服务。

### 3.1 MediaCrawler 系(小红书 / 快手 / 微博 / 贴吧 / 抖音 / B站)

这六家**带 Cookie 直连过不去**(微博 `ok:-100`、贴吧 403、小红书/抖音要请求签名),
只能走 MediaCrawler:`app/services/mediacrawler_source.crawl(platform, keywords)`。

* ⚠️ **独立 venv + 绝对路径**(`tools/MediaCrawler/.venv`),且**一次浏览器跑完所有关键词**;
* 贴吧等平台**需要先手工登录一次**(档案 `browser_data/cdp_<平台>_user_data_dir`,
  见 `tools/tieba_login.py`);未登录会卡扫码直到超时 → `MediaCrawlerError`;
* **实测命中率**(2026-10-03,同一批词):**贴吧 56%** > 知乎 17.8% ——
  所以"公开发现链"以**贴吧为主源**(`PAN_DISCOVERY_TIEBA`)。

### 3.2 公众号阅读数:**微信读书列表接口能给,但有会话额度**(2026-10-04 二次定案)

> ⚠️ **本节在 2026-10-04 当天被改过两次,留痕警示**。上午的版本写着
> 「全平台断供、`mp/articles` 恒 `-2041`」——**那是错的**,是**没控制变量的证伪**:
> 当时那几次测试用的号**全都排在额度之后**。傍晚从书架**第 1 个号**重测,
> **前 29 个号 100% 拿到精确阅读数**。详见
> `doc/阅读数与迅雷盘-结论与方案-2026-10-04.md` 第二节。

**结论先行**:别人号的**精确**阅读数(`readNum`,如 `1151` 而非分档),**能免费拿到** ——
走微信读书 `/web/mp/articles`(本仓客户端 `WereadClient.mp_articles` +
`flatten_mp_articles`,**一行都不用改**)。**限制是会话额度**:

| 项 | 实测值 |
| --- | --- |
| 每个会话能问多少个号 | **约 29 个**(第 30 个回 `-10100`) |
| 一次拿多少篇 | 该号 **15~158 篇**的全部历史的精确阅读数 |
| 单个号耗时 | 约 2.4s(客户端自带节流) |
| 额度耗尽后的错误码 | **`-10100`**(旧见过的 `-2014`/`-2041` 同族) |

⇒ **`_listen` 的处置:每轮只问「上次问到列表时间最久」的 25 个号**(`_LIST_WINDOW`,
记号存 `system_config[weread_list_marks_<uid>]`)。按"最久没轮到"挑 ⇒ 与批子集、
与书架闸门的排序**都无关**,有闭式上界 `ceil(池/批) × ceil(批/窗口)`,
142 号池 / 批 36 / 窗口 25 ⇒ **8 轮 ≈ 2 天轮一圈**(实测吻合)。
⚠️ 别用"按序号 + 游标右移"——本轮号列表既非全量、次序又每轮都变,那种写法覆盖是碰巧而非保证。

**仍拿不到的那部分**:`/api/mp/cover`(每轮保底路径)返回体里**没有 readNum** ——
所以**不在轮转窗口里的号,那一轮就是没有阅读数的**,这是设计取舍,不是故障。

2026-10-04 逐条**当场实测**(不是推断)的负面结论:

| 路 | 结果 |
| --- | --- |
| 微信读书 `/api/mp/cover` | 200,但返回体只有 `avatar/name/title/pic/reviewId/template/coverBoxInfo` —— **没有 readNum** |
| 微信读书 `/web/review/list`(listType 1~9)、`/web/mp/notes` | 全空 / 404 |
| 文章页 HTML(`mp.weixin.qq.com/s/xxx`) | 阅读数是服务端**空占位符** `'' * 1`,全靠前端 `getappmsgext` 补 |
| `mp/getappmsgext`(带微信 PC 端**全套真 cookie**) | `ret:0` 但**响应里没有 `appmsgstat`** —— 静默空壳,**别被 ret=0 骗**(客户端本地缓存的 read_num 也是 8-28 的,24h TTL 已过期) |
| `mp/profile_ext?action=home/getmsg`(带真 cookie) | `ret:-3 no session` / 「请在微信客户端打开链接」—— 要的是**客户端身份**,不是 cookie |
| 腾讯官方 Agent API 的公众号 scope | `-2041`(未对 API Key 开放) |
| 微信**安卓 App** `i.weread.qq.com/book/articles` | 401(21 种鉴权形状全试过;凭据已从 `WRAcount` 表拿到仍不行) |
| MITM 微信读书 App(雷电:系统证书 + ADB 代理 + 防火墙放行) | ❌ App 一挂代理就卡死(pinning) |
| 微信读书**搜索**端点 `wx_search_broker_proxy` | ⚠️ 阅读数**只有分档**(`阅读 1万+`)、**只覆盖约 8%**;但**当"发现链"有用**(盘链 + 号名 + 分钟级新鲜) |
| **WeRSS** | **无此能力**:5 种采集模式里 `read_num` 只出现在 `weread_mp.py`(即上面那条);生产入口把 `read_num` **写死 0** |
| 公众号后台 `appmsgpublish` | ⏸️ 凭据已就位且有效,但恒回 **`200013 freq control`**(账号/IP 维度限流),待复验 |
| dajiala(极致了)付费 | 2026-09-29 用户决定不充值(¥0.06/篇)后废弃 —— **现在也不需要了** |


**数据侧印证**:库里 `read_num>0` 的 168 篇,入库时间**全部落在 09-14 ~ 09-28**,之后一篇都没有。
**原因现在知道了**:那段时间 `_listen` 是**先枚举列表**的,09-28 之后列表被额度挡住、
代码又没做轮转 ⇒ **每一轮都只有最前面那几个号能拿到**,最后连"最前面"也拿不到
(那时的熔断器连 `-10100` 都不认)。轮转落地后这批历史数据会自然补齐 ——
**不用回填**,下个周期每个号都会带上当轮的精确阅读数。

**用途别记错**:阅读数是**爆款判据**(`_listen.py` 的同号中位数倍数检测、卡片排序/显示),
**不参与结算**(`hotspot_suggestions.reads_gain` 至今全 0、`wechat_traffic_samples` 0 行;
结算已改道 `repost_gain`)。

**还剩什么**:① 公众号后台 `appmsgpublish`(免费,待验证 —— 有它就**不受 29 个号的额度限制**,
值得复验);② 用搜索端点(`wx_search_broker_proxy`)当**发现链**(盘链 + 号名,分钟级新鲜)。
