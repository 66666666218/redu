# 闲鱼纯协议:链路拆解与自修指南

> 2026-10-08 建。姊妹篇:`小红书纯协议-链路拆解.md`、`抖音纯协议-链路拆解.md`。
> **这篇的核心是一句话**:`RGV587_ERROR::哎哟喂,被挤爆啦` 跟账号、出口、TLS、请求头**都无关**,
> **卡的是 cookie 那一份**。我们为此绕了两年。

---

## 0. 结论(时间紧只看这里)

1. **纯协议可用**,`XianyuClient` **一行代码都不用改** —— 换一份**完整的 cookie jar** 就行。
2. 实测:3/3 关键词、每个约 **0.35 秒**(浏览器那条要 10~20 秒,还偶发 `TargetClosedError`)。
3. **搜索与深采(详情)两个接口都验过了**。
4. 采集路径已改成**协议优先、浏览器兜底**;开关 `XIANYU_PREFER_PROTOCOL`。

⚠️ **还没验的**(别当成已完成):只验了**首屏**;翻页未验;整套 cookie 的**有效期**未知;
连发多少会再触发风控未知。

## 1. 链路长什么样

```
tools/xianyu_export_cookie.py      ← 从浏览器档案导出**整套 jar** → 加密 cookie 库(平台 goofish)
        │
        ▼
app/services/tenant.py  run_xianyu()
        │  客户端选择:`tenant_base.pick_xianyu_client()`
        │     ① 协议优先(约 0.35 秒/词)
        │     ② 失败 → 回落浏览器(`_collect_hot_with_fallback`,重跑且**留痕**)
        ▼
app/services/xianyu.py  XianyuClient      ← 签名 / 令牌刷新 / 错误分类,本来就写好了
        │
        ▼
POST https://h5api.m.goofish.com/h5/mtop.taobao.idlemtopsearch.pc.search/1.0/
        │
        ▼
app/services/xianyu_analytics.py  run_xianyu_deep()   ← 深采(详情/想要数)**同一个选路函数**
```

★ **搜索与深采必须用同一条路**。2026-10-03 就是因为两边分叉(搜索走浏览器、深采走协议),
行情(想要数/收藏/出单)一直卡在风控上,而症状看起来像"接口没数据"。
现在两边共用 `tenant_base.pick_xianyu_client`,规则只有一处。

## 2. 接口合同

**端点**:`POST https://h5api.m.goofish.com/h5/mtop.taobao.idlemtopsearch.pc.search/1.0/`

**查询参数(12 个,一个不多一个不少 —— 抓包实测)**:

| 参数 | 说明 |
|---|---|
| `jsv` | `2.7.2` |
| `appKey` | **`34839810`** |
| `t` | 毫秒时间戳 |
| `sign` | `md5(token & t & appKey & data)`,token = `_m_h5_tk` 里 `_` 之前那段 |
| `v` / `type` / `dataType` / `accountSite` / `timeout` / `api` / `sessionOption` / `spm_cnt` | 固定值,见 `xianyu.py` |

**⚠️ body 是 form 编码**:`data=<urlencode 过的 JSON>`,**不是裸 JSON**。
`json.loads(body)` 能过但顶层字段是空的 —— 我第一次就栽在这,又包了一层
`data={"data": body}`,被回 `FAIL_BIZ_COMMON_PARAM_ILLEGAL::闲鱼太累了休息一会吧`。

**请求头 —— 只有两个**:
```
Accept: application/json
Content-type: application/x-www-form-urlencoded
```
★ 抓包实测页面**没有带任何自定义头**。所以"我们少了某个头"这个方向**是死的**,
别再往那儿查。

## 3. ★ 真正的关卡:cookie jar

页面发出去的是**整套 jar**(16~18 项),而我们当年只贴了"登录三件套"。关键在这几组:

| 组 | 项 | 作用 |
|---|---|---|
| 登录态核心 | `unb`、`cookie2` | 缺任一必 `TOKEN_ILLEGAL`(代码里有校验) |
| **风控 SDK** | **`sgcookie`、`tfstk`、`_tb_token_`、`_hvn_lgc_`、`havana_lgc2_77`** | ★ **阿里 Havana 风控 SDK 发的** —— 被校验的就是它们 |
| mtop 令牌 | `_m_h5_tk`、`_m_h5_tk_enc` | 短效,采集器首屏会自己从网关拿 |

**判据是控制变量出来的**:

| 变量 | 结果 |
|---|---|
| 匿名(只有 `cna` 等 5 项) | ❌ `RGV587_ERROR::被挤爆啦` |
| 匿名 + 照抄开源客户端(httpx / 老 UA / 无 Origin) | ❌ 同样被挤爆 |
| **整套 jar + 普通 `requests`(连 TLS 指纹都不伪造)** | ✅ `SUCCESS::调用成功` |
| 整套 jar + `curl_cffi` | ✅ 同样成功 |

⇒ 与账号无关、与出口无关、与 TLS 无关。**只与 cookie 有关。**

## 4. 凭据从哪来

```bash
python tools/xianyu_export_cookie.py --check   # 只看关键项齐不齐,不写库
python tools/xianyu_export_cookie.py           # 导出进加密库(用户 1,平台 goofish)
```

⚠️ **别再手工从浏览器 Network 里抄 Cookie 了** —— 抄不全,而且**没人知道漏了哪一项**。
这次绕两年,根源就是这个动作。

**两个已踩的坑**:

1. **必须先访问一次首页**。只开浏览器不导航时 `ctx.cookies()` 只回 **13** 项,
   **缺 `cookie2` 和 `_tb_token_`**;页面加载过之后才变成 16~18 项。
   所以导出工具里的 `goto` 不是"顺手逛逛",是**必要条件**。
2. **别去杀占着档案的浏览器**:那是生产在用的那个(进程内单例、闲着也留着)。
   等它闲置自关(`XIANYU_BROWSER_IDLE_CLOSE_SEC`,默认 900 秒)。

## 5. 踩过的坑(2026-10-08,全部真踩)

### 坑 1:★ 两年的错误归因 —— "账号级限流"
我们一直写 `RGV587 是账号级限流`(依据:"换手机热点出口也没用、请求量只有 6 次/小时,
所以既不是 IP 也不是频率")。**这个归因是错的** —— 匿名请求(压根没有账号)照样被挤爆。
它会把后来的人引向"换个号/换份 Cookie 就好了",而那不是解法。

### 坑 2:协议相对 URL 让重放"看起来被拒"
页面用 `//h5api.m.goofish.com/...`(协议相对),`urlparse` 给的 scheme 是**空串**,
拼成 `://host` ⇒ 两次重放全报 `InvalidSchema` / `InvalidURL`。
**看起来像被拒,其实是自己拼错了 URL。** 这类"自己造的失败"最容易被误读成平台行为。

### 坑 3:form body 被包了两层
见 §2。注意它回的是 `FAIL_BIZ_COMMON_PARAM_ILLEGAL::闲鱼太累了休息一会吧`
—— ⚠️ **那已经不是 `RGV587` 了**,说明风控关卡当时**已经过了**,只是参数不对。

### 坑 4:深采与搜索分叉(2026-10-03)
见 §1。规则现在只有一处(`pick_xianyu_client`),并有测试钉住。

### 坑 5:浏览器路自己的偶发失败
`TargetClosedError: BrowserType.launch_persistent_context`(2026-10-08 00:43 实测一次)
会让**整轮**失败。换成协议后这类失败一并消失。

### ★★ 坑 6:截获钩子静默失效,把「被风控」伪装成「接口超时」(2026-11-18)

`xianyu_browser._search_by_page` 一直用 `add_init_script` 钩
`window.lib.mtop.request`(存进 `window.__xy_cap`)。**现在页面已不再经过那个入口发搜索**:
用 `page.on("response")` 旁听同一次搜索,搜索请求 **9/9 都发了出去、状态 200**,
而 `__xy_cap` **一条都没截到**(它截到的 8 条全是 `gaia` / `loginuser` 之类)。

**后果是两层静默**:

1. 首选路**返回 0**(而不是报错)⇒ 调用方以为"页面没发请求";
2. 于是落 `_search_direct`,那条路必回 **`TIMEOUT::接口超时`**
   ⇒ 真因(滑块 `FAIL_SYS_USER_VALIDATE` / `RGV587_ERROR::SM::哎哟喂,被挤爆啦`)
   连报都报不出来。值班的人会去查网络/接口,而正确的动作是**去拖滑块**。

**修法**:截获点搬到网络层(`page.on("response")`),`__xy_cap` 只作兼容保留;
并且网络层**认得出风控**时抛 `XianyuVerify`(`search()` 里单独 `raise`,不许落兜底)。

⚠️ **判据不许用 `"success" in body`** —— 滑块 `punish` 端点回的是
`{"code":0,"dt":"success","ec":200,"result":{"code":0,"sig":"from bx"}}`,不含 `api`/`ret`,
按子串判会把**被拦**读成**恢复**(当天第一版监测脚本就是这么假报了一次)。
只认 `obj["api"] == "mtop.taobao.idlemtopsearch.pc.search"` 且 `ret` 含 `SUCCESS`
且 `data.resultList` 非空。

⚠️ **反过来也不许要求 `api` 字段存在**:真的风控回包
`{"ret":["FAIL_SYS_USER_VALIDATE","RGV587_ERROR::SM::…"],"data":{"url":"…/punish?…"}}`
**没有 `api`**(那是正常回包才有的)。我第一版把 `obj.get("api") != API` 当过滤器,
于是**风控回包被当成 other 扔掉**、读数显示 `RGV587=0`、整条风控判定形同虚设
(当天第二次栽在同一个判据上,两次方向相反)。正解:**按 URL 定位接口**,
`api` 只在**存在时**交叉校验。

### ★★ 滑块藏在哪里 + 「登录态过期」是个假线索(2026-11-18 同日订正)

被风控时页面**确实**弹出滑块,但**主文档里搜不到任何可疑节点** ——
它在 iframe `baxia-dialog-content` 里,src 指向 `.../_____tmd_____/punish?x5secdata=…`。
只扫主文档(`document.querySelectorAll` + `captcha|slider|nc_` 正则)会得出
「页面没有滑块」的结论,于是我让人「等恢复」而不是「去拖滑块」,白等十几分钟。

同时 `mtop.taobao.idlemessage.pc.loginuser.get` 与 `mtop.idle.web.user.page.nav`
都回 `FAIL_SYS_SESSION_EXPIRED::Session过期`,**看起来像登录态没了**。但同一时刻:
页面右上角有用户名(`xy885357173685`)、消息红点 `total=14` 且 `redpoint.query`
回 **`SUCCESS::调用成功`** ⇒ **账号是登录着的**。

⇒ **别拿这两个接口判登录态**,也别把 `RGV587` 当"匿名请求"的证据。
真结论是:**搜索接口被单独风控**,修法只有拖滑块(或换出口/等冷却)。
`scripts/xianyu_login.py` 的判据已按这条改(多取一个 `redpoint.query` 交叉验证,
`SESSION_EXPIRED` 单独出现不算过期)。

### ★★ 自动过滑块(2026-11-26):`app/services/xianyu_verify.py`

滑块不再靠人拖。模块做四件事,顺序固定:

1. **找验证框**:遍历 `page.frames`,URL/name 命中 `punish|_____tmd_____|baxia` 即是。
   ⚠️ **必须轮询**(默认 8 秒)—— 风控回包先到,iframe 之后才建,只查一次必空。
2. **定位手柄**:`#nc_1_n1z` / `.btn_slide` / `[class*='btn_slide']` … 依次试,
   取第一个**可见且 ≥8px** 的盒子;轨道用 `#nc_1_n1t` / `.nc_scale` …,
   且要求轨道宽度 > 手柄 1.5 倍(排除同名小装饰节点)。
   **识别不到手柄 ⇒ 立刻返回 `handle_not_found` 并把验证框文案带出来**,
   绝不猜、绝不瞎拖。
3. **人手轨迹拖动**:加速(25%)—匀速(55%)—减速(20%)的步长分布,
   纵向 ±1px 抖动、每 7 段一次短停顿、按下/松手前后各留 60~260ms;
   总时长 0.9~1.9 秒(太快是脚本特征,太慢会撞 baxia 的空闲判定)。
4. **验收**:拖完**真发一次搜索**(`search_probe`),只认
   `ret` 含 `SUCCESS` **且** `data.resultList` 非空 —— 见下面 §6 那三条禁止。

**接线**(三处,少一处就只救半边):

| 位置 | 行为 |
|---|---|
| `XianyuBrowserClient.search` | 撞 `XianyuVerify` ⇒ `_try_autosolve`(每次 search 只试一次),过了重跑同一页搜索 |
| `XianyuBrowserClient.solve_verification` | 先导航搜索页**把验证框引出来**,再 `find_challenge_frame` + `solve_challenge` |
| `tenant._persist_jar_after_autosolve` | 过验证后把档案**整套 jar 回写**加密库(同一个 `solved_at` 只导一次) |
| `tenant._persist_jar_after_fallback` | **回落浏览器跑通后也导一次**(见下) |

⚠️ **第三条最容易漏**:滑块是在**浏览器**里过去的,种上的 `sgcookie`/`tfstk` 不回写,
**协议路下一轮用的还是过验证之前那份旧 jar**,照样被挡 —— 自愈只救了浏览器路,
而协议路才是常态路。回写前用 `xianyu_cookie_missing` 把关(**缺 `unb`/`cookie2` 不许覆盖**)。

### ★★ 兜底成功把主路失效藏住了(2026-11-26,静默失败的第十种变体)

实测 **07:06~08:37 连续 10 轮**记录都是 `[浏览器兜底]`,每轮 60~90 条 ——
链路看着健康,**协议路却每轮都 `SESSION_EXPIRED`**。查明:库里的 jar `_m_h5_tk`
停在 **11-19**(166 小时前)。浏览器路根本不读那份 jar(登录态在档案里),所以**它救不了协议路**,
而它的成功又让人以为"闲鱼是好的"。

⇒ **凡是"主备双路"的地方,备用路成功时必须回答一句「主路现在到底行不行」**,
否则备路会长期掩盖主路失效(与第九种变体"整批回滚只留一条 WARN"同族:
都是**成功/正常的信号把失败盖住**)。

修法:回落浏览器**跑通**之后,也把档案里那份(必然新鲜的)jar 导给协议路;
与过验证那条路共用 `_write_jar_if_complete` 的完整性闸(`xianyu_cookie_missing`),
**缺 `unb`/`cookie2` 一律不覆盖**。

⚠️ **冷却与自愈的时间关系**:`tenant_base.verify_cooldown_active` 原本只按最近一条
风控 marker 算指数退避(实测 09:08 触发后 09:38/10:09/10:30 三轮全空转,冷却 120 分钟)。
现在多一条:**marker 早于「最后一次真过完验证」⇒ 那条 marker 作废**。
判据是**比时间**,不是"解过就放行" —— 解完之后**又撞上**的风控照旧冷却,否则就成了连拖
(每次拖动都是一次风控输入)

## 6. 出问题时的排查顺序(照这个走)

```
闲鱼采集没数据
  ├─ 运行记录 `[协议]` + 0 条      → 可能真没货;换个词再看
  ├─ 运行记录 `[浏览器兜底]`       → **协议失败了**,日志里有 `闲鱼纯协议失败(kind)`
  │      └─ kind=XianyuRateLimit(被挤爆) → **cookie 过期了** → 重跑导出工具
  │      └─ kind=XianyuVerify(滑块)      → 自动过验证也没成 ⇒ 看异常里的 `reason`:
  │            `handle_not_found` → 验证框换了形态(拼图/点选),跑
  │                                 `python scripts/xianyu_slider.py --probe` 抓 DOM 再补选择器
  │            `search_blocked`   → 拖过去了但平台仍拦(换出口/等更久,别连拖)
  │            `drag_failed`      → 鼠标动作被环境吞了(窗口最小化等),看 `data/_xianyu_slider_probe/`
  │      └─ kind=XianyuCookieExpired     → 令牌坏了 → 重跑导出工具
  ├─ `cookie_incomplete(缺 unb/cookie2)` → 库里那份 jar 不完整 → 重跑导出工具
  ├─ 深采运行记录 `partial` + `cookie_expired`
  │      → 详情接口登录态失效(搜索可能仍正常,那是不同的接口)
  │      → 重跑 `python tools/xianyu_export_cookie.py` 导出整套 jar
  ├─ 深采运行记录 `partial` + `all_detail_failed(n/m)`
  │      → 这一轮 m 个商品**全部**抓不到(个别解析问题不会全灭,多半是风控前兆)
  │      → 先看是不是滑块/WAF 的开头迹象,再考虑换出口
  └─ 详情/行情一直不更新           → 检查**深采是否与搜索同路**(§1)
```

⚠️ **`saved == 0` 不许记 success**(2026-11-26 修正):11-19 12:55 ~ 11-26 02:31
连续 **15 轮「success + items=0」**,把行情停摆藏了整整 7 天。现在的判据是:
**有该抓的(`todo` 非空)而一条都没抓成 ⇒ `partial` + 非空 reason**。
用 `partial` 而不是 `failed`,是因为后者不满足 `xianyu_deep_due`,会让每轮搜索都
重新空打 10 次详情、反而加重风控。

**别做的事**:改签名(= 它本来是对的)、换 UA、换出口、反复重试。
§3 那张表已经把这四条逐一排除过了。
