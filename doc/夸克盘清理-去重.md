# 夸克盘清理:跨目录重复 + 别人的引流文件

> 2026-10-08 建,2026-10-10 补「多轮收敛」。代码:`app/services/quark_dup.py`(判据)+
> `app/services/quark_dup_cache.py`(扫描快照)+ `scripts/quark_dup_{report,apply}.py`。

## 要解决什么

盘上有**一堆「家」目录**:`redian监听`、`redian监听_0913`、`redian监听_0920`…(2026-10-10 实测 **19 个**,
其中 6 个带 `_2` 后缀 —— 同一天建了两次)。每换一次家,**同一个资源的文件就又存一份**
(查重是按目录做的,换了目录就一个都认不出来)。

⇒ 要做的:**跨家去重**(同名 + 同大小视为同一份,留**最新在用的那个家**里的那份),
外加清掉**别人的引流文件**(导流到别的网盘/加群的广告文件、二维码…)。

## 怎么用

```bash
python scripts/quark_dup_report.py            # 只读,出计划(默认只清 10 月的账)
python scripts/quark_dup_report.py 10         # 同上,显式指定 MMDD 前缀
python scripts/quark_dup_apply.py             # 再看一遍计划(dry-run,一个字节都不删)
python scripts/quark_dup_apply.py --yes       # 真删 —— **进回收站**,可捞回
python scripts/quark_dup_apply.py --yes --max 5   # 先小批试
```

## 判据(在 `classify()` 里,是纯函数,可离线测)

| 情况 | 处理 |
|---|---|
| 名字命中**强模式**(名字本身就是"下载/加群指令") | **删** |
| 名字命中**弱模式**(含 必看/教程/注意/截图…) | **只报告,不删** —— 见下 |
| 跨 **≥2 个家**、且 ≥1 MiB | **删**,留**最新在用的那个家**里的那份 |
| 我方**已发出的分享链**指着的 fid / 名字 | **永不删**(删了 = 已发出的链接变"已失效") |
| 我们的宣传简介 | **永不删** |

⚠️ **弱模式为什么只报告**:它在这份盘上**逻辑失效** —— 同一份资源本来就被重复存到多个家,
于是包里几乎每个文件都"横跨多个家",那条判据退化成"名字里带『注意』就删"。
实测误判过 `高中英语151组最容易拼错的单词，考场上一定要注意！.docx` 这类**真学习资料**,
而这一类总共只有 269 MiB —— **省不到空间却会误删资源** ⇒ 降级成"待确认",由人判。

## 扫描要多久(2026-10-10 实测)

**一个家 ≈ 728 次 `list_dir` ≈ 10.7 分钟**(`list_dir` 每次约 1.2 秒)。
19 个家全扫完 ≈ **3.4 小时**。而 `QUARK_CLEANUP_BUDGET` 默认 2500
⇒ **一轮只能扫完约 3 个家**。

## ★ 多轮收敛(2026-10-10 新增)

**以前**:扫不完 ⇒ 什么都不留 ⇒ 下一轮又从头发起,永远卡在同一处。

**现在**:扫完的家写进快照 `data/quark_dup_cache.json`(原子替换),
下一轮**直接复用**;没排上的家记进 `remaining_homes`,**接着扫**。
⇒ 重复跑同一条命令即可,6~7 轮收敛完 19 个家。

⚠️⚠️ **这条路有个硬前提:两次调用之间的间隔必须小于 TTL。**
2026-10-15 实测踩到了它 —— `build_plan` 的默认 TTL 是 **8h**,而**定时作业是每天 04:20 一轮**
⇒ 每轮开始时上一轮的快照**全已过期** ⇒ 每轮从零重扫、在**同一处**撞预算、留下**同样几个**家
⇒ `complete` 恒 False ⇒ 护栏「没扫完就拒绝删」**天天生效**:
**夸克连着三天一个文件都没删**(10-12 / 10-13 / 10-14),而运行记录里那三天**一字不差**
(`已扫19个家,还差9个`)—— 一个"设计成会收敛"的循环,数字却**纹丝不动**。
⇒ 修法:TTL 改为**可配**、默认 **48h**(`PAN_AUTO_CLEAN_QUARK_TTL_HOURS`),
并让**作业显式传进来**(配置写了没人传 = **空转**,本仓为这个栽过:`xhs_sign_x_rap` 空转三天)。
⇒ 同时把"**为什么重扫**"记进运行记录:`build_plan` 现在返回 `cache_miss`
(`{"stale": 19}` = 快照过期 ⇒ **该改 TTL**;没有 `stale` 才是预算不够 ⇒ **该加预算**)。

```
扫了 19 个家、… 次 API 调用(本轮复用快照 12 个家 / 新扫 3 个;快照共 15 个家)
   ⏳ 还差 4 个家没扫(其中 0 个扫了一半):redian监听_0928、…
```

### 安全边界(这份快照会参与"删文件"的判据,所以每条都是故意设计的)

1. **TTL(默认 48 小时,`PAN_AUTO_CLEAN_QUARK_TTL_HOURS`)**:过期的家**重扫**,不吃旧数据。
   ⚠️ **它必须大于"两次调用之间的间隔"** —— 短于间隔的 TTL 会让这层缓存**永远不起作用**
   (2026-10-15 那次"三天一字不差"的事故,见上面「多轮收敛」那段);
2. **`complete` 要求"所有家都有有效数据"且"没撞预算"**。只要有一个家没扫到,
   重复数就会**算少** ⇒ "只在一个家里"变成假判断 ⇒ **执行器默认拒绝删**;
3. ⚠️ **危险方向**:快照说"某文件在 A、B 两家都有",而其实 A 那份已经没了 ⇒ 会删掉**唯一的副本**。
   兜底两层:① TTL 限窗口;② **删除永远进回收站**(`to_recycle=True`);
4. **删过东西的家立刻作废**(`drop_homes`)—— 那些家的内容变了,旧快照不再代表现状;
5. **残缺数据是安全的**:漏扫只会让重复看起来更少 ⇒ 倾向于**不删**(漏删,不是误删)。

### `--depth` 怎么选

`depth=2` 是默认,**别改成 1 来"加速"**:同一个家实测 `depth=1` 只看到 **491** 个文件,
`depth=2` 看到 **4953** 个 —— **差 10 倍**,因为资源多在 `家/资源名/子目录/文件` 这一层。
漏扫只会漏删(安全),但清不干净。**正路是保持 depth=2 + 多跑几轮。**

  **零 API 调用**),只看**资源本体(≥1MiB)**那 9,375 条:

  | 判据 | 跨家重复的"东西" | 落在重复里的条目 |
  |---|---|---|
  | **`(名字, 大小)`** | **17 种** | 58 条(**0.6%**) |
  | `core_resource_name`(**不问大小**) | 85 种 | 963 条(10.3%) |
  | **`(core_resource_name, 大小)`** | **18 种** | 62 条(**0.7%**) |

  ⇒ **所以「19 个家」是"命名/组织"问题,不是"重复占用"问题**:
  `_ensure_dir` 当年每次 fid 缓存丢失就新建一个家,而**新家接的是新转存**
  ⇒ 旧家里是**更早的资源**,不是同一份的副本。根因已修(**不再新增**),
  剩下的旧家**就是我们的库**,不该为"整洁"去动它。
  ✅ **只有 4 个是真空家**(`_0918_2` / `_0920` / `_0928_2` 快照 0 条、`_0927` 只有 1 条且
  无独占)⇒ 真要动手只动这几个。
  ⚠️ **残留的不确定(如实记)**:快照是 40~118 小时前的;而且「**改了名、大小也变了**」的
  同一份资源,靠 `(名字,大小)` / 名字归一化**都判不出来** —— 那需要内容哈希,
  现状给不了。所以这条结论是"**按现有判据,旧家几乎全是独占**",不是"绝对没有重复"。

## ⚠️ 2026-10-10 踩到的一个**危险不一致**(已修)

`report` 与 `apply` 两个脚本的**默认清理范围原本不一样**:

| 脚本 | 原本的 `mmdd_prefix` | 含义 |
|---|---|---|
| `quark_dup_report.py 10` | `"10"` | 只清 **10 月**的家 |
| `quark_dup_apply.py` | **`""`(没有这个参数)** | **所有月份** |

差的 70 倍就是"10 月"与"全部月份"。

**修法**:`apply` 加上 `--month`(默认 `"10"`,与 report 同口径),并在执行时**大声打印范围**。
**教训**:"用来判风险的报告"和"真正动手的执行器"**必须同范围** ——
否则人按报告做的判断,执行时全不作数。这是比"某个判据写错"更隐蔽的一类错,
因为它两边**各自都是对的**。

## ★★ 2026-11-13:清理原来**只扫最空的那个号**(连挂 8 天 `计划0 删0`)

### 现象

`runs` 里 `pan_auto_clean` 从 **11-05 到 11-12** 每天都记着同一句:

```
夸克 扫19 计划0 ... 删0
```

看着像"扫了 19 个家、确实没重复"。**实际不是** —— 现场查两个号:

| 账号 | 池里 `last_ratio` | 盘上的"家" |
|---|---|---|
| 夸克2 | 0.0568(最空) | **1 个**(`redian监听`) |
| 夸克1 | **1.2327(123%,超额)** | **19 个** |

所以那 19 是我**看错了**:`扫19` 里的 19 是**配置里的家数上限**一类的数,
真正被扫的号只有 1 个家。而**该清的 1 号从来没被扫过**。

### 根因

`clean_quark` 取凭据用的是 `pan_accounts.cookie_for()` —— 它返回**最空的那一个**
(这个语义是给**转存**定的:写要挑最空的盘;清理不是)。于是:

> 越满的号越需要清 → 越满 ⇒ `last_ratio` 越大 ⇒ `usable_hint` 越大 ⇒ **越排不到**
> ⇒ **永远不清理** ⇒ 永远满。

是个**正反馈**:池子的择一顺序与清理的目的**正好相反**。

### 修法

`clean_quark` 改为按池**遍历所有账号**(`pan_accounts.refs_for`),逐号:

- 各自的 `ScanCache` 与 `quark_fid_store` 走新增的 `pan_accounts.scoped_path(base, cookie_key)`
  **按 `cookie_key` 分家** —— 两个号都有 `redian监听` 这个家但 **fid 不同**,
  共用一份快照会 `FID_CHANGED` 每轮互废(见 `pan_discovery._fid_store_for` 的同一条)。
- **单号失败不挡其余**(`QuarkAuthError` / 扫描异常各自记进 `errors`);
- 硬上限 `pan_auto_clean_max_deletes` 仍然**三盘共用**,并且在账号之间**递减**。

运行记录改成**每号一段**,这是这次最要紧的产出:

```
夸克 扫21 计划0 账号2 (夸克2 扫1 计划0 删0) (夸克1 扫19 计划0 删0)
```

没有这一段的话,「1 号扫了 19 个家但 0 重复」与「2 号压根没被扫」**长得一模一样**
—— 正是这个盲点让 bug 活了 8 天。

### 顺带修掉的一个真 bug:`AccountRef` 不可哈希

`refs_for` 过滤百度死号时写了 `r not in {a[0] for a in alive}`,而 `AccountRef`
是 **dataclass(带 list 字段)⇒ 不可哈希** ⇒ 池里只要有 **≥2 个百度号**就 `TypeError`。
`cookies_for` 的调用方普遍把异常吞成"没凭据",于是表现成「盘满 / 没配账号」。

- 改成按 `cookie_key` 比(它就是账号身份)。
- **守卫为什么没抓到**:`tests/test_pan_accounts_alive.py` 原来用的是一个普通类 `_R`
  (按 identity 可哈希)当替身 —— **替身与真类型不是一回事**。
  现补 `test_真AccountRef也要能滤死号`,用真的 `AccountRef` 跑一遍
  (同一个坑:memory `test-double-drift-and-safe-editing`)。

### 验证

`python -m pytest tests/test_quark_cleanup.py tests/test_pan_accounts_alive.py -q` ⇒ 48 passed。
`test_清理要扫遍池里的每个号_且各自用各自的快照` 已用「只取 `pool[:1]`」的旧行为**验红过**
(报 `没扫遍池:['ck-quark#2']`)。

## 简介目录的日志必须带号名(2026-11-16)

**症状**:一轮 dry-run 的日志里同时出现

```

...
"intro_protected": 2
```

前两句说「没护住」,最后一行又说「护了 2 个」—— 看着像代码自相矛盾。

**真实情况**(逐号实测):

| 号 | 盘上有 `监听宣传` 目录吗 | 本轮简介保护 |
|---|---|---|
| `quark`(夸克1,19 个家) | 有(`resolve_named_dir` 命中) | **2 个文件** |
| `quark#2`(夸克2,1 个家) | **没有**(搜「监听宣传」「宣传」均 0 条) | **0** |

`pan_auto_clean.clean_quark` 是**逐号**跑 `build_plan` 的,两句话说的是**不同的号**,
只是日志里没有号名,并排看就成了矛盾。

**修法**:`collect_intro_protect` / `refresh_protect` / `build_plan` 新增 `label` 参数,
`clean_quark` 把账号标签传下去,两条 warning 都带上 `(号名)`。
⚠️ **不能靠 `qt` 自己猜**:`QuarkTransfer` 只有一个 cookie 串、**没有账号身份**,
从它身上取 `cookie_key` 永远为空(第一版就是这么写的,测试没测出来 —— 补了显式传参的用例)。

**顺带记一条环境陷阱**:`C:/Program Files/Git/监听宣传` 是 **Git Bash(MSYS)** 把
`.env` 里的 `/监听宣传`(夸克**盘内**目录名)当本地路径转换出来的,生产(cmd 启动)不受影响。
判据:`env -u pan_intro_quark_dir python -c "from config.settings import get_settings; print(get_settings().pan_intro_quark_dir)"`
应回 `/监听宣传`。而 `resolve_named_dir` 恰好会 `strip('/').split('/')[-1]`,所以**即使被污染也能找到目录** ——
这也是为什么同一个值在一号能护住、在二号护不住。

### 遗留

**夸克2 盘上没有「监听宣传」简介目录**(2026-11-16 实测)。它是活跃的转存目标,
但转到它名下的资源**不会带宣传简介**。这属于盘运营配置,未在本次改动范围内。

## ★★ 2026-11-17:空间根本不在那 19 个家里,而在**根目录**(清出 17.78 TiB)

> 用户口径:「把一些**重复**和**很老旧没人推**的删了」。

### 先纠正一个错判

前面的章节都在讲 `redian监听_*` 这 19 个家。实测它们的**全部内容**只有:

| 项 | 数 |
|---|---|
| 19 个家的顶层条目 | **1044** |
| `quark_dup_cache` 递归文件合计 | **5028 GiB(≈5 TiB)** |
| 配额 `use_capacity` | **106.01 TiB** |
| ⇒ 家只占配额 | **约 5%** |

而根目录 `pdir_fid=0` 有 **250540** 个顶层条目(`file_type=1` 文件 **208050** / 目录 **42490**)。

⇒ `pan_auto_clean`(只扫两层)与 `pan_retention`(只按监控源)天天 `计划0`,
**不是判据保守,是视野之外** —— 它们从来没看过根目录。

### 三个判据(每条都有实测依据)

**① 重复** = `_pkg_base(文件名主段)` + 扩展名 + 字节数 相同。

- 按 `size:desc` 前 10200 条里有 **8830 份带 `(N)` 后缀**;
- 且**没有一份不带后缀的原件** ⇒ 夸克重名 saveas **只加后缀**,原件在别处或已删;
- 典型:`超凡蜘蛛侠2.The.Amazing.Spider-Man.2.2014.2160p.mp4` **同一资源 10 份**、
  `Spider-Man.No.Way.Home.2021.2160p.REMUX` 3 份 × 64.5 GiB。

**② 很老旧** = `l_created_at`,实测 **573~849 天**。

⚠️⚠️ **别用 `created_at`**:它是**操作时间**,全部挤在 2026-08-13/14 的 **28 个时刻**
(3453 条同一秒)—— 拿它判新旧会得出「全都不老」,一条都删不掉。
判据:`l_created_at` = 真入库时间(2024-07-21 等),`created_at` = 最近一次被触碰。

**③ 没人推** = 三条**同时**不成立才算:

1. fid 不在 `pan_owned_shares.first_fid`(按 `account_key`);
2. 整名**不等于**任何分享标题;
3. 整名不在 `push_ledger.title`。

实测 300 份抽样命中 **0**。

⚠️⚠️ **子串匹配全是假阳性**:分享标题里有 `'4'`、`'9'`、`'荒'` 这种单字符标题,
`any(t in name for t in titles)` 会命中**每一个带数字的文件名**(抽样 293/300)。**只认整名相等**。

### 执行:8 轮,窗口每轮前移

接口 `_page` 到 **103**(`_size=100`)就恒回 `61004` —— 这是**窗口上限**,不是限流:

- 换 `size:asc` / `file_name:asc` / `l_created_at:desc` 一样卡在 10200;
- 退避 20/35/50/65/80 秒也过不去。

所以**每轮删完必须重新扫**:删掉的条目会让窗口前移,下一轮露出下一批。

| 轮 | 待删 | 配额 |
|---|---|---|
| 1 | 9022 份 / 10865 GiB | 106.011 → 95.400 TiB |
| 2 | 7804 份 / 3359 GiB | → 92.121 |
| 3 | 6785 份 / 1731 GiB | → 90.430 |
| 4 | 6036 份 / 994 GiB | → 89.459 |
| 5 | 5401 份 / 552 GiB | → 88.921 |
| 6 | 4943 份 / 340 GiB | → 88.595 |
| 7 | 4570 份 / 236 GiB | → 88.364 |
| 8 | 4251 份 / 163 GiB | → 88.199 |
| **合计** | **48766 份 / 17.78 TiB** | **ratio 1.2327 → 1.0256** |

每组**至少留 1 份**(留 `l_created_at` 最老那份 —— 内容同,最老的最可能已被索引),
删除全部 `to_recycle=True`。

**抽样复核**:应删的 fid 全部 `21001 file not found`;保留的那份全部仍在。

### ★ 顺带证伪「回收站占配额」

删一个 **597.19 MiB** 文件后,`use_capacity` **当场 -597.19 MiB**(分毫不差)。

⇒ **回收站不占配额**。所以:

- 那 **16.35 TiB / 49781 条**深回收站**早就被释放了**,不是空间的去向;
- **清空深回收站不会多出空间**,不必去做(而且它不可逆)。

### 顺手修掉的一个真缺陷:目录型分享保护失效

`quark_dup.protected_fids()` 返回的 `prot_names` 只收 `file_num > 1` 的分享标题
(6335 条分享 → **393 个标题**),而 `classify()` 拿 `prot_names` 去比**文件名**。

实测 `first_fid` 里 **2836/2890(98%)是目录 fid**,只有 54 个落在扫描到的文件里
⇒ **目录型分享跨家重复时,老家那份会被删,已发出的分享链立刻「已失效」**。

`build_package_plan()` 里 `protected` 只比 `fids & prot_fids`(`_walk` 返回的是**里面文件**的 fid),
**目录自己的 `mfid` 不比** —— 同一缺陷的第二个入口。

**修法**:

- 新增 `_top_dir_of(path)`:取 `家/资源目录/…` 的二级名字;
- `classify()` 在名字级保护之后加**目录级保护**:`_top_dir_of(c[path]) in prot_names` ⇒ 整组 `protected_left`;
- `build_package_plan()` 补 `mfid in prot_fids`。

**量化**(真实快照 + 真实台账,离线):修复前会删 38 份 / 1.23 GiB,修复后 **0 份 / 0.00 GiB**。
⇒ 所谓「跨家重复 17 组 / 1.29 GiB」其实**全部落在受保护目录里,本来就不该删**。

### 新增脚本

```bash

python scripts/quark_root_dedupe.py --yes         # 真删(回收站)
python scripts/quark_root_dedupe.py --rescan      # 重新扫根目录(每轮都要加)
python scripts/quark_prune_old.py                 # 家里顶层目录:重复+老旧+没人推
```

### 还剩下的

配额 `88.199 / 86.000 TiB`,**仍超 2.2 TiB**(ratio 1.0256)。
剩下的空间不在「重复副本」里 —— 每组的第 1 份都是真资源:

- 根目录里 10200 个目录中 **10161 个是空壳**(`include_items=0`),不占空间;
- 真正的内容在**根目录的散文件**里(教资/考研课件,大量是**同一门课的不同章节**,
  名字不同、大小不同 ⇒ 判据认不出重复);

## ★★★ 2026-11-18:配额的大头从来不在根目录 —— `pdir_fid` 为空字符串 才是「全盘」

### 前八轮清理为什么只清到皮毛

`scripts/quark_root_dedupe.py` 扫的是 **`pdir_fid` 为 0(根目录)**,而根目录的
`size:desc` 窗口**只有 10200 条**(`_page` 到 103 就 `61004`;换偏移量、换排序键
都绕不过)。根目录实际有 **201727** 条 ⇒ **约 19 万条从来没被看过**。
2026-11-17 清掉的 17.78 TiB 全部来自那 10200 条窗口。

### 真正的入口:把 `pdir_fid` 传成**空字符串**

| 请求 | `_total` | 含义 |
|---|---|---|
| `pdir_fid` 为 0 | 201727 | 根目录的**直接**子项 |
| `pdir_fid` 为空字符串 + `file_type=1` | **1094602** | 全盘**所有文件** |
| `pdir_fid` 为空字符串 + `file_type=0` | **148393** | 全盘**所有目录** |

全盘按 `size:desc` 前 10000 个文件合计 **34.02 TiB**,而这批文件**没有一个**
出现在根目录那 10200 条窗口里。`redian监听_*` 家(约 5 TiB)+ 根目录(约 3 TiB)
加起来才 8 TiB —— **88 TiB 里约 80 TiB 藏在这个全盘视图里**。

⚠️ `file_ext` 在 `pdir_fid` 为空字符串 维度**会被忽略**(传什么扩展名都回同一个 `_total`),
所以「按扩展名分窗」那招只在**根目录**有效,不能用来覆盖全盘。

### 判据与结果

两条纯本地计算:

1. **同名 + 同字节数**(≥1 GiB)⇒ 1501 组、多余 2704 份;
2. **父目录内「(文件名, 字节数) 集合」完全相同**⇒ 1.56 TiB(整套课程/剧集被另存多份)。

去重后出计划 **2703 份 / 7.42 TiB**,执行结果:

```
配额  88.199 TiB → 80.779 TiB   (-7495.8 GiB = 7.32 TiB)
ratio 1.0256    → 0.9393        ★ 首次降到配额线以下
```

### 为什么「同名同字节数」可以信

抽查 `【107】2027年白鹭申论扎马步特训营`:四个父目录里各存一份,每份
**173.65 GiB / 20 集 / 前 3 个文件名逐字一致** —— 是「整套课程被重复另存 4 份」,
不是同名巧合。另有 3 组是**同一个父目录内**的重复
(`超凡蜘蛛侠2.The.Amazing.Spider-Man.2.2014.2160p.mp4` 等)。

### 目录体积没有捷径

夸克的目录 `size` 字段**恒为 0**,`file/dir_size` / `file/statistic` /
`capacity/stat` **全部返回 `null`**。只能递归:

- `include_items` 是**直接子项数**(根目录 42490 个目录里只有 139 个非零)
  ⇒ **为 0 的直接跳过**,否则 `redian监听_1007` 那种 638 个子目录的树要跑一小时;
- 实测单家:顶层只有 4.7 GiB,**递归下去 15~144 GiB** —— 用顶层值估体积会差一个量级。

## ★★ 2026-11-18 第二轮:判据漏了「副本后缀」,又清出 1.96 TiB

第一轮只认**名字完全相同**。但同一份文件被重复下载/保存时,第二份会被改名为
`课件(1).mp4`,第三份 `课件(2).mp4` —— 名字不同、**字节数完全相同**,老判据整批漏掉。

实测这批有 **822 组 / 883.2 GiB**,其中 70% 是 `Di5.x_…zip`(夸克客户端安装包)

### 判据怎么扩的(`strip_copy_suffix`)
