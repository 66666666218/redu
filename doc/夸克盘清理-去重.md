# 夸克盘清理:跨目录重复 + 别人的引流文件

> 2026-10-08 建,2026-10-10 补「多轮收敛」。代码:`app/services/quark_dup.py`(判据)+
> `app/services/quark_dup_cache.py`(扫描快照)+ `scripts/quark_dup_{report,apply}.py`。

## 要解决什么

盘上有**一堆「家」目录**:`redian监听`、`redian监听_0913`、`redian监听_0920`…(2026-10-10 实测 **19 个**,
其中 6 个带 `_2` 后缀 —— 同一天建了两次)。每换一次家,**同一个资源的文件就又存一份**
(查重是按目录做的,换了目录就一个都认不出来)。

⇒ 要做的:**跨家去重**(同名 + 同大小视为同一份,留**最新在用的那个家**里的那份),
外加清掉**别人的引流文件**(导流到别的网盘/加群的广告文件、二维码…)。

## 怎么用

```bash
python scripts/quark_dup_report.py            # 只读,出计划(默认只清 10 月的账)
python scripts/quark_dup_report.py 10         # 同上,显式指定 MMDD 前缀
python scripts/quark_dup_apply.py             # 再看一遍计划(dry-run,一个字节都不删)
python scripts/quark_dup_apply.py --yes       # 真删 —— **进回收站**,可捞回
python scripts/quark_dup_apply.py --yes --max 5   # 先小批试
```

## 判据(在 `classify()` 里,是纯函数,可离线测)

| 情况 | 处理 |
|---|---|
| 名字命中**强模式**(名字本身就是"下载/加群指令") | **删** |
| 名字命中**弱模式**(含 必看/教程/注意/截图…) | **只报告,不删** —— 见下 |
| 跨 **≥2 个家**、且 ≥1 MiB | **删**,留**最新在用的那个家**里的那份 |
| 我方**已发出的分享链**指着的 fid / 名字 | **永不删**(删了 = 已发出的链接变"已失效") |
| 我们的宣传简介 | **永不删** |

⚠️ **弱模式为什么只报告**:它在这份盘上**逻辑失效** —— 同一份资源本来就被重复存到多个家,
于是包里几乎每个文件都"横跨多个家",那条判据退化成"名字里带『注意』就删"。
实测误判过 `高中英语151组最容易拼错的单词，考场上一定要注意！.docx` 这类**真学习资料**,
而这一类总共只有 269 MiB —— **省不到空间却会误删资源** ⇒ 降级成"待确认",由人判。

## 扫描要多久(2026-10-10 实测)

**一个家 ≈ 728 次 `list_dir` ≈ 10.7 分钟**(`list_dir` 每次约 1.2 秒)。
19 个家全扫完 ≈ **3.4 小时**。而 `QUARK_CLEANUP_BUDGET` 默认 2500
⇒ **一轮只能扫完约 3 个家**。

## ★ 多轮收敛(2026-10-10 新增)

**以前**:扫不完 ⇒ 什么都不留 ⇒ 下一轮又从头发起,永远卡在同一处。

**现在**:扫完的家写进快照 `data/quark_dup_cache.json`(原子替换),
下一轮**直接复用**;没排上的家记进 `remaining_homes`,**接着扫**。
⇒ 重复跑同一条命令即可,6~7 轮收敛完 19 个家。

⚠️⚠️ **这条路有个硬前提:两次调用之间的间隔必须小于 TTL。**
2026-10-15 实测踩到了它 —— `build_plan` 的默认 TTL 是 **8h**,而**定时作业是每天 04:20 一轮**
⇒ 每轮开始时上一轮的快照**全已过期** ⇒ 每轮从零重扫、在**同一处**撞预算、留下**同样几个**家
⇒ `complete` 恒 False ⇒ 护栏「没扫完就拒绝删」**天天生效**:
**夸克连着三天一个文件都没删**(10-12 / 10-13 / 10-14),而运行记录里那三天**一字不差**
(`已扫19个家,还差9个`)—— 一个"设计成会收敛"的循环,数字却**纹丝不动**。
⇒ 修法:TTL 改为**可配**、默认 **48h**(`PAN_AUTO_CLEAN_QUARK_TTL_HOURS`),
并让**作业显式传进来**(配置写了没人传 = **空转**,本仓为这个栽过:`xhs_sign_x_rap` 空转三天)。
⇒ 同时把"**为什么重扫**"记进运行记录:`build_plan` 现在返回 `cache_miss`
(`{"stale": 19}` = 快照过期 ⇒ **该改 TTL**;没有 `stale` 才是预算不够 ⇒ **该加预算**)。

```
扫了 19 个家、… 次 API 调用(本轮复用快照 12 个家 / 新扫 3 个;快照共 15 个家)
   ⏳ 还差 4 个家没扫(其中 0 个扫了一半):redian监听_0928、…
```

### 安全边界(这份快照会参与"删文件"的判据,所以每条都是故意设计的)

1. **TTL(默认 48 小时,`PAN_AUTO_CLEAN_QUARK_TTL_HOURS`)**:过期的家**重扫**,不吃旧数据。
   ⚠️ **它必须大于"两次调用之间的间隔"** —— 短于间隔的 TTL 会让这层缓存**永远不起作用**
   (2026-10-15 那次"三天一字不差"的事故,见上面「多轮收敛」那段);
2. **`complete` 要求"所有家都有有效数据"且"没撞预算"**。只要有一个家没扫到,
   重复数就会**算少** ⇒ "只在一个家里"变成假判断 ⇒ **执行器默认拒绝删**;
3. ⚠️ **危险方向**:快照说"某文件在 A、B 两家都有",而其实 A 那份已经没了 ⇒ 会删掉**唯一的副本**。
   兜底两层:① TTL 限窗口;② **删除永远进回收站**(`to_recycle=True`);
4. **删过东西的家立刻作废**(`drop_homes`)—— 那些家的内容变了,旧快照不再代表现状;
5. **残缺数据是安全的**:漏扫只会让重复看起来更少 ⇒ 倾向于**不删**(漏删,不是误删)。

### `--depth` 怎么选

`depth=2` 是默认,**别改成 1 来"加速"**:同一个家实测 `depth=1` 只看到 **491** 个文件,
`depth=2` 看到 **4953** 个 —— **差 10 倍**,因为资源多在 `家/资源名/子目录/文件` 这一层。
漏扫只会漏删(安全),但清不干净。**正路是保持 depth=2 + 多跑几轮。**

  |---|---|---|
  | **`(名字, 大小)`** | **17 种** | 58 条(**0.6%**) |
  | `core_resource_name`(**不问大小**) | 85 种 | 963 条(10.3%) |
  | **`(core_resource_name, 大小)`** | **18 种** | 62 条(**0.7%**) |

  `_ensure_dir` 当年每次 fid 缓存丢失就新建一个家,而**新家接的是新转存**
  ⇒ 旧家里是**更早的资源**,不是同一份的副本。根因已修(**不再新增**),
  剩下的旧家**就是我们的库**,不该为"整洁"去动它。

  无独占)⇒ 真要动手只动这几个。
  ⚠️ **残留的不确定(如实记)**:快照是 40~118 小时前的;而且「**改了名、大小也变了**」的
  同一份资源,靠 `(名字,大小)` / 名字归一化**都判不出来** —— 那需要内容哈希,
  现状给不了。所以这条结论是"**按现有判据,旧家几乎全是独占**",不是"绝对没有重复"。

## ⚠️ 2026-10-10 踩到的一个**危险不一致**(已修)

`report` 与 `apply` 两个脚本的**默认清理范围原本不一样**:

| 脚本 | 原本的 `mmdd_prefix` | 含义 |
|---|---|---|
| `quark_dup_report.py 10` | `"10"` | 只清 **10 月**的家 |
| `quark_dup_apply.py` | **`""`(没有这个参数)** | **所有月份** |

**教训**:"用来判风险的报告"和"真正动手的执行器"**必须同范围** ——
否则人按报告做的判断,执行时全不作数。这是比"某个判据写错"更隐蔽的一类错,
因为它两边**各自都是对的**。

## ★★ 2026-11-13:清理原来**只扫最空的那个号**(连挂 8 天 `计划0 删0`)

### 现象

`runs` 里 `pan_auto_clean` 从 **11-05 到 11-12** 每天都记着同一句:

```
夸克 扫19 计划0 ... 删0
```

看着像"扫了 19 个家、确实没重复"。**实际不是** —— 现场查两个号:

| 账号 | 池里 `last_ratio` | 盘上的"家" |
|---|---|---|
| 夸克2 | 0.0568(最空) | **1 个**(`redian监听`) |
| 夸克1 | **1.2327(123%,超额)** | **19 个** |

所以那 19 是我**看错了**:`扫19` 里的 19 是**配置里的家数上限**一类的数,
真正被扫的号只有 1 个家。而**该清的 1 号从来没被扫过**。

### 根因

`clean_quark` 取凭据用的是 `pan_accounts.cookie_for()` —— 它返回**最空的那一个**
(这个语义是给**转存**定的:写要挑最空的盘;清理不是)。于是:

> 越满的号越需要清 → 越满 ⇒ `last_ratio` 越大 ⇒ `usable_hint` 越大 ⇒ **越排不到**
> ⇒ **永远不清理** ⇒ 永远满。

是个**正反馈**:池子的择一顺序与清理的目的**正好相反**。

### 修法

`clean_quark` 改为按池**遍历所有账号**(`pan_accounts.refs_for`),逐号:

- 各自的 `ScanCache` 与 `quark_fid_store` 走新增的 `pan_accounts.scoped_path(base, cookie_key)`
  **按 `cookie_key` 分家** —— 两个号都有 `redian监听` 这个家但 **fid 不同**,
  共用一份快照会 `FID_CHANGED` 每轮互废(见 `pan_discovery._fid_store_for` 的同一条)。
- **单号失败不挡其余**(`QuarkAuthError` / 扫描异常各自记进 `errors`);
- 硬上限 `pan_auto_clean_max_deletes` 仍然**三盘共用**,并且在账号之间**递减**。

运行记录改成**每号一段**,这是这次最要紧的产出:

```
夸克 扫21 计划0 账号2 (夸克2 扫1 计划0 删0) (夸克1 扫19 计划0 删0)
```

没有这一段的话,「1 号扫了 19 个家但 0 重复」与「2 号压根没被扫」**长得一模一样**
—— 正是这个盲点让 bug 活了 8 天。

### 顺带修掉的一个真 bug:`AccountRef` 不可哈希

`refs_for` 过滤百度死号时写了 `r not in {a[0] for a in alive}`,而 `AccountRef`
是 **dataclass(带 list 字段)⇒ 不可哈希** ⇒ 池里只要有 **≥2 个百度号**就 `TypeError`。
`cookies_for` 的调用方普遍把异常吞成"没凭据",于是表现成「盘满 / 没配账号」。

- 改成按 `cookie_key` 比(它就是账号身份)。
- **守卫为什么没抓到**:`tests/test_pan_accounts_alive.py` 原来用的是一个普通类 `_R`
  (按 identity 可哈希)当替身 —— **替身与真类型不是一回事**。
  现补 `test_真AccountRef也要能滤死号`,用真的 `AccountRef` 跑一遍
  (同一个坑:memory `test-double-drift-and-safe-editing`)。

### 验证

`python -m pytest tests/test_quark_cleanup.py tests/test_pan_accounts_alive.py -q` ⇒ 48 passed。
`test_清理要扫遍池里的每个号_且各自用各自的快照` 已用「只取 `pool[:1]`」的旧行为**验红过**
(报 `没扫遍池:['ck-quark#2']`)。

## 简介目录的日志必须带号名(2026-11-16)

**症状**:一轮 dry-run 的日志里同时出现

```

...

```

前两句说「没护住」,最后一行又说「护了 2 个」—— 看着像代码自相矛盾。

**真实情况**(逐号实测):

| 号 | 盘上有 `监听宣传` 目录吗 | 本轮简介保护 |
|---|---|---|
| `quark`(夸克1,19 个家) | 有(`resolve_named_dir` 命中) | **2 个文件** |
| `quark#2`(夸克2,1 个家) | **没有**(搜「监听宣传」「宣传」均 0 条) | **0** |

`pan_auto_clean.clean_quark` 是**逐号**跑 `build_plan` 的,两句话说的是**不同的号**,
只是日志里没有号名,并排看就成了矛盾。

`clean_quark` 把账号标签传下去,两条 warning 都带上 `(号名)`。

### 二、两处真缺陷(都验红过)

**① 原件被当成副本删(留的那份带后缀)**

`build_plan` 只按 `created` 排序取第一份当 `keep`。而**同一次批量转存的几份
时间戳完全相同** —— 实测 `超凡蜘蛛侠2.The.Amazing.Spider-Man.2.2014.2160p.mp4`
的原件、`(1)`、`(2)` 三份 `created` 都是 `1786689946501`,而 Python 的 `sorted`
是**稳定排序** ⇒ 谁当 `keep` 取决于输入顺序(快照里 `(1)` 恰好排在原件前面)。

实测旧计划 **8205 份里 6666 份(81%)的 `keep_name` 带着副本后缀**。

删仍然是安全的(`strip_copy_suffix` 把 `(1)`/`(2)` 剥成同一个 base),但
「**留最老的原件**」这个目标完全失效,而它还决定了回收站里按 `keep_name` 捞哪份。

⚠️ 我第一版把它归因成「`l_created_at` 常为 0 ⇒ 排序退化」,**是错的**:这 10200 条
里 `created` 一个 0 都没有(10200/10200 有值)。归因错了就会把用例写成
「时间戳全 0 时怎样」,而这个 bug 在**时间戳齐全且相等**时照样发生。

修法 —— **原件优先**,再比时间:

```python
g = sorted(g, key=lambda x: (x["name"] != base, x.get("created") or 0))
```

实测带后缀 6666 → **0**。对应的两个用例(`test_时间戳全为0时也要留不带后缀的原件`、
`test_原件的创建时间更晚也优先保留`)都**回退修复后验过红**。

**② 全盘视图有低端盲区(0.33~1.14 GiB)**

| 视图 | `pdir_fid` | `size:desc` 前 10000 条的**下限** |
|---|---|---|
| 全盘 | 空串 | **1.137 GiB** |
| 根目录 | `0` | **0.583 GiB** |

两个窗口**互相独立** ⇒ 0.33~1.14 GiB 这一段**只有根目录视图看得见**。而旧判据的
`quark_root_dup_plan_r2.json`(7804 份 / 3.36 TiB)**全部落在这一段**里。
只扫全盘 ⇒ 静默漏掉 2.16 TiB 的可回收重复。

修法:`VIEWS` 双视图取并集(全盘 7 个键 + 根目录 4 个键),实测
**96655 条 / 33.63 TiB**,根目录视图独有 **34822 条**:0.1~0.33 GiB 6324 个、
0.33~0.58 GiB 2518 个、0.58~1.0 GiB 1245 个。
守卫 `test_扫描入口必须同时有两个视图` 断言 `{p for _, p, _ in VIEWS} == {"", "0"}`。

### 五、删完必须重扫一次(窗口会前移)

删掉 2632 份之后再扫一遍,**又多出 298 份 / 149.9 GiB**:

```
第一轮  2632 份 / 1000.4 GiB   79.039 → 78.062 TiB
第二轮   298 份 /  149.9 GiB   78.064 → 77.917 TiB   ← 删后重扫才看得见
```

原因和第一轮那八次一样:`size:desc` 的窗口是**按现存条目排的**,删掉头部之后
下一批就露出来了。所以「一轮清完」不成立,**要跑两轮才算收敛**。
核对同样三层全过(自洽重叠 0 / keep 存活 80/80 / 体积 37/37)。

⚠️ 顺手记一个我自己写错的检查口径:我最初写「**原件被误删**」判据时用
`s(name) == name and s(keep_name) == keep_name` 去算,得出 **287** 条报警 ——
看代码才发现这 287 条是**同名原件分处不同目录**(`08高新技术.mp4` 在
`a25e31f8` 与 `b940f86c` 各一份),删一份留一份**完全正确**。
真正的危险项是「**删原件、留副本**」(`s(name)==name and s(keep_name)!=keep_name`),
实测 **0**。判据写错方向会把正常行为报成事故,和「子串匹配全是假阳性」同源。

### 六、「必须有不带后缀的原件」那道闸**误挡了真资源**(回归,已修)

**现象**:第四轮残留的旧输出里反复出现 `[85.2]--题型变上限积分(1..17).mp4` 十七份,
但计划里 0 条。顺着查下去发现这不是旧数据的问题,而是**判据本身的回归**。

**根因**:`build_plan` 里那道闸写成了「`base` 不在 `names` 里就整组跳过」:

```python
if base not in names:
    continue
```

它的原意是「全是 `(1)(2)` 副本 ⇒ 认不出原件 ⇒ 不删」。但**名字里自带编号的真资源**
也被它一刀切掉了 —— `42期预测3（2）.mp4` 两份**名字完全相同**、字节数完全相同,
`strip_copy_suffix` 把 `（2）` 当成副本后缀剥成 `42期预测3.mp4`,于是 `base` 不在
`names` 里 ⇒ 整组跳过。

⇒ **在加副本后缀判据之前,这些组本来是能正常去重的。这是上一轮引入的回归。**

**关键认识**:组内名字**完全相同**时,剥不剥后缀**根本不影响判断** ——
同名 + 同字节数就是同一份文件存了两遍,它叫「副本」还是「第 2 讲」都不改变这一点。
那道闸只该管**名字真的不一样**的情形。

**修法**:

```python
exact = len(names) == 1                  # 组内名字完全一致
if base not in names and not exact:
    continue                             # 只有「名字只差后缀」才需要原件才能判
```

**量化**(当前快照,≥0.1 GiB):

| | 组数 | 份数 | 体积 |
|---|---|---|---|
| 被闸误挡的组 | **21** | **28** | **25.06 GiB** |
| 其中「名字只差后缀、确实无原件」(仍应跳过) | 4 | 6 | 1.54 GiB |

修完重出计划,新放出 28 份,包含 `14.长期股权投资（2）.mp4`、`08.金融资产（3）.mp4`、
`44.千词计划·1000词精讲训练营（44）.mp4` 这类**名字自带课程编号**的真资源。

⚠️ **验收口径也要跟着改**:我最初用
`s(name)!=name and s(keep_name)!=keep_name` 查「删副本留副本」,报 **28 条** ——
但那 28 条全是**名字完全相同**的组(`name == keep_name`),根本不是两个不同的副本。
加上 `x["name"] != x["keep_name"]` 之后**真异常 0**。判据和验收口径必须同步改,
否则会把正常行为报成事故(这是**同一天第二次**栽在这个形状上)。
