# 公众号模块:反复出现的问题与防复发机制(2026-10-05)

> 这份文档不是"功能说明",而是**对着"同一个坑反复踩"建的**。
> 每条问题的写法统一为:**症状 → 历史实例(几次?)→ 根因 → 现在的强制手段(违反会怎样)**。
> 没有强制手段的,就不是"防复发",只是"说过了"。

---

## 一、A 类:**看起来成功,实则失败**

这是本仓最贵的一类 —— 它不会让人立刻发现,而是**让能力静默消失**,等发现时已经过了很久。

### A1. 失败只写日志、不推人 ⇒ 断了一周没人知道

**症状**:采集一切正常(`status=success`、`new=18`),但某一路能力早就没了。

**历史实例(至少 4 次)**:

| 时间 | 断的是什么 | 藏了多久 |
|---|---|---|
| 2026-09-29 ~ 10-05 | **精确阅读数**(`mp/articles` 被 `-2041` 拦) | **6 天**,近 3 天入库 162 篇、**有阅读数的 0 篇** |
| 2026-10-04 | `resource_presence` 注册着、trigger 正确,**六天一次没跑** | 6 天 |
| 多次 | `mp/articles` 失败"每进程只记一次 warning" | 只进 `data/app.log`,不推飞书 |
| 多次 | 采集源把限流吞成空结果 → `success(候选0)` | 看起来像"今天没资源" |

**根因**:失败路径**各自决定"要不要说"**,没有统一约定;而且"说"的默认落点是**日志**,
而日志**没人看**(14.7MB,还在涨)。

**现在的强制手段**:

1. **统一入口 `weread_budget.call()`** —— 被挡**永远是个显式信号**(抛异常),
   任何一条路都不可能再悄悄吞成空结果;
2. **`chain_health` 的「精确阅读数」专检** —— 查**库里的真值**(`read_num>0` 的占比),
   全丢报 🔴 **并直接给出修法**;这不是"补充说明",是**每天推管理群**的那份报告的一部分;
3. **"只写不读的计数等于没有"** —— `weread_cover_shelf_skipped` 曾只写不读,
   已加进 run detail(`shelf(... skip=… saved=N ...)`)。

### A2. 把责任甩给下游,而下游按它自己的判据是"成功"

**症状**:体检报 🟡「多半是正常空窗」,理由写的是"若那次续期也失败,续期作业会单独推飞书告警"
—— **而续期作业按自己的判据报的正是 `success`**。

**历史实例**:2026-10-05 的阅读数断供(上面那条的放大版)。

**根因**:判"活着没"和判"能用没"是**两件事**,而当时用前者的绿灯给后者背书。
续期的 success 只说明"换出了新 skey 且 shelf 能读",**不说明 `mp/articles` 能用**。

**现在的强制手段**:`chain_health` 的阅读数专检**直接查产出**(库里的 `read_num`),
不再经由任何中间层的 success 转述。

### A3. HTTP 200 但业务码是错

**症状**:`requests` 不抛异常,代码就当成功。

**历史实例**:B站 `code=-352`;微信读书 `errCode=-2012`;微博、知乎同理。

**根因**:HTTP 层与业务层是两套语义,只看 HTTP 就是把"服务端说不行"当成"行"。

**现在的强制手段**:所有客户端**必须显式检查业务码**(B站、`WereadAppClient`、微博源等都已加);
`WereadAppClient` 里 `errcode != 0` 一律抛,并**把 `-2010/-2012` 单列**。

### A4. 静默跳过已有行 ⇒ 数据悄悄丢

**症状**:同一篇内容,先入库的那次**不带阅读数**,后一次带精确值的**被当重复丢掉**。

**历史实例**:`_insert_new_articles` 的 `if url_norm in existing: continue`
—— **每号每轮正好少 1 篇**(cover 在前、列表在后),且**断供期的 162 篇积压永远补不上**。

**根因**:去重逻辑把"重复"与"已有信息需要更新"混为一谈。

**现在的强制手段**:改成"已有行也回填"(`新值>0 且旧值=0` 才写;
**绝不覆盖非零旧值**(没有依据)、**不写 0**(0 是"不知道")),4 条测试钉住。

### A5. 静默返回空 ⇒ 提示指向相反方向

**症状**:`_subscribe_by_name` 在不支持按名解析时 `return ""` ⇒ 上层写成
「**WeRSS 未搜到该号**」,而真相是「**我们没有按名解析能力**」。
**一个让你去别处找号,一个让你去修配置 —— 方向完全相反。**

**历史实例**:同上(未爆雷,但已埋)。

**现在的强制手段**:改成抛 `PlatformError`,hint 说"解析能力缺失"。

### A6. 检查器自己烂了

**症状**:`job_liveness.py` 打印 `❌` 撞 GBK 控制台**直接崩**,而且**恰好崩在报"从没执行过"清单那一刻**;
`check_production.py` 还在 `import` **9-30 就删掉的 `dajiala_client`** ⇒ **永远 FAIL**。

**根因**:检查器没有被测试盯着,也没人每天看它。

**现在的强制手段**:已修两处;**"永远红的项会训练人忽略整份报告"** 写进了代码注释。

## 二、B 类:**抢额度**

### B1. 同一个账号的额度被 6 条互不知道的路一起花

**症状**:监听轮被挡、闸门都合了,**同步那条路照打不误** —— 闸门形同虚设,风控越打越深。

**历史实例**(路径清单,改之前的真实状态):

| 路径 | 打什么 | 当时判额度吗 |
|---|---|---|
| 监听轮 | cover / 网页列表 / App 列表 | ✅(轮内熔断) |
| **文章同步** `_sync._fetch` | 网页列表 | ❌ **完全没有** |
| **推荐全量同步** `_ticks` | 同上 | ❌ |
| 续期 | `renewal` + `shelf` | 自己一套 |
| 链路体检验活 | `shelf` | 自己一套 |
| 探针脚本 | 列表/书架 | 自己一套 |

**根因**:额度是**跨模块的公共资源**,但**没有任何一处公共记账**。
判据还住在 1200 行的 `_listen.py` 里 —— 别的路径要用就得 import 那个重模块,**嫌重就不 import**。

**现在的强制手段**:

1. **`app/services/weread_budget.py`** —— 判据(`QUOTA_MARKS` / `is_quota_error`)与
   **跨路径共享熔断**(写 `system_config`,不是内存)的**单一事实来源**;
2. **熔断中连请求都不发** —— 失败本身会加深风控,少打一次都是赚;
3. **续期成功要解熔断** —— 新会话 = 新额度账(否则"刚换到好会话却被旧账停半小时");
4. **源码级守卫测试** —— 凡调用微信读书列表的模块必须出现 `weread_budget.call(`,
   规则落在"**定义还是调用**"这个事实上(不是文件名白名单),**反向验证过**。

### B2. 熔断粒度错了会误伤

**症状**:拿"列表被挡"去停 **cover**。

**为什么错**:实测 `-2041` 打的是**列表预算**,同一时刻 **`shelf` 与 cover 都好好的** ——
停了 cover 就等于每个号连"当天有没有发文"都答不上,**那才是真瞎**。
(这条是 `test_listen_counts_quiet_rounds_on_weread_path` 当场逼出来的。)

**现在的强制手段**:熔断粒度是**端点类**(`SCOPE_WEB_LIST` / `SCOPE_APP_LIST`),
不是"通道";网页列表熔断**只合 `list_off`,不合 `off`**。

### B3. 兜底被上游的熔断连累 ⇒ 在最需要它的时候失效

**症状**:第一版 App 兜底写的是 `not list_skipped`。而
`list_skipped = (不在窗口) or (网页本轮已熔断)` —— **用它挡 App,
就等于"网页一被挡,唯一还能用的 App 也一起停"**。

**根因**:一个布尔混了两种语义("该省额度" vs "上游已熔断")。

**现在的强制手段**:改用 `list_allow`(**在不在本轮窗口**)——
窗口纪律照旧,但不让网页的熔断连累 App。**改动理由写在代码里,注明"别改回去"**。

### B4. 一次性打穿额度

**历史实例**:续期后打 `81×2` 的补采炸弹 —— "数小时内打穿全部会话额度"(已关,`weread_fullsync_on_renewal` 默认关)。

**现在的强制手段**:该开关保持默认关;要开必须显式。

## 三、每次改这个模块前,先问这 5 个问题

这是这份文档**最实用的部分** —— 上面每条事故,都能被其中一个问题提前拦住:

1. **我这次失败,会不会被上层读成"今天没有数据"?**
   → 会,就抛异常,别返回空。(A1 / A4 / A5)
2. **我这次调用,花的是谁的额度?还有谁在花同一个?**
   → 有别人在花,就必须经 `weread_budget.call`。(B1)
3. **我这里的成功判据,是"我发出了请求"还是"我拿到了真东西"?**
   → 必须是后者;HTTP 200 不算,`status=success` 不算。(A2 / A3)
4. **我写的这个计数/标记,有人读吗?**
   → 没人的话,要么接进体检/卡片,要么别写。**只写不读等于没有。**(A1)
5. **我这次改动,需不需要同步改另一条链?**
   → 本仓的老毛病是"同一个坑在两条链上,只修了一条"。
   不确定就去 `grep` 一下同一个 API/同一张表还有谁在用。

## 四、仍然存在、明确没修的

| 项 | 为什么没修 |
|---|---|
| `dajiala` / `wechat_traffic` 僵尸链(model+表+API+maintenance+删除语句,**五处**) | 源 9-29 已摘,**全项目无一写入、API 读它恒空**。涉及表与 API 废弃,该走"标记废弃 + 迁移",不该随手删 |
| `_sync.py` 的 `if True:` 空壳 | 去掉要反缩进 60 行,大 diff 易错,收益只是观感 |
| UA 常量 ×4 + 1 内联(⚠️ `wemp_client` 是 Chrome/131、其余 147,**不一致,改前先确认是否刻意**) | 要碰多个热路径,建议单独一次、单独验证 |
| `_parse_time` ×2、列表归一化 ×3 | 同上 |
| `reader_platform` 整个源从未被构造 | 待定:要不要这条备份源 |
| 前端 4 条后端接口没接线(`/analyze`、`/keywords` GET+PUT、`/weread/shelf`、`/articles/{id}/rewrites`) | `/weread/shelf` 看着**本该用在"导入书架"的 UI 上**;`PUT /keywords` 文档自己写着"占位接口,恒 400" |
| `run_full_sync_if_pending` 默认关 | 保持关闭,知道它是"待启用"即可 |
