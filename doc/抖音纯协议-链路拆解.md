# 抖音纯协议:链路拆解与自修指南

> 2026-10-07 建。姊妹篇:`小红书纯协议-链路拆解.md`。
> 那篇讲的是"签名怎么算";**这篇的核心不是签名** —— 抖音搜索的卡点是**登录态**,
> 而且签名**大概率压根不需要**。先把这一个反直觉的结论记住,往下读才顺。

---

## 0. 四句话结论(时间紧只看这里)

1. **抖音搜索必须登录**。匿名请求回 `HTTP 200 + status_code=2483 +「请先登录,再继续搜索吧」`。
2. **`a_bogus` 不但不必需,加了还会把请求打坏** —— 实测:不带它拿到 **14 条 / 812KB**,
   带它拿到 **0 条 / 3.9KB**(同一账号、同一时刻、只改这一个变量)。所以 `use_abogus`
   默认 `False` 是**实测支持的**,别去"补上签名"。
3. 请求头里的 `x-tt-argus: 1` 要带(别人的注释说缺了会被网关 403),
   但**我们实测没有撞到那个 403** —— 连 `uifid` 都没有也过了。
4. **别连发**。连发 4 次(35 秒内)会把账号推进一种**"空成功"**状态
   (`status_code=0` + `data: []`,约 3.9KB)—— 与"真没搜到"**形状完全相同**。
   实测约 **35 分钟**后自己恢复。`_GAP` 因此定在 **8 秒/词**(见 §5 坑 5)。
5. ✅ **这条路整体是通的**:登录 + 不带 `a_bogus` ⇒ 稳定拿到 13~14 条真数据、
   含**真实作者名**。

## 1. 链路长什么样

```
app/services/douyin_protocol_source.py    ← 拼请求、解析响应(我们写的)
        │
        ├─ build_params()   ← 25 个"设备指纹"式参数 + 业务参数
        ├─ build_headers()  ← UA / Cookie / Referer / x-tt-argus
        └─ build_url()      ← 可选 a_bogus(默认**不加**)
        │
        ▼
GET https://www.douyin.com/aweme/v1/web/general/search/single/?<query>
        │
        ▼
{"status_code":0, "data":[{"aweme_info":{...}}], "extra":{"logid":"..."}}
        │
        ▼
_parse() → 与 mediacrawler_source.crawl 同一形状
        │
        ▼
douyin_leads.collect_leads()   ← 「协议优先、浏览器兜底」就在这里(见 §8)
        │
        ▼
口令解析 → 落库 → 推送卡片

app/services/douyin_sign/            ← 签名(a_bogus / X-Bogus),**f2 的逐字移植**
```

**为什么搬 f2 的源码而不是 `pip install`**:见 `app/services/douyin_sign/NOTICE.md`。
一句话 —— f2 是 9MB 的全能下载器,我们只要那 40KB;而且**改版时源码在自己手里才修得动**。

## 2. 签名(`a_bogus` / `X-Bogus`)

| | `a_bogus` | `X-Bogus` |
|---|---|---|
| 用在 | 抖音 web 当前主用 | 老版本,部分接口仍认 |
| 实现 | `app/services/douyin_sign/abogus.py`(914 行) | `app/services/douyin_sign/xbogus.py`(235 行) |
| 依赖 | `gmssl`(纯 Python SM3) | **零第三方** |
| 调用 | `ABogus(fp=…, user_agent=…).generate_abogus(params)[1]` | `XBogus(ua).getXBogus(query)[1]` |

**两个"以为"会踩的坑**:
- **返回值是元组**:`XBogus` 给 **3 个**、`ABogus` 给 **4 个**,签名在 `[1]`。当字符串用会拼出
  `a_bogus=<tuple>`。形状由 `tests/test_douyin_sign.py` 钉住。
- **UA 与 `fp` 都进签名**。签名用的 UA 必须与请求头里的 UA **完全一致**,否则站点那边对不上。
  指纹 `fp` 每次随机生成是**对的**(真浏览器本来就逐机不同),但**测试里必须用定值**,
  否则金标就成了薛定谔的。

**上游更新了怎么办**:
```bash
python scripts/vendor_f2_sign.py --sha <新提交>   # 先看上游更新到哪
python scripts/vendor_f2_sign.py                  # 重新移植
python -m pytest tests/test_douyin_sign.py -q     # 金标/哈希变了 = 要你确认
```
`tests/test_douyin_sign.py::test_算法体未被改动` 是**有意的绊索**:改了算法体必须在这里红一次,
逼改动被看见。另有一条**外部锚点** —— 上游自己公布的硬编码期望值(`DFSzswVY7OiANnTJtmWx-e9WX7jo`),
它是**独立于我们这份拷贝**的,不是我拿自己的输出给自己对账。

## 3. 接口合同

**端点**:`GET https://www.douyin.com/aweme/v1/web/general/search/single/`

**业务参数**(`build_params`):

| 参数 | 值 | 说明 |
|---|---|---|
| `keyword` | 搜索词 | |
| `search_channel` | `aweme_general` | |
| `search_source` | `tab_search` | |
| `offset` | `0, 15, 30…` | 翻页偏移 |
| `count` | `15` | 单页条数 |
| `search_id` | 首屏**空串** | ★ **翻页用上一屏响应里的 `extra.logid`** |
| `from_group_id` | `7378810571505847586` | ⚠️ **会过期的魔数**;失效表现是"200 但 data 空" |
| 其余 | `enable_history` / `query_correct_type` / `is_filter_search` / `need_filter_settings` / `list_type` | 照抄即可 |

**设备指纹参数**(24 个):`device_platform=webapp`、`aid=6383`、`channel=channel_pc_web`、
`version_code/version_name`、`pc_client_type`、`cookie_enabled`、`browser_*`、`engine_*`、
`os_*`、`cpu_core_num`、`device_memory`、`platform=PC`、`screen_*`、`effective_type`、
`round_trip_time`,外加 `webid`(19 位随机数字)+ `msToken`。

> ⚠️ **`version_code` / `browser_version` 是会过期的** —— 它们是"客户端版本号"的模仿。
> 哪天接口开始回空数据,先怀疑这几个值过时了(去网页版 F12 抄一份新的)。

**请求头**(`build_headers`):

| 头 | 值 | 为什么 |
|---|---|---|
| `User-Agent` | 与签名用的**同一个** | 签名把 UA 算进去了 |
| `Cookie` | 登录态 | **没它 → 2483** |
| `Referer` | `https://www.douyin.com/search/<词>?aid=…&type=general` | 需要 URL 编码 |
| `x-tt-argus` | `1` | 网关 ArgusSecurityPlugin;当前不校验取值 |
| `uifid` | cookie 里的 `UIFID` 或 `UIFID_TEMP` | **两个名字都要认** |

## 4. 凭据从哪来(**这是当前的拦路虎**)

搜索**必须登录**。所以要么:
- 从**已登录的浏览器档案**导出 cookie(像小红书那样:`ctx.cookies()` 解密读,**别手抄**),
  写进**加密 cookie 库**(`user_cookies` 表,平台名 `douyin`),或
- 在 `.env` 里配 `DOUYIN_COOKIE`(回落用;⚠️ `.env` 是 gitignore 的,**值绝不能进仓库**)。

**现成的工具**(2026-10-07 加):

```bash
python tools/douyin_export_cookie.py --check    # 只看关键项齐不齐,不写库
python tools/douyin_export_cookie.py            # 导出进加密库(用户 1)
```

默认读 `tools/MediaCrawler/browser_data/cdp_dy_user_data_dir` —— 那是 `douyin_leads`
**每天在用的号**,已经在生产里跑,不是新增的账号风险。
⚠️ 同目录的 `dy_user_data_dir` 是旧模式留下的(10-03 就停更),**别用错**。
⚠️ 工具**只读、不导航任何页面**,凭据**只写加密库、不打印不落盘**。

⚠️ **必须包含的关键项**:`UIFID`(或 `UIFID_TEMP`)、`ttwid`、`odin_tt`、**`sessionid` 系列**。
实测那个档案给 54 项、齐全;若缺 `sessionid`,纯协议会被回 **2483**。

## 5. 实测踩到的坑(2026-10-07,全部真踩过)

### 坑 1:以为"账号限流是签名没处理好" —— **这次的实测不支持这个假设**
匿名对照组(`tools/douyin_probe.py`,4 次请求):

| 组 | HTTP | status_code | 响应 |
|---|---|---|---|
| A **不带** `a_bogus` | 200 | 2483 | `请先登录,再继续搜索吧` |
| B **带** `a_bogus` | 200 | 2483 | **一字不差** |

⇒ 卡点是**登录态**,签名**根本没轮到被校验**。
⚠️ **结论的边界**:这只证明"**未登录时**签名不是瓶颈",**不证明登录后也不需要它**。

### 坑 2:`x-tt-argus` / `uifid` 的 403 **没有出现**
MediaCrawler 的注释写着"缺 uifid → 403 `Blocked by ArgusSecurityPlugin Uifid Not Found`"。
我们匿名(连 `UIFID_TEMP` 都没有)实测**没撞到**,`x-tt-argus: 1` 一传就过。
⇒ 那条注释**当前不成立**(可能只对某些接口或某个时期)。
两个头照旧带着(免费、无害),但**它们不是现在的瓶颈** —— 别照着旧注释去查错方向。

### 坑 3:匿名首页只发 `__ac_nonce`,拿不到 `UIFID_TEMP`
所以"先去首页蹭一个匿名 uifid"这条路**走不通**,必须真登录。

### 坑 4:★ **带上 `a_bogus` 反而把请求打坏**(登录后实测,这是本篇最有价值的一条)
从 MediaCrawler 用的那个号(`cdp_dy_user_data_dir`)导出凭据后重跑对照:

| 组 | 响应 | `data` | 解析出 |
|---|---|---|---|
| A **不带** `a_bogus` | **812,814 字节** | 14 | **13 条作品**(真实作者名) |
| B **带** `a_bogus` | 3,922 字节 | `[]` | 0 条 |

同一账号、同一时刻、同一份 cookie,**只改了这一个变量**。
⇒ **不是"签名没用",是"签错了会被判成可疑请求"** —— 我们本地算的 `a_bogus`
与请求实际发出的参数/UA/指纹配不上,站点就干脆给空。
**所以 `use_abogus` 默认 `False` 是实测支持的**,别去"补上签名"。
(这也解释了 MediaCrawler 那句看着像笔误的**反条件** `if "/v1/web/general/search" not in uri:`
—— 它是有意的。)

### 坑 5:★ **"空成功"长得和"没搜到"一模一样** —— 已判定:是**限流**
坑 4 之后,同一个号在同一分钟内再发请求,开始**一律**回:

```
HTTP 200 | status_code=0 | data=[] | cursor=0 | has_more=0 | 约 3921 字节
```

这正是**最危险的那类响应** —— 它**不报错**。

**判定过程(照"控制变量 + 找免费对照"走的,最后结论和最初两个猜测都不同)**:

| 步骤 | 做法 | 结果 |
|---|---|---|
| ① 排 `__ac_nonce` | 只改这一个变量:库里 53 项 vs 加上匿名 nonce | 两组**都是 0**、响应同 3921 字节 ⇒ **证伪** |
| ② 排"分钟级限流" | 静默 **7 分钟**后发**单次** | 仍 0 ⇒ 比分钟粗 |
| ③ **免费对照** | 等 `douyin_leads` 那班作业(00:10,走 MediaCrawler 浏览器) | **成功:8 个词、16 条线索** ⇒ **账号没事** |
| ④ 决定性一测 | MediaCrawler 刚成功(00:12),**立刻**再发我们的协议请求 | **13 条** ⇒ **就是限流,已恢复** |

⇒ **结论**:既不是"账号被标记",也不是"我们请求构造错了"(同一份代码现在能跑到数据),
而是**连发触发的临时限流**,约 **35 分钟**自愈。

**两条可操作的推论**(已落到代码里):
1. **`_GAP` 从 1.5 秒改成 8 秒**。生产一轮 4 个词按 1.5 秒跑 = **6 秒内打完**,大概率撞同一个坑;
   8 秒是照**能跑通的对照**取的:MediaCrawler 8 个词花 90 秒 ≈ **11 秒/词**,留了余量。
   测试 `test_间隔不许被随手调小` 是**绊索**,调小会让它红。
2. **"空成功"目前仍无法与"真没结果"区分** —— 这是**没解决的**。
   将来若要加信号(如"连续 N 次空 ⇒ 记一条疑似限流"),**别把它做成静默降级**。

### 坑 6:`_cookie(session=None)` 静默不查加密库(已修)
`_cookie()` 只在**传了 session** 时才去读加密库,否则回落到 `.env`。
而 `.env` 里通常没有 `douyin_cookie` ⇒ 返回**空串** ⇒ 请求不带登录态 ⇒ 2483,
**表现只是"搜不到"**。
当天是靠"库里 53 项 vs 函数读到 0 字节"这个对比才发现的。
现在**没传 session 会明确告警**(`test_没传_session_要报警告`)。

### 坑 7:★ `play_count` 是**假 0**(逐字段核对抓到的)
2026-10-08 抓了一份真实响应(14 条)逐字段对,**我依赖的 6 个字段 13/13 命中**、
5 个统计键也 13/13 —— 名字不是照猜的,交叉核对也对得上(作者名/标题/时间/转发数零不符)。

但同一批数据里:

| 指标 | 实测取值 | 判定 |
|---|---|---|
| `digg_count` / `share_count` / `collect_count` / `comment_count` | 61~321,184 / 106~73,472 / 20~264,295 / 7~3,085 | ✅ 真实 |
| **`play_count`** | **13/13 全是 0** | ❌ **假 0** |

抖音**把字段填 0** 而不是不给(与已知事实一致:播放量是**创作者私有数据**)。
直接采就会把"拿不到"读成"没人看" —— 而且它会**喂给 `conversion.estimate` 算曝光**,
影响的不只是展示。现在这些键**取到 0 时按缺失处理**(`_ALWAYS_ZERO_KEYS`)。

⚠️ **这条也是"条数对不代表字段对"的活例子**:13 条解析得好好的、字段名全中,
里面却藏着一个系统性假值。**只数条数的核对是抓不到它的。**

### 5.x ★ 响应里**明说了原因**,而我们没读它 —— `search_nil_info`(2026-10-08)

**症状**:12:11 之后连续 4 轮抖音**全部关键词零结果**,活体探针也回 0 条。
排查一度压在"登录态失效"和"连发限流"上(凭据确实没回 `2483`、看起来是好的)。

**真因**:抖音把搜索结果**整页换成了验证页**,而这件事**在响应里写着**:

```json
{"status_code": 0, "data": [],
 "search_nil_info": {"search_nil_type": "verify_check",
                     "is_load_more": "first_flush",
                     "search_nil_item": "verify_check", "text_type": 9},
 "polling_time": 3}
```

而当时那一层**只看 `status_code` 与 `data`**:`0` + `[]` 完美通过检查 ⇒ 返回空
⇒ 上层读成「限流 / 登录态失效」⇒ 白跑一次浏览器兜底 ⇒ 运行记录失败。
**日志里一个字都没提"验证"。**

**修法(代码)**:认出 `search_nil_type`。`verify_check` ⇒ 抛 `kind="verify", needs_human=True`
(单列一档,因为它**既不是凭据失效、也不是限流**,处置完全不同);
空结果时也把 `nil_type` 记下来,将来出现别的类型能一眼看出。

**修法(人)**:在浏览器里打开抖音**过一次验证**(滑块/验证码)。
⚠️ **重导 cookie 解决不了** —— 重导只是复制 cookie,过不了验证。
链路体检验到这一档会**判红并明说这句**,不会给"重导"这条无效修法。

**教训(比 bug 本身值钱)**:响应里**已经写好的原因字段**一旦不读,
它的症状与"真的没有数据"**一模一样**,而且**所有下游都会给出各自的错误归因**
(限流 / 登录态 / 账号被限),每一个都听着合理 —— 于是排查方向会离真因越来越远。
⇒ 遇到"莫名其妙变空",第一件事是**把原始响应打出来看**,
而不是先怀疑已知的那几个错误码。

### 5.y ✗ **证伪:补全 cookie jar 并不能消掉验证要求**(2026-10-08)

**动机**:闲鱼那次的经验是「**卡的是 cookie 那一份** —— 只贴登录三件套不够,
页面发的是**整套 jar**」。于是拿同一条思路验抖音:把我们的 jar 与**浏览器档案的真实 jar** 逐项对比。

**实测差集**(导出时刻的对比):

```
我们的 jar        53 项
浏览器档案里的 jar 57 项
  档案里有、我们没发:__ac_nonce ★ / x_tt_token / is_dbsc / (一个空名)
  同名但值不同:web_sign_token / __ac_signature
```

`__ac_nonce` 与 `__ac_signature` 是**一次会话生成的一对**(服务端发 nonce、页面 JS 算出签名),
而我们**发了签名却没有配对的 nonce** —— 形状上确实像"jar 不完整"。

**结果**:**重新导出把 4 项补齐了(53 → 56,含 `__ac_nonce`),滑块依旧。**
⇒ **「jar 不完整」不解释这次的 `verify_check`**。

**结论与保留**:
- 补全 jar **该做**(那是纪律,不是假设),以后导出都该与档案对齐;
- 但**验证要求是服务端决定的** —— 剩下能动的只有「**人去过验证**」与「**换出口 IP**」;
- ⚠️ 别把这个负结果读成"cookie 不重要":它只说明**这一种缺项**不是本次的原因。

**体检里怎么处理**:`_douyin_jar_note()` 会在凭据行后面附一句 jar 完整性提示
(**只提示、不判红** —— 给一个解释不了的项判红就是造假红灯)。

### 5.z ✅ **实战验证:人过一次滑块 + 重导 = 恢复**(2026-10-08 当晚)

**做法**(缺一不可,顺序也对):
1. 用**导出 cookie 的那个档案**开浏览器并过验证 —— 必须带 `--user-data-dir`:
   ```
   "C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe" ^
     --user-data-dir="<仓库>	ools\MediaCrawlerrowser_data\cdp_dy_user_data_dir" ^
     https://www.douyin.com/search/夸克口令
   ```
   ⚠️ 用**平时那个浏览器**过验证是**没用的** —— 档案不同,导出读不到。
2. 过完**把那个窗口关掉**(档案被占用时读不进来:Playwright 撞 profile 锁)。
3. **重新导出** —— 体检的 `_douyin_reheal` 会自动做;手工是
   `douyin_cookie_export.export_from_profile(db, 1)`。

**实测结果**:导出后 `search(["夸克口令"])` → **15 条**;`search([夸克口令,咐置,网盘口令])`
→ **40 条、3/3 个词都命中**。⇒ 恢复。

**导出时多出来的项**(过验证之后才有,只作**观察**,别当成判据):

```
新增: SEARCH_RESULT_LIST_TYPE / passport_auth_mix_state / bit_env / gulu_source_res / sdk_source_info
值变: odin_tt / x_tt_token / IsDouyinActive / …
```

`SEARCH_RESULT_LIST_TYPE` 是**搜索相关**的新 cookie,`passport_auth_mix_state` 与登录态有关 ——
**很可能就是"这个会话已被验证"的痕迹**,但**我们没有做控制变量**(没法只加它不加别的),
所以**不把它写进判据**。真要拿它当判据,得先做一次"只补这一个字段"的对照。

**所以自动化在这里的边界是**:能自动**发现**、能自动**重导**、能自动**重试**,
但**过验证那一下只能是人**。别再去 GitHub 找"绕过的办法"了 ——
调研结论是**没有任何开源项目解决过 `search_nil_info`/`verify_check`**
(唯一原始 dump 是 MediaCrawler #358,作者无处置;TikTokDownloader 四个搜索接口 2025-11 全线返空,
作者原话「似乎需要新算法,尚未开源」)。

### 5.aa ✅ 2026-10-19 加固:把「登录 / 风控 / 瞬时故障」彻底分开

**现象**:10-18 14:02 之后连续三轮全空(16:10 / 20:10 / 22:30),00:10 浏览器兜底
又直接退出码 1。看起来像"登录掉了",用户也提出要不要重扫。

**证据(先证伪再动手)**:
- 协议 cookie 与 MediaCrawler 档案是**同一会话**:两边 `sid_guard` 都是
  `2026-10-03 签发 / 2026-12-02 到期`;
- `profile_login_state('douyin') == True`(档案里 `sessionid` 齐全);
- 00:10 浏览器兜底的真错是 **`Page.goto: Timeout 30000ms exceeded`**(打开 douyin.com
  超时),不是登录失败;
- 20:10 / 00:10 的日志明确是 `kind=verify_cooldown` ⇒ **服务端 `verify_check` 风控**。

⇒ **不是登录过期,重扫没用**。但浏览器兜底本身确实有几个可修的脆弱点:

1. **`--lt` 必须跟着 cookie 走**:MediaCrawler 的 CLI 最后一行是
   `config.LOGIN_TYPE = lt.value` —— 以前恒传 `--lt qrcode`,于是 base_config 里写的
   `LOGIN_TYPE="cookie"` **被当场覆盖**,cookie 登录等于没接。现在有 cookie 就传
   `--lt cookie`。
2. **浏览器兜底也注入协议路的 cookie**:档案登录是第一条退路,cookie 注入是第二条;
   档案被锁/损坏时仍然是登录态,不会空跑一圈。
3. **瞬时故障重试一次**:`Page.goto` 超时 / `TargetClosed` / `ERR_*` 属于瞬时;
   空结果与登录失效**不重试**(重试只会对同一账号多打一次风控)。
4. **验证冷却内浏览器兜底每个窗口只探一次**:09:30 的实测证明真人形状的浏览器有时还能
   搜到,所以不能一刀切禁;但 16:10~00:10 连续四轮也空,反复探只会延长风控。
   现在把"这个冷却截止时间已探过"记进 `system_config`,同一窗口再来就跳过。
5. **浏览器兜底成功 = 会话是通的** ⇒ 自动从档案重导凭据并 `clear_verify`,让下一轮
   回到更便宜的协议路(失败只告警,绝不把已拿到的线索作废)。

⚠️ **这五条不绕过风控**:`verify_check` 是服务端对自动化搜索下的要求,动作仍然是**等**;
它们解决的是"**别再因为登录/超时/重复探针而白白失败**",以及"成功一次后能自动回到协议路"。

  │       (2026-10-28 实测:同一份 cookie 换全新空档案立刻能搜到)。

  │       实测因此连空 8 小时、排查方向全错。
  ├─ CDP 路日志说「**验证码中间页**」? → 同上:先看它说的是「首页也这样」还是

## 6. CDP 路(2026-10-25 新增,当前**第一优先**)

### 6.1 为什么加

2026-10-25 一整天线索链「8 个关键词全部无结果」。受控判别一步步行:

| 判别 | 结果 |
|---|---|
| MediaCrawler 浏览器路 + 泛词「**美食**」(必然有大量结果) | **0 条** |
| 协议接口 | `kind=verify`,`search_nil_info.search_nil_type=verify_check` |
| `profile_login_state('douyin')` | `True` —— ⚠️ 它**只查 cookie 名**,不代表会话有效 |
| MediaCrawler 档案本身(不注入 cookie 直接开) | **未登录**(搜索页弹扫码框) |
| **CDP:普通 Edge + 注入库里的 cookie** | **16 条**,`webdriver=false`,`logged_out=false` |

⇒ **账号没被限、cookie 是好的、出口也能出结果** —— 卡住的是我们那条自动化路
(Playwright launch 出来的浏览器)。这与小红书 2026-10-15 的结论完全同源。

### 6.2 它怎么工作(`app/services/douyin_cdp_source.py`)

1. 端点默认 `http://127.0.0.1:9333`(与小红书的 9222 分开);
2. 端点不通就用**普通命令行** `subprocess.Popen` 拉起 Edge(专用档案
   `data/_douyin_profile`,`--start-minimized`)—— **不是** Playwright launch,
   所以 `navigator.webdriver === false`;
3. 连上后**注入库里的抖音 cookie**(档案干净,登录态只靠注入);
4. 逐词打开 `https://www.douyin.com/search/<词>?type=video`,读 DOM 里的 `/video/` 链接;
5. 作者**不是链接**(实测搜索卡里 `a[href*="/user/"]` 命中 0),而是卡片正文里单独一行
   `@昵称` ⇒ 从 `innerText` 按行取。

### 6.3 三条纪律

1. **连不上/读不到就抛**,绝不返回空列表 —— 空列表与「抖音没人推」完全同形。
2. **只关自己开的那个标签**(接管的是浏览器上下文,别动别人的页面)。
3. **词间硬下限 5 秒**,每轮词数由 `DOUYIN_CDP_MAX_KEYWORDS` 定。
   ★ 2026-10-28 由 **4 改为 8**:CDP 已是**第一优先且唯一能出数**的路,一旦成功
   就**不再回落** MediaCrawler ⇒ 停在 4 个词等于每轮**少搜一半**。取 8 是
   **与改造前 MediaCrawler 的覆盖持平**(它一直是 8 个词),不是新增量。
   ⚠️ 代价是每轮请求量翻倍;再见到「验证码中间页」/ `verify_check` 时,
   **第一步就是把它调回 4**,再谈别的。

### 6.4 顺序与回落

`douyin_leads._collect`: **协议(默认关) → CDP → MediaCrawler**。
CDP 失败**必须留痕**(日志 `抖音CDP 路失败`),否则"CDP 挂了"会被读成"没人推"。

### 6.5 已知边界

- 搜索卡里**没有** `/user/` 链接,作者只能从正文 `@` 行取;取不到时为空(卡片显示 `—`)。
- 浏览器是**服务进程拉起**的(不是人开的),窗口会在每轮出现一次(已 `--start-minimized`)。
- 仍会受**出口 IP 漂移**影响:同日实测 IPv4/IPv6 每 ~15 分钟来回切,
  如果哪天 CDP 也失败,先看 `network_guard` 再谈别的。

### 6.6 ★★ 档案会被平台标记,换空档案即可(2026-10-28)

**症状**:`douyin_leads` 每轮先跑 CDP,日志固定一行
`抖音CDP 路失败(DouyinCdpError),回落 MediaCrawler:抖音返回的是「验证码中间页」`,
**15 轮 15 次**,一次都没成功过;随后 MediaCrawler 在**白天**那几轮也全空,
整条链 08/12/16 三轮连续失败。

**受控判别(四步,一步只改一个变量)**

| # | 变量 | 结果 |
|---|---|---|
| ① | 专用档案 `data/_douyin_profile` + 注入库里 cookie | **连首页都是「验证码中间页」**(`body` 仅 4 字节空白) |
| ② | **全新空白档案**,不注入 cookie | 正常(跳 `/jingxuan`,正文 2573 字) |
| ③ | **全新空白档案** + 注入库里那 66 条 cookie | **正常且已登录**(页面上没有「登录」按钮) |
| ④ | 隔离旧档案后跑 `douyin_cdp_source.search(["美食"])` | **16 条真数据** |

⇒ 排除了**出口 IP**、**cookie/会话**、**账号**三种解释,**只剩档案本身被标记**。
这一步很关键:同一份 cookie 换个浏览器身份就能搜到 ⇒ 这正是"② 被要求过验证"
(不是"① 登录态过期"),动作是**换档案**,不是重扫码 —— 而 ① 才是要人动手的那个。

**已落地的代码**(`app/services/douyin_cdp_source.py`)

1. **自动愈合**:看到「验证码中间页」⇒ `profile_suspect=True` ⇒
   `quarantine_profile()` 把档案改名成 `data/_douyin_profile.flagged-<时间戳>`
   (只留最近 1 份,每份约 600MB),下一次启动自动建空档案,**重试一次**。
   登录态本来就只靠注入 cookie(`§6.2` 第 3 步)⇒ **换档案不丢登录**。
2. **只隔离一次**:重试**仍**被挡 ⇒ 写明"不是档案的问题(查出口 IP / 账号)",
   并记 12 小时冷却(`douyin_cdp_quarantine_cooldown_hours`),不再每轮丢一份 600MB。
   判据是"**换全新档案也没用**"这个事实,不是"又失败了"。
3. **页面级判据收紧成只看标题**:`验证码` 现在会触发自动隔离,而正文里出现「验证码」
   三个字完全可能是某条视频的标题 —— 误判代价从"多报一次错"变成"丢一份档案"。
4. **首页预热**:先落到 `https://www.douyin.com/` 停 3 秒,再去搜索页。
   改前是**冷启动直达** `/search/<词>`(全新标签、没有首页访问),真人不会这么用
   —— 与小红书那条的结论同源(`xhs-461-solved-by-page-render`)。
   首页本身就是验证码页 ⇒ 这是**最干净的"档案被标记"证据**,直接触发隔离。
5. **把 CDP 的结论接进回落告警**(`douyin_leads._with_douyin_verdict`):
   MediaCrawler 那句"全部无结果"自己都说"两种原因、别先猜一个",
   而本轮 CDP 看的是**真实页面** ⇒ 有它就直接定成②并给出动作,不再让人去看体检报告。

### 6.7 ★ 档案修好后还有第二个坑:CDP 的行没有 `publish_at`

修完档案立刻端到端跑一遍,结果 `来源=CDP 线索=0` —— 而 CDP 明明取回 16 条。
追下去:`douyin_leads.collect_leads` 的新鲜度闸对 `publish_at<=0` 的处理是**整条丢掉**
(用户口径「判不了就宁可不收」),而 `_rows_of` 产出的行**根本没有这个字段** ⇒ 全被丢掉,
运行记录还写成 `success(0 条)`。**取数通了 ≠ 有线索**。

卡片上确实有时间,但是**相对写法**。抓真实 `innerText` 得到的 5 行是:

```
06:22                     ← ① 时长(不是时间!)
13.4万                    ← ② 点赞
童哥冬眠前安排顿丰盛的…     ← ③ 标题
@猪猪狠无敌                ← ④ 作者
1小时前                    ← ⑤ 发布时间
```

两个坑:

1. **第一行 `06:22` 是时长**,当发布时间就全错 ⇒ 解析器**不认 `HH:MM`**,只从**末尾 3 行**取。
2. 共享的 `hot_time.parse_published` **故意不认** `周前/月前/年前`(它的口径是
   「宁可留空,不给一个错的时刻」)⇒ **不要为抖音去改它**。另加
   `hot_time.parse_published_coarse()`,明确只用于**阈值比较**,不许用于展示。

实测效果:同一批 16 条里认出 `2026-10-28 / 10-26 / 10-27`、`2021`(5 年前)、`2025`(1 年前),
新鲜度闸(下限 `2026-10-01`)准确留下 **4 条**。

> ⚠️ **覆盖度**:CDP 每轮只搜前 `DOUYIN_CDP_MAX_KEYWORDS` 个词,而它一旦成功
> **不再回落** MediaCrawler ⇒ 超出上限的词这一轮**没搜**。
> ★ 2026-10-28 该值由 4 **改为 8**,与改造前 MediaCrawler 的覆盖(8 个词)持平;
> 覆盖不足时日志会明说「本轮只搜了 N/M 个词…其余本轮没搜,不是没结果」。


> ⚠️ **下一轮再空怎么办**:先看日志里 CDP 那一行。若是
> 「**连首页**都给验证码」/「换全新空档案也一样被挡」⇒ 那是出口 IP 或账号的风控,
> **重扫没用**,等就行;只有档案被标记时,自动隔离才会真的把数据拿回来。
