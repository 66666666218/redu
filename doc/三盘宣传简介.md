# 三盘的「宣传简介」(夸克 / 百度 / 迅雷)

> 2026-10-10 定案。目的:别人从我们分享的链里保存资源时,**一并拿到我们的宣传简介**。

## 一条纪律

**简介必须"并进建链清单",在建链那一步就带上。**

链是**快照** —— 建完再往里补,链子里那份不会变(夸克侧有注释明确写过这件事)。
所以三家的做法是同一个:**把简介的路径/id 加进建链调用的清单里**。

| 盘 | 建链调用 | 简介怎么进去 | 配置项 |
|---|---|---|---|
| **夸克** | `share_fids(share_ids, …)` | 资源是**目录** ⇒ **复制进目录里**(对方整包保存自动带走);是**散文件** ⇒ 并进 `share_ids`(并排顶层) | `pan_intro_quark_dir` |
| **迅雷** | `POST /drive/v1/share {file_ids:[…]}` | **同上规则**:目录 ⇒ `:batchCopy` 复制进去,只分享那些目录;散文件 ⇒ 并进 `file_ids` | `pan_intro_xunlei_dir` |
| **百度** | `share/pset(path_list=[…])` | **只能并进 `path_list`(并排顶层)** —— 见下,百度做不到"塞进目录" | `pan_intro_baidu_dir` |

> **实测的三家最终形态**:百度、迅雷 = **顶层并列**;**夸克 = 目录内**。
> ⚠️ "塞进目录"的代价:**每个资源目录会真的多存一份**(实测约 2.9 MB/份)。
> "并排顶层"一份都不多存。

简介文件在**各盘自己的一个目录里**(实测用的是 `监控简介` / 监听宣传),用户在 App/网页里手动放一次即可。

## 为什么不用"复制"

**百度侧三条路都试过并排除了**(2026-10-10 实测):

1. `POST /api/filemanager?opera=copy` → **恒 `errno=2`**。
   ★ **决定性对照**:同一路由的 `opera=delete` 正常(`errno=0`)⇒ **不是会话问题**;
   `async=2`、`channel=chunlei`(从百度前端 bundle 里挖出来的参数)也试过,一样。
2. **转存自己的分享**(建一条简介分享 → `share/transfer` 回来)→ `errno=2 文件已存在`
   —— 百度挡"自转",与夸克的 `41017` 同类。
3. **上传接口未实现**(百度客户端没有 upload)。

⇒ **"并进 path_list" 一次就成了** —— 而且比复制**更干净**:不占盘、不多一份副本、一次调用。

**迅雷侧**盘内复制是**有**的(`POST /drive/v1/files:batchCopy`,形状
`{"ids": […], "to": {"parent_id": "…", "space": ""}, "space": ""}` —— 从**迅雷自己的网页 JS**
里挖出来的;我先试的 `/{id}/copy` 是错路由)。**迅雷的"塞进目录"就是用它做的。**

## 百度为什么做不到"塞进目录"

**四条路全排除了**(2026-10-10 实测,**不是没试够**):

1. `POST /api/filemanager?opera=copy` → **恒 `errno=2`**;
   ★ **决定性对照**:同一路由的 `opera=delete` 正常(`errno=0`);
   连从它**自己的前端 bundle** 里挖出来的 `async=2` / `channel=chunlei` 也用上了,一样。
2. **转存自己的分享**(建一条简介分享 → `share/transfer` 回来)→ `errno=2 文件已存在`
   —— 百度挡"自转",与夸克的 `41017` 同类。
3. **没有上传接口**。
4. 把它的 **96 个前端 chunk 逐字搜过** —— 复制那次请求**根本不在里面**(只有 `opera=rename`)。

⇒ 百度只能保持「顶层并列」。**对用户的效果其实一样**(打开链就看见、整包保存一并拿到),只是位置不同。

⚠️ **迅雷的搜索接口要验证码**(`/drive/v1/files:search` 回 `_CaptchaExpired`),
而**列目录和分享详情都不要**(分享详情走 `_with_captcha_retry` 也能成)——
所以迅雷那边的按名搜索不可用时,改用**走盘**(复用 `pan_dedupe` 已验证的走法)。

## 一个曾经的误判(留档,别重犯)

我一度报"资源库缺简介、约 50 条缺" —— **是判据写错了**:简介有**两种放法**
(塞进资源目录里 / 与资源并排在分享顶层),我只看了前者 ⇒ **假阴性**。
用"顶层 + 目录内两处都看"重测:**97%(29/30)的分享其实都带简介**。
⇒ 教训:**报"缺失"之前,先把判据的两个方向都查一遍。**

## 文案定稿(2026-10-13)

**夸克简介文案**:

> **热点监控第一时间获取热点**

### 怎么改上去 —— **只能人工,别找代码**
⚠️ **夸克没有上传接口**(实测结论,记在 `config/settings.py` 的 `pan_intro_quark_dir` 注释里)
⇒ **简介文件只能你在夸克 App / 网页里手动改**,代码侧做不了:

2. 手动编辑 / 替换里面那个简介文件的内容;
3. 下一轮 `transfer_and_share` 会**自动把它复制进每个新转存的资源目录** ——
   ⚠️ 必须夹在「转存」与「建链」之间(**链是快照**,建完再补,链子里那份不会变)。

⚠️ 同样的限制对**百度**成立:百度侧**连"塞进目录"都做不到**(三条路实测全排除),
只能「顶层并列」并进 `path_list`。

### ★ 纪律:文案只放**我们自己服务**的介绍
简介是**跟着别人的资源一起被保存走**的 ⇒ 它等于把话说到**陌生人的盘里**。
所以只放"我们是谁、干什么"这种**自己服务的事实描述**;
⚠️ **不放**第三方招募/兼职/返利类内容,也不给文件起与内容无关的**诱饵名** ——
本项目做的是**盗版与引流监测**,拿同一套渠道去做标题党/广告注入,方向正好相反
(而且我们对别人的判据就是"标题与内容不符 + 硬塞广告")。

> ⚠️ **2026-10-13 用户口径**:夸克侧已按用户要求放入**文案 + 一张图**
> (文件名 `热点监控第一时间获取.doc` + `招兼职代发日入200-500.jpg`)。
> 上面这条纪律**没有被删除**,它记录的仍是本项目的判断;
> 代码只是**照做**(有几个带几个),不再就此反复论证。
> 真正需要注意的是**技术后果**(见下一节):那个文件名**命中我们自己的引流判据**,
> 不做保护就会被自家夜间清理端掉。

## ★★★ 机制与两个「静默失效」的坑(2026-10-13 实测补齐)

### 有几个带几个 —— 不写死名字
`QuarkTransfer.transfer_and_share(intro_dir=...)` 取的是该目录里的**全部文件**
(`promos = [x for x in self._list_dir(src) if not x.get("dir")]`,子目录不搬),
**没有白名单、没有扩展名过滤** ⇒ 目录里放几个、下次就带几个,改名也跟得上。
- 资源本身是**一个目录** ⇒ 简介复制进**它里面**(对方整包保存自动带走);
  资源是**散文件** ⇒ 简介与它并列,并**并进分享清单**(否则躺在我们自己盘里,对方拿不到)。
- 夹在「保存资源」与「建链」**之间**(链是快照,建完再补链子里那份不会变)。
- 日志会打「命中 N 个文件,全部随资源走:[名字…]」,返回值里也有 `intro_names` ——
  **只有计数的话,"带了 1 个"看不出"带错了哪个"**。

### 坑① 保护名单**写死文件名** ⇒ 用户一改名就静默失效
`PROTECT_NAMES` 原来只有 `简介.doc`,而用户 10-13 把文件改名成了
`热点监控第一时间获取.doc` ⇒ **那份保护从改名那一刻起就不存在了**,且没有任何地方会报出来。
而简介偏偏是盘上**最容易被判死**的东西(它被复制进每一个资源):
- 广告图那种名字**命中 `STRONG_PATTERNS`** ⇒ 强模式**单家也删**;
- 简介本身在多个家**同名同大小**(3.28 MB ≥ `DUP_MIN_BYTES`)⇒ 判成**跨目录重复**、只留最新那个家。

而 `PAN_AUTO_CLEAN_ENABLED=true` + `PAN_AUTO_CLEAN_DRY_RUN=false`(**每天 04:20 真删**)
⇒ **"自动挪进去"会被自己的夜间清理一个个吃掉,而日志一切正常。**

⇒ 修法:`quark_dup.intro_protect_dirs()`(**从 `pan_intro_quark_dir` 现取**)→
`collect_intro_protect()`(**名字 + fid 两个维度都要**:原件靠 fid,被复制进资源的副本 fid 不同、
只能靠名字)→ `refresh_protect()`(分享链 + 简介目录一次取全);
`build_plan(protect_dirs=None)` 默认自动取,传 `()` = 显式不加(离线测试用)。
**取不到目录 ⇒ 不加保护、也绝不改判据**(这层只用于"少删"),并把"没生效"写进日志与 `runs.detail`(`简介护N`)。

### 坑② 夸克**同名冲突会自动改名** ⇒ 落地判据永远匹配不上
盘上实证:`简介(1).doc` 与 `简介.doc` **并列** ⇒ 目标目录里已有**同名不同大小**的文件时,
夸克**不覆盖**,而是把新复制的那份改名成 `名字(1).扩展名`。
而落地判据是「**(原名, 大小) 都在**」⇒ 改名后**永远匹配不上** ⇒ 轮询超时抛错 ⇒ **简介静默放不进去**。
⇒ 修法:`QuarkTransfer._collision_re()` 让**名字**一侧兼容 `名字(N).扩展名`(复用与落地都走它),
**大小一侧绝不放宽**(那是 2026-10-08 抓到的另一个坑)。

### 仍然只有一件人工
夸克**没有上传接口** ⇒ 那两个文件的**内容与名字**只能在夸克 App / 网页里改。
代码这边保证的是:**你放什么就带什么,而且不会被自家清理端掉。**

## ★★★ 多账号之后:简介与落点**都是按账号的**(2026-10-16 实测)

**背景**:迅雷加了第二个号,账号池挑「最空的」⇒ 转存落到 **2 号**。而 `.env` 里两个配置项
(`XUNLEI_TRANSFER_PARENT_ID` / `PAN_INTRO_XUNLEI_DIR`)**原来都指向 1 号的盘**。

| 症状 | 真因 | 修法 |
|---|---|---|
| 每笔转存 `file_not_found / error_code 5 / 文件(夹)不存在`(当天 41 笔) | 落点 id 是 **1 号盘**的目录,`resolve_parent_id` **无条件返回**它 ⇒ 带着别人的 `parent_id` 去 `share/restore` | 配置的 id **先确认在这一枚凭据的盘里存在**;不在 ⇒ 按名字找**这个账号**的目录,**广度优先下探 3 层**;再没有才落根目录 |
| 新链**没有宣传简介**(而所有指标全绿) | `监控简介` 这个目录**只在 1 号盘里** | ① 把简介搬过去(见下);② 代码侧**把降级写进行上**(`intro_note`),不再只打日志 |

⚠️ **两个坑都值得记住**:

1. **「找不到就落根目录」这条兜底被写死的 id 短路了** —— `if fixed: return fixed`
   让它**永远走不到**,于是"目录没了也不该让整条链停摆"这句注释成了空话。
2. **按名字找必须能下探**:2 号的「最全文件」**不在根目录**,而在
   `你想要的都在里面哦/最全文件` ⇒ 只扫根目录 = 判「没有」= 资源**静默散落根目录**。

### 怎么把简介搬到另一个号

迅雷**没有上传接口**,`batchCopy` **只在同一账号内** ⇒ 跨账号**唯一**的路是
「**甲建一条分享 → 乙转存**」:

```bash
# 甲那一半:在 1 号的 App / 网页里给「监控简介」目录点「分享」,复制链接(约 10 秒,只能人工)
# 乙那一半(纯协议、可自动化):
python scripts/xunlei_intro_copy.py "<分享链>" --target xunlei#2        # 预演(只读)
python scripts/xunlei_intro_copy.py "<分享链>" --target xunlei#2 --yes  # 真搬
```

⚠️ **甲那一半需要 1 号还能登录**:2026-10-16 实测 1 号的凭据曾被串号 bug 覆盖掉
(库里两个 key 都成了 2 号)—— **当天已用网页 cookie 免扫码重铸救回**
(`python scripts/xunlei_login.py --cookie-file <网页cookie.txt> --cookie-key xunlei`)。
⚠️ 重铸**必须确认真正登记进了账号池**:池非空时**默认位那张凭据不会被用**,只写 cookie_store
等于「登了但没人用」(脚本已修成按「池里用起来了没」判)。

⚠️ 脚本搬完会**复核目标账号里有没有 `PAN_INTRO_XUNLEI_DIR` 那个目录名** ——
**搬进去但名字不对,简介照样静默不挂**,所以这一步必须报出来。
