# 全自动化监控与转化率口径 —— 设计方案(2026-10-04)

> 用户给定目标:
> 1. **公众号**:自己搜索 → 自己加进书架 → 按阅读数总结,**全自动化**
> 2. **知乎 / 贴吧 / 小红书 / 抖音** 同理,都要能自动化
> 3. **没有外链的平台**:只按**名字**去**资源库配对**
> 4. **转化率口径**:公众号阅读数 **30%** / 抖音分享数 **80%** / 其余平台播放量 **40%**
> 5. **基于已有的自研**(不重造轮子)
> 6. 估算值**给内部用**;客户群**只看到"火爆程度",不给具体数字** —— 具体多少推管理群

---

## 一、结论先行

| 目标 | 现状 | 缺什么 |
|---|---|---|
| 公众号全自动闭环 | **三段都已存在** | 只缺"**串起来自动跑 + 失败告警**" |
| 无外链平台按名字配对 | `resource_library.search_resources()` 现成 | 缺"**从标题挖资源名**"这一层,以及配对后的自动转存/推链 |
| 转化率 30/80/40 | **本次新建 `conversion.py`(单一事实源)** | 缺"把结果接进结算/周报/管理群" |
| 各平台自动化 | 知乎/B站(自研)✅;贴吧/小红书(MediaCrawler)✅;抖音(口令)✅ | 缺**统一的调度与失败告警** |

**最需要先说清的一件事**:三个系数乘的都是**别人的号 / 别人的视频**的曝光量
(对标号文章阅读数、线索视频转发量)。所以它算的是
**「这个资源有多热 ⇒ 预估能带来多少拉新」**,**不是我方实收**。
全程标「**预估**」,且**这一条要写进文案**,免得被当成结算真值。

## 二、转化率口径 —— 已落地为单一事实源

新增 `app/services/conversion.py`(**纯函数,不碰 DB**):

```
预估拉新量 = 曝光指标 × 平台系数
  公众号      read_num    × 0.30   ← 用户点名
  抖音        share_count × 0.80   ← 用户点名
  其余平台    play_count  × 0.40
```

### ⚠️ "播放量"在多数平台**根本取不到**(2026-10-04 实测,项目内 + GitHub 双路查证)

**第一轮:项目内**。MediaCrawler 存下来的记录里(逐条 dump 全部键):

| 平台 | 实际存下来的指标 |
|---|---|
| 小红书 | `liked_count` / `collected_count` / `comment_count` / `share_count` —— **无播放量** |
| 贴吧 | `total_replay_num`(回复数)、`total_replay_page` —— **无播放量,连浏览量都没有** |
| 抖音 | `liked_count` / `collected_count` / `comment_count` / `share_count` —— **无播放量** |

**第二轮:顺着源码再挖一层,发现分三种情况**:

| 平台 | 播放量 | 依据 |
|---|---|---|
| **B站** | ✅ **本来就有** | `store/bilibili/__init__.py:69` `video_play_count ← video_item_stat["view"]`;自研 `ranking/v2` 也返回 `stat` |
| **抖音** | ⚠️ **原始响应里有,被 MediaCrawler 丢掉了** | `store/douyin/__init__.py:97` 已取到 `statistics` 字典,却只映射了 `digg/collect/comment/share` 四项 —— **`play_count` 没映射**。补一行即可取到 ⚠️ **但仍需实测**:抖音对**别人的视频**常把 `play_count` 给 0 |
| **小红书** | ❌ **平台不给** | 卡片 JSON 里就没有该字段(`store/xhs/__init__.py:84-88` 映射的就是全部) |
| **贴吧** | ❌ **平台不给** | 公开接口只有回复数 |
| **知乎** | ⚠️ 搜索返回 `voteup_count`(赞),浏览量在**详情**里 | 需补详情请求 |

**第三轮:GitHub 上找经验 —— 找到了那条决定性的限制**。
项目 [`cwjcw/xhs_douyin_content`](https://github.com/cwjcw/xhs_douyin_content) 的 README 原文:

> 「由于平台的限制,**自己发布的视频/笔记的互动数据,无法通过 API 接口获取**……自动抓取抖音、
> 小红书**创作者中心**里的每条视频的**播放、完播、点击、2s 跳出、播放时长**……」

同类的还有 [`Skyler1n/XHS_Statistics`](https://github.com/Skyler1n/XHS_Statistics)(抓小红书创作者后台播放数据)。

⇒ **决定性结论:小红书/抖音的"播放量"是「创作者私有数据」** ——
**只对自己的号可见,别人的内容拿不到**。这不是技术问题,是平台设计。

**所以"其余平台按播放量的 40%"只剩下两条路**:

| 方案 | 做法 | 拿到的是什么 | 代价 |
|---|---|---|---|
| **A. 降级(已实现)** | 播放量 → 浏览量 → 分享数 → 互动总量,乘 0.4 | **别人内容的热度代理** | 量纲不同,**必须标 `basis`/`degraded`** |
| **B. 采我方创作者后台** | 扫码登录**我们自己的**小红书/抖音创作者中心,抓**我们自己作品**的播放量 | ✅ **真·播放量**,这时 40% 才接近"**我方效果**" | 新开一条采集源;只覆盖**我们自己发的内容**;需维护登录态 |

**B 是唯一能让"40%"名副其实的路**,而且它比 A 更贴近"结算真值"——
因为它量的是**我们自己的**曝光 × 转化。但前提是**我们确实在这些平台发内容**。
**要不要做 B,需要你定**:它是一条全新的采集链路(登录态 + 后台接口),不是补几行代码的事。

**A 里已实现的降级阶梯**:`播放量 → 浏览量 → 分享数 → 互动总量(赞+藏+评+转)`。

三条纪律(都有测试钉住):

1. **必须带出用的是哪一档**(`basis`)—— 0.4 乘在"播放量"和乘在"回复数"上量纲不同,
   **不许静默替换**;`degraded=True` 表示"没用上用户点名的那个指标"。
2. **拿不到返回 `None` 而不是 `0`** —— 0 会被读成"这资源没人看",事实是"我们不知道"
   (与 `admit_transfer` 的"不知道≠满"同一条纪律)。
3. **客户群不给数字**:`heat_level()` 只出 `🔥🔥🔥 极热 / 🔥🔥 很热 / 🔥 偏热 / 一般 / —`,
   一个数字都不含(有测试断言档位里不出现数字字符)。

### ⚠️ 一个需要你拍板的口径

同一条小红书笔记(赞 4013 / 藏 6498 / 评 28 / 转 419):

| 走哪档 | 算出 |
|---|---|
| 分享档(当前,阶梯里分享优先) | **167** |
| 互动档 | **4383** |

**差 26 倍。** 现在按"分享更接近曝光/传播"排的。若你认为小红书该按"点赞+收藏"看热度,
把 `share_count` 从 `EXPOSURE_LADDER` 拿掉即可(一行),测试已把两种口径都钉住。

### ⚠️ 抖音 `play_count`:补丁打了,但**实测拿不到值**(2026-10-04 实跑)

`store/douyin/__init__.py` 早就取到了 `statistics` 字典,原版只映射 digg/collect/comment/share
—— **`play_count` 没映射**。本仓已出补丁把它带出来(`patches/mediacrawler-douyin-playcount.patch`)。

**但实跑一次抖音搜索(203 条)的结论是**:

| 字段 | 有值 | 非 0 |
|---|---|---|
| **`play_count`** | 203 | **0** ← 抖音对**别人的视频**恒给 0 |
| `share_count` | 200 | 194 |
| `liked_count` | 200 | 196 |

同批数据里 share/like 都正常 ⇒ **不是抓取坏了,是抖音就是不给**——
与 §二 那条 GitHub 结论完全一致:**播放量是创作者私有数据**。

**所以:抖音按用户口径继续用 `share_count × 0.8`**;补丁保留(将来接自己的创作者后台可直接复用),
但 **`0` 必须当"平台没给"**——`conversion.ZERO_MEANS_MISSING` 已把曝光类的 0 当缺失。

> 为什么这条要紧:若把 0 当真实值,一条"点赞 4013"的笔记会被算成「曝光 0 × 0.4 = **预估 0**」,
> 而它明明是热门。**数字会精确地骗人** —— 不是大得离谱,而是小得像个结论。

## 二·五、**同一资源多人发布 → 必须按聚合判断**(2026-10-04 用户口径)

> 用户原话:「同一个资源会多个人发布,到时候你还可以根据多人发布的情况以及数据来结合判断,
> **而不是随机一个文章或者作品来判断**」。

这条**正好补上现有共振机制缺的一半**。仓库里已经有"多号同发"的雏形
(`resource_library.resonance_resources`,`resource_library.py:214-227`):

```sql
GROUP BY pan_url
HAVING COUNT(DISTINCT author) >= min_accounts     -- "被验证过"的门槛
ORDER BY COUNT(DISTINCT author) DESC              -- 或按最近一次被发(fresh)
```

### 资源身份怎么定

| 情况 | 身份 |
|---|---|
| **有盘链**(公众号/知乎直链/贴吧) | `pan_url` —— **现成的**,继续用 |
| **无盘链**(小红书/按名配对的那些) | **规范化资源名**(需新做,复用标题实体挖掘) |

### 聚合规则(要实现的)

```
给定一个资源身份:
  发布者集合  publishers = DISTINCT author          ← 现成做法
  样本数      N = |publishers|                      ← **必须带出来**
  曝光总量    exposure = Σ(每个发布者的曝光)          ← 跨人求和:不同人发 = 不同受众
  预估拉新    estimate = exposure × 平台系数
```

**三条纪律**:

1. **同一发布者的多次发布取"最大",不是求和** —— 同一个人反复发同一资源,
   受众高度重叠,求和会把它刷成"爆款"。
2. **`N` 必须带出来**。`N=1` 要明写"**单样本,可信度低**";
   `N≥2` 才是"被反复验证"(这就是共振的含义)。**不许把 N=1 和 N=5 算成同一件事。**
3. **聚合的是"同一个资源",不是"同一篇文章"** —— 用户点名要避免的正是"随机拿一个作品代表"。

⚠️ **跨平台要不要合并?** 暂定**分开**:抖音的分享数与公众号的阅读数**量纲不同**
(这也正是系数不一样的原因),混在一起乘同一个数会失真。跨平台只做"**同资源在几个平台出现过**"的
**计数**信号,不合并曝光量。

## 三、公众号全自动闭环(三段都已存在,只差串起来)

```
① 发现     discover_candidates()   搜狗微信搜索 + 从**我们自己库里**挖词
                                    → 产出候选号名(免费、免账号)
② 收录     add_benchmark_by_name() 号名 → WeRSS search_mp → fakeid
                                    → base64 → MP_WXS_* → 写进 weread_book_id
                                    ※ 这一步**必须留 WeRSS**:它是唯一可用的解析器
③ 监控     _listen 的轮转窗口       每轮问 25 个号的列表 → 拿精确 read_num
                                    (2026-10-04 已修好;窗口 ~2 天轮一圈)
④ 总结     read_num × 30%          进结算 / 复盘 / 管理群
```

**要补的只有两件事**:

1. **串成一条自动链**:现在 ①② 有 `wechat_candidates`(每天 08:20)与
   `wechat_candidate_import`(每天 08:30)两个作业 —— 已经自动。缺的是
   **②失败时有人知道**(现在 `listenable=0` 是安静的,见下方)。
2. **给"收录为 0"接告警**:`listenable=0` 本身正常(候选名对不上是常态),
   但**连续 N 天全 0** 就该有人看一眼。

### 彻底自研(摆脱 WeRSS)的路径

WeRSS 现在只承担一件事:**号名 → fakeid**。要自研掉它,只需给自研 `WempClient`
补上 `search_mp` + `add_feed`(它现在只有 `mp_articles`),走公众号后台 `searchbiz`。
⚠️ 那条路当前卡在 `200013` 频控 —— 但**低频调用(每天几次)大概率没事**,值得一试。
**在补上之前,WeRSS 不能删。**

## 四、无外链平台 → 按名字配对资源库

用户口径:**配对成功 → 自动转存 + 推我们自己的链。**

```
平台内容(小红书/知乎/贴吧…)
   ↓ 从标题/正文挖"资源名"(复用现有的标题实体挖掘)
   ↓ resource_library.search_resources(名字)          ← 现成的
   ├─ 命中 → 取我方链 → 转存/复用 → 推卡片
   └─ 未命中 → 记"库里没有",不产生动作(不许瞎猜)
```

**三条要做到的**:
- **同名即命中,形近不算**(沿用 `_subscribe_by_name` 的"拿不准一律空串,不猜"纪律)
- **命中后走现有转存链**,不新写一套(复用 `xunlei_transfer` / `quark_transfer`)
- **配对结果要可见**:卡片上标明"这是按名字匹配到的",与传统盘链区分开
  (用户口径:未搬要说明原因 —— 同理,按名匹配也要说明来源)

## 七、两条要守住的纪律

1. **预估 ≠ 实收,必须写在文案里。** 系数乘的是别人的曝光量,它是**需求侧**估算。
   本仓已经吃过一次亏:那 168 篇带阅读数的文章,一度被当成"我方效果"来复盘。
2. **降级不许静默。** 拿不到播放量就换分享、换互动 —— 换可以,**换完必须标出来**
   (`basis` / `degraded`)。这与本仓反复出现的「静默失败=假成功」是同一条线。
