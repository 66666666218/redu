# 阅读数 & 迅雷盘:结论与方案(2026-10-04)

> 这一天从"微信读书里能不能看到阅读量"这个问题开始,走了 **12 条路**,
> 中间**把一条正确的结论误判成错的**,最后**免费、精确的阅读数拿到了**。
>
> **这份文档的目的**:把结论钉死、把踩过的坑留痕,别让下一个人(或下一次的我)重走一遍。

---

## 一、结论先行

| 问题 | 结论 |
|---|---|
| **别人号的精确阅读数,能免费拿到吗?** | ✅ **能**。微信读书 `/web/mp/articles` —— **一直活着**,只是有**会话额度** |
| 额度是多少? | **每个会话约 29 个号**(实测),142 个号 **分 5 批轮转** |
| 拿到的精度? | **精确值**(如 `1151` / `682` / `183`),**不是分档** |
| 一次能拿多少篇? | 该号 **15~158 篇**的全部历史阅读数 |
| 迅雷盘满怎么办? | 盘 **79.9%**、剩 **6.04 TiB**,而卡住那个包要 **6.88 TiB** ⇒ **差 0.84 TiB** |

## 二、⚠️ 今天最重要的教训:我们把**对**的结论否掉了

**代码里本来写着**(`weread_client.py` docstring):

> 列表接口 `/web/mp/articles` **仅在会话续期后初期可用**,之后服务端恒 `-2041`

**我们在今天的排查里把它判定为"过期信念"并改掉了** —— 理由是做了"四层测试":
直接请求 / 伪 Referer / 正确 readerUrl / **真阅读器页内 fetch**,**全部 `-2041`**。

**但那四次测试有一个共同的前提错误**:
**它们都不是在"会话刚续期 + 额度没被前面的号烧掉"的条件下做的**。
`§9.2` 里早就写明:「81 号 × 每轮 2 次 ≈ 162 次/轮,会在**开头十几个号之内**把额度烧光」——
也就是说,那时候**排在后面的号必然拿不到**,而我又正好是用**后面的号**在测。

**重新实测(2026-10-04 傍晚,续期后按书架顺序从头测)**:

```
[  1] ✓ 小小栀颜      15 篇 | read_num 样本 [11, 78, 17, 1151]
[  2] ✓ 墨滴          75 篇 | [183, 682, 471, 266]
[  7] ✓ 爱娣的寻觅记  117 篇 | 有阅读数 107 条
[ 20] ✓ 长乐项目手记   13 篇
[ 30] ✗ 孤舟遗忘 —— code=-10100        ← 额度边界
成功 29 个号 | 70s | 2.4s/号
```

**⇒ 前 29 个号 100% 拿到精确阅读数。** 我们整套客户端(`WereadClient.mp_articles` +
`flatten_mp_articles`)**本来就能用**,一行代码都不用改。

**教训(写给自己)**:
> **"证伪"和"证真"一样需要控制变量。** 我用"排在额度之后"的号去证明"接口死了",
> 这和一个只看摘要就宣布"已经打通"的错误**是同一类**——方向相反而已。

## 三、精确阅读数:方案

### 3.1 现状(为什么会缺)

`_listen` 的 **⓪ 分支**一轮**对所有号**都要一次文章列表 →
**前 ~29 个拿到(含阅读数),后面的全部熔断** → 所以"大部分号没有阅读数"。

`_listen` 里那个**额度熔断器本身是对的**(第一次 `-10100/-2041` 就本轮不再问),
缺的是**"把额度轮流花在不同号上"**。

### 3.2 方案:列表额度**分批轮转**

复用**已有**的游标套路(`category_topics.advance_category` 就是同一个写法):

| 步 | 做法 |
|---|---|
| 1 | `system_config` 加游标 `weread_list_cursor`(存号 id 或序号) |
| 2 | 每轮从游标处取 **25 个号**(留余量:实测 29,取 25 更稳),**只对这 25 个号要列表** |
| 3 | 其余号**照旧只取 cover**(不花额度、必成功) |
| 4 | 本批**全部成功**才推进游标;**遇到额度错误就停、不推进** ⇒ 下轮从同一处继续,不丢号 |
| 5 | 续期后**立刻跑一批**(把最鲜的会话用在列表上) |

**轮转周期**:⚠️ **实测 2 天/圈**(原写 1.4 天,**是错的**,见下)。
按「上次问到列表时间最久」挑,全覆盖有闭式上界 `ceil(池/批) × ceil(批/窗口)`
= `ceil(142/36) × ceil(36/25)` = `4 × 2` = **8 轮 ≈ 2 天**(5 个随机种子实测都是 8 轮)。

⚠️ **同一段还有个实现级的坑,当天就改掉了**:第一版按**序号**切窗口 + 游标右移。
但一轮的号列表**既不是全量、次序还每轮都变**(先被 `_select_listen_batch` 按批轮转切成
36 号的子集,再被书架闸门 `sorted(rows, key=tier)` 按"有没有更新"重排)——
在那种列表上按序号切窗口,覆盖是**碰巧**而不是保证(模拟要 16~22 轮)。
改成按"最久没轮到"挑之后,与子集和排序**都无关**。

### 3.3 顺带修掉的两处

1. **文档里那句"接口已废弃"要改回来** —— 是**额度**问题,不是废弃;
   `§3.2`(外部接口速查)与 `_listen` docstring 一起更正。
2. **`-10100` 这个错误码要进额度熔断名单** —— 实测的边界码是它,
   而 `_WEREAD_QUOTA_MARKS` 现在只有 `-2014 -2041`。

### 3.4 ★ 事后:`§3.2` 的轮转**静默失效了两天**(2026-10-08 定位并修)

**症状**:2026-10-07 15:59 之后再没有一篇拿到阅读数,卡片阅读数列整片 `—`;
而**凭据是好的**(App token 13:52 刚续过、手工实测 3/3 个号拿回精确读数)。

**真凶在 `_list_window`**:`_list_key` 对**没有 `weread_book_id` 的号**返回空串,
而空串在记号里没有(取 0.0 ⇒ 排序最前)⇒ 窗口的 25 个名额**全被这些"永远用不上窗口"的号占住**,
`{...}` 集合推导又把 25 个空串**收敛成一个元素 `{""}`**;
真正有 bookId 的号 `_list_key(b) in {""}` **恒为 False** ⇒ **窗口对它们恒为空**。

⇒ 后果不是"被拦",而是**两条路一次都没被调用过**。实测那天的库:263 个号里 **57 个 bookId 为空**,
206 个有 bookId 的**全被挡在窗外**。

**指纹(以后照这个认)**:运行记录里

```
weread_list(ok=0 app=0 off=0 off_with_new=1 skipped=79)
```

**`ok`/`app`/`off` 全 0 而 `skipped` 满员 = "谁都没问过"**;
被风控/额度挡住会长成 `off>0`(或 `off_with_new>0`)—— 两者从计数就能分开,
不用去猜"是限流还是没跑"。

**修法**:`_list_window` 排队前先滤掉空键(写入侧 `_mark_listed` 本来就过滤空键,
说明"空键不是有效号"在写入侧早就成立,**漏的只是读取侧的排队**)。

**为什么两天没被发现**:告警全挂在"凭据失效/被拦"上(App 兜底失败会推飞书),
而这一次**根本没发出过请求** —— 没有任何错误路径会响。
⇒ 教训与 §3.4 的指纹配套:**"一条路好不好"要用"它有没有被调用过"来判,
不能只看"它有没有报错"(不报错的沉默,比报错更像正常)。**

## 四、迅雷盘:方案

### 4.1 数字(实测)

| 项 | 值 |
|---|---|
| 盘总容量 | 33,092,723,015,680 B = **30.10 TiB** |
| 已用 | 26,454,214,882,191 B = **24.06 TiB**(**79.9%**) |
| **剩余** | **6.04 TiB** |
| 回收站占用 | **586 KB**(几乎为空,**不是元凶**) |
| 卡住的那个包 | 迅雷自己报 **`required_size` = 6.88 TiB** |
| **缺口** | **≈ 0.84 TiB** |

**⇒ 不是"盘满了",是"这一个包比剩下的空间还大"。**

### 4.2 为什么闸门没挡住(已修)

盘级预闸门按「使用率 ≥ 90%」挡 —— 而实际 **79.9% 就已经搬不进这个大包**,
所以闸门**结构上挡不住**「单个资源比剩余空间大」这件事。
已加**「闸门失准」告警**(见 `operations.md §4o`),把这个区别报给运维。

### 4.3 可选的处置(按性价比)

| 选项 | 做法 | 代价 |
|---|---|---|
| **① 放弃那个包** | 就一个资源包,不值当为它动盘 | **0** |
| **② 清理腾空间** | 开 `xunlei_cleanup`(过期清理,**默认关**)/ 手动清泛化大包合集 / **清空回收站** | 要人看一眼清单 |
| **③ 扩容** | 迅雷会员容量 +1 TiB | 花钱 |
| **④ 修正吞吐策略** | 转存前**按 `required_size` 预判**(迅雷报错里带这个数),超了就**只推链不搬**、并记明原因 | 半天 |

**建议:先做 ④(把"单个太大"变成可预判的一件事),再看要不要 ②/③。**
`required_size` 是迅雷**自己给的数**,用它预判比用"使用率"准得多。

### 4.4 ✅ ④ 已落地(2026-10-04 晚)

| 改动 | 位置 |
|---|---|
| 转存前用分享各文件 `size` 之和比剩余空间,超了**连试都不试** | `xunlei_transfer.share_required_bytes` |
| 真撞上时取迅雷自己报的 `required_size`,把「需要/剩余/还差」写进失败文案 | `xunlei_transfer.required_size_from_error` |
| **单个太大的那条只跳过它自己,不再拖停整批**;保持 `pending`(清空间后仍可搬) | `xunlei_group.transfer_pending` |
| 本轮跳过数写进运行记录(否则"没搬成"和"今天真没这条"长得一样) | `xunlei_group.xunlei_group_tick` |

⚠️ **三条边界都刻意守住了**:⒜ 文件夹 `size` 恒 0 ⇒ 预判只是**下限**,只会漏报不会误报;
⒝ 配额探针拿不到时**照常转**(「不知道 ≠ 满」);⒞ **"单个太大"与"闸门失准"分开报** ——
前者不用人工动作,后者才要。
⇒ **所以 ②/③ 现在不必急着做**:⒜ 不会再堵住别人,⒝ 到底要不要清盘,等真正搬不动**大部分**资源时再说。
